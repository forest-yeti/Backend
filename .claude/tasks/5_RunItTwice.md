# Задача 5. Run it twice: два прогона борда при олл-ине

Расширение `lib/block_poker/engine/hand.ex`, `lib/block_poker/tables/table_server.ex`
и шаблона кэш-игры. Когда ставок больше не будет, а борд не доведён, двое
оставшихся могут договориться разыграть недостающие улицы **дважды** — каждый
прогон забирает половину банка.

Ключевое наблюдение, на котором держится вся задача: **колода тасуется один
раз целиком** в `Hand.start/3`, а улицы лишь откусывают от её головы
(`deal_street/1`). Второй прогон — это продолжение той же колоды, а не новая
случайность: карты первого прогона исключены сами собой, RNG не трогается,
`Engine.Rng` не меняется. Ровно то же свойство уже используется в
`Engine.Rabbit`.

Второе наблюдение, экономящее половину работы: **слои банка от борда не
зависят.** `levels`, суммы, `eligible` и возврат неотвеченной ставки в
`split_pots/2` считаются по вложениям игроков; от карт зависят только
победители. Значит два прогона — это один расчёт слоёв и две ранжировки,
а не два независимых расчёта банка.

Чего в задаче нет: трёх и более претендентов (§9), трёх и более прогонов
(§9), турниров (§3.1 — там функция выключена навсегда), клиентской части
(отдельный документ в `client-tasks/`).

---

## 1. Цель

* `cash_game_settings.allowed_run_it_twice` — флаг шаблона, по умолчанию
  `true`, включая все существующие строки.
* Согласие обоих претендентов запрашивается явно, с таймаутом; молчание —
  отказ.
* Ровно два прогона, ровно два претендента. Всё остальное — обычная доводка,
  байт-в-байт как сегодня.
* Рейк берётся **один раз** с полного банка, до деления на прогоны.
* Инвариант §11 «фишки не возникают и не исчезают» не ослабляется ни на
  одну фишку, включая нечётный остаток.
* Ноль знания о run it twice в `socket/*` и `api/*` (§3).

---

## 2. Когда предложение возможно

Все условия обязаны выполниться одновременно, и проверяет их **чистая
функция ядра**, а не оболочка:

1. Ставок больше не будет — раздача входит в доводку (`begin_runout/1`,
   `hand.ex:398`). Обычный чек-даун до ривера сюда не относится: там борд
   доводится ставками, а не случаем.
2. Претендентов ровно два (`contenders/1`, статус `!= :folded`).
3. Борд не полон: `Hand.board_plan(hand) != []`. Олл-ин на ривере
   разыгрывать нечего.
4. Раздача заведена с разрешением (`hand.run_it_twice_allowed?`, §3).
5. В колоде хватает карт на оба прогона. Для холдема и Short Deck это
   всегда так, но проверка живёт в коде, а не в комментарии: варианты с
   четырьмя карманными картами добавляются одной строкой в реестр.

Порядок событий важен: **карты открываются раньше предложения.** Игрок
решает, видя расклад и эквити, как в любом современном руме. `all_in_showdown`
уходит первым, предложение — вторым.

## 3. Разрешение: кто и где решает

### 3.1 Режим важнее шаблона

Run it twice — функция кэш-игры. В турнирах и любых будущих режимах она
**выключена всегда**, без настройки: турнирная фишка — это позиция в
структуре мест, и дробление банка по прогонам меняет распределение мест.

Решение принимает `GameMode` — тот самый шов «политика между раздачами»
(`lib/block_poker/game_mode/game_mode.ex`). Новый колбэк:

```elixir
@doc "Разрешён ли run it twice за этим столом. Турниры отвечают false всегда."
@callback run_it_twice?(RoomState.t()) :: boolean()
```

* `GameMode.Cash` — `state.setting.allowed_run_it_twice`.
* Любой будущий режим — литерал `false`. Поля в его настройках не заводится.

Запрет на будущее: не добавлять «разрешить RIT» в турнирные настройки и не
писать `case` по режиму нигде, кроме реализации behaviour.

### 3.2 Шаблон кэш-игры

Миграция `add_cash_game_run_it_twice`:

```elixir
add :allowed_run_it_twice, :boolean, null: false, default: true
```

`default: true` на уровне колонки закрывает и существующие строки, и будущие
вставки мимо changeset'а — отдельный `execute UPDATE` не нужен. Поле
добавляется в `schema`, в `@editable` и в `mix cash_game.seed`.

### 3.3 Как разрешение доходит до движка

Через `HandSetup` — флагом, а не ссылкой на шаблон, как уже сделано
с блайндами:

```elixir
run_it_twice_allowed: boolean(), default: false
```

`Cash.build_setup/2` кладёт туда результат `run_it_twice?/1`. Движок про
`CashGameSetting` по-прежнему не знает ничего. **Дефолт в структуре —
`false`:** искусственный вариант в тестах и любой новый режим получают
выключенную функцию молча, а не по забывчивости.

## 4. Согласие: новая фаза раздачи

### 4.1 Состояние

Новый модуль `Engine.RunItTwice` — чистая логика согласия и деления. Его
структура живёт в поле `hand.rit`:

```elixir
%RunItTwice{
  seats: [pos_integer()],                  # ровно два претендента
  answers: %{pos_integer() => boolean()},  # неотвеченные отсутствуют
  status: :offered | :accepted | :declined
}
```

`hand.rit == nil` означает «предложения не было» — это состояние всех
сегодняшних раздач, и весь существующий код с ним работает без правок.

### 4.2 Переходы

```
begin_runout(hand)
  ├─ не подходит по §2 ──▶ runout?: true            (сегодняшнее поведение)
  └─ подходит ──▶ rit: %{status: :offered}, runout?: false
                  события: [{:all_in_showdown, …}, {:run_it_twice_offer, …}]
```

Две новые функции ядра:

```elixir
@spec answer_run_it_twice(t(), seat :: pos_integer(), boolean()) ::
        {:ok, t(), [event]} | {:error, atom()}
@spec close_run_it_twice(t()) :: {:ok, t(), [event]} | {:error, atom()}
@spec offering_run_it_twice?(t()) :: boolean()
```

* `answer_run_it_twice/3` пишет ответ. Отказ **закрывает окно немедленно** — ждать
  второго ответа незачем. Согласие обоих — тоже. Повторный ответ того же
  места — `{:error, :already_answered}`; ответ не претендента —
  `{:error, :not_a_contender}`; когда `rit == nil` —
  `{:error, :run_it_twice_not_offered}`.
* `close_run_it_twice/1` вызывается по таймауту снаружи и трактует **неотвеченное
  как отказ**. Молчание не может стоить игроку половины банка при отказе
  оппонента, но и подвесить стол не может.

Обе ведут в одно место: `status` фиксируется, `runout?: true`, доводка
начинается обычным порядком. Событие
`{:run_it_twice_decided, %{accepted: bool, answers: …}}`.

Отдельно: **дисконнект во время окна — это отказ.** Grace-период
реконнекта (§5 CLAUDE.md) здесь не применяется: фишки уже в банке, ход
делать не нужно, и держать стол ради вернувшегося нельзя.

## 5. Два борда

### 5.1 Хранение

`hand.board` остаётся первым прогоном — его читают `Showdown`, `Equity`,
`Outs`, `take_rake`, `TableView` и все тесты. Второй прогон — новое поле
`hand.board_2 :: [Card.t()] | nil`, `nil` при обычной раздаче.

Общий префикс борда (карты, легшие до олл-ина) принадлежит **обоим**
прогонам: `board_2` инициализируется копией `hand.board` в момент принятия
предложения и дальше расходится с ним.

### 5.2 Раздача улиц

Прогоны идут **синхронно, улица в улицу**, а не «первый до ривера, потом
второй»: так это выглядит в GG и PokerStars, и так один тик таймера
`@runout_step_ms` показывает игроку обе карты сразу.

`deal_street/1` при активном RIT берёт с головы колоды `count` карт в
первый борд, следом ещё `count` — во второй. Порядок фиксирован и является
частью правил: он определяет, какой прогон какие карты получил, и должен
быть воспроизводим по seed в тестах.

### 5.3 Эквити и ауты: борд свой, колода общая

`equity_payload/1` считается **по каждому борду отдельно** — после флопа
расклады разные, и общий процент смысла не имеет. Событие `equity_update`
получает форму `%{runs: [%{run: 1, equity: [...]}, %{run: 2, equity: [...]}]}`.

Но борд у прогонов разный, а **колода одна**, и это не деталь отображения,
а правило счёта. Карта, легшая на тёрн первого прогона, физически ушла из
колоды и на втором борде выйти уже не может.

> Пример, ради которого пункт существует: на флопе у игрока четыре аута.
> На тёрне первого прогона приходит один из них — игрок переехал, но на
> ривере всё равно проиграл. На втором прогоне аутов у него уже **три**,
> а не четыре: четвёртая карта лежит на первом борде.

Показать во втором прогоне ауты, которых в колоде нет, — прямая ложь
игроку и завышенный процент эквити. Поэтому:

**Множество мёртвых карт — общее на оба прогона, борд — свой.** При счёте
прогона `N` в `dead_cards` уходят карты, лежащие на **чужом** борде и
отсутствующие на своём (общий префикс до олл-ина в `dead_cards` не идёт —
он уже учтён как `board`).

Отдельной работы в движке это не требует: `Outs.compute/4` и
`Equity.equity/4` **уже принимают `dead_cards`** четвёртым аргументом и
опцией соответственно (`outs.ex`, `equity.ex`). Задача — правильно их
заполнить, а не научить чему-то новому:

```elixir
defp dead_for(hand, board, other_board), do: other_board -- board
```

Момент предложения (борды ещё не разошлись) — вырожденный случай той же
формулы: `dead_cards == []` у обоих, проценты совпадают. Это верно и по
теории: пока ни одна карта не открыта, маргинальное распределение каждого
прогона одинаково.

Стоимость: Монте-Карло гоняется дважды. При `iterations: 20_000` и двух
руках это по-прежнему миллисекунды, отдельной оптимизации не требует.

## 6. Банк: слои считаются один раз

Это центральная правка `hand.ex`, и она полезна сама по себе — сегодняшний
`split_pots/2` смешивает две несвязанные вещи.

### 6.1 Разделение

`split_pots/2` разрезается на две функции:

```elixir
# Не зависит от борда: суммы, претенденты, рейк, возвраты.
defp pot_layers(hand) :: {[%{amount: …, eligible: […]}], refunds :: map(), rake :: non_neg_integer()}

# Зависит от борда: кто выиграл каждый слой.
defp resolve_layers(layers, place_of) :: [%{amount: …, winners: […]}]
```

`take_rake/3` переезжает в `pot_layers/1` и вызывается **ровно один раз на
слой**, независимо от числа прогонов. Наивное «прогнать `payout/1` дважды»
сняло бы с игроков двойной рейк — это главный денежный риск задачи, и
структура кода должна делать такую ошибку невыразимой, а не запрещать её
комментарием.

Возврат неотвеченной ставки (`refunds`) — тоже один раз: он про ставки, не
про карты.

### 6.2 Деление на прогоны

Для каждого слоя:

```
share_1 = div(amount, 2) + rem(amount, 2)
share_2 = div(amount, 2)
```

**Нечётная фишка достаётся победителю первого прогона.** Правило
детерминированное, объяснимое игроку одной фразой и не зависящее ни от
позиции, ни от порядка мест. Внутри одного прогона деление между
несколькими победителями (ничья) остаётся как есть — `distribute/3`,
остаток ближайшему по часовой от кнопки.

### 6.3 Форма результата

`results` становится списочной по прогонам — **всегда**, включая обычную
раздачу с одним прогоном. Один код исполнения вместо двух веток:

```elixir
%{
  runs: [
    %{run: 1, board: [...], pots: [...], placements: [...]},
    %{run: 2, board: [...], pots: [...], placements: [...]}   # только при RIT
  ],
  payouts: %{seat => total},   # сумма по всем прогонам, плоско
  rake: non_neg_integer(),     # один на раздачу
  showdown?: boolean()
}
```

`payouts` остаётся плоским словарём: `finish/1` зачисляет фишки в стеки
один раз, и инвариант сохранения проверяется против него.

Потребители, которые придётся пройти:

| Место | Что меняется |
|---|---|
| `Hand.finish/1` | зачисление стеков — без изменений, `payouts` плоский |
| `Hand.finish_payload/2` | отдаёт `runs`; `board`/`pots` верхнего уровня уходят |
| `Hand.shown_cards/2` | `category` руки считается по **первому** борду |
| `HandStats.finish/2` | читает `results.showdown?` — без изменений |
| `Cash.on_hand_finished/2` | `results` игнорирует — без изменений |
| `Rabbit.runout/1` | читает `results.showdown?` — без изменений |
| `TableServer.record_stats/2` | без изменений |

### 6.4 Rabbit hunting

Пересечения нет: rabbit доступен только после раздачи, законченной **фолдом**,
RIT возможен только при доводке всех олл-инов. Но `Rabbit` читает хвост
`hand.deck`, который второй прогон уже потратил, — на это нужен явный тест,
а не рассуждение.

## 7. Оболочка: `TableServer`

### 7.1 Таймер

Новый тип таймера `:rit`, константа `@rit_offer_ms` рядом с
`@runout_step_ms`. По срабатыванию — `Hand.close_run_it_twice/1`, дальше обычный
`apply_hand/3`. Окно взводится один раз: ответ первого из двоих не должен
продлевать время второму, поэтому `arm_rit_timer/1` не трогает уже
выставленный `rit_deadline_at`.

`apply_hand/3` получает третью ветку в `cond`:

```elixir
Hand.finished?(hand)     -> finish_hand(...)
Hand.offering_run_it_twice?(hand) -> arm_rit_timer(state)
hand.runout?             -> schedule(cancel_timer(state, :action), :runout, @runout_step_ms)
true                     -> advance_to_actor(state, hand)
```

### 7.2 Точка входа

`Tables.answer_run_it_twice(table_id, user_id, accept?)` → `handle_call` →
`Hand.answer_run_it_twice/3`. Авторизация («он ли претендент») — внутри `Hand.answer/3`,
не в канале и не в сервере: это правило игры.

Ответ, закрывший окно (согласие обоих или первый отказ), **отменяет таймер
`:rit`** и сразу переходит к доводке. Просроченный таймер после этого
игнорируется — обычным механизмом `deadline_ref`.

### 7.3 Снапшот и реконнект

Открытые карты доводки уже живут в `room.showdown`, чтобы подключившийся
в середине увидел стол, а не пустоту (`emit({:all_in_showdown, …})`).
Туда же добавляется блок предложения, а дедлайн — в `room.rit_deadline_at`,
рядом с `deadline_at`. Игрок, переподключившийся внутри окна, получает
предложение с **остатком** времени и может ответить.

## 8. Протокол

Клиент → сервер (топик `table:<id>`):

```
"run_it_twice"  %{accept: true}
```

Сервер → клиент:

```
"run_it_twice_offer"    %{seats: [3, 5], deadline_ms: 8000}
"run_it_twice_decided"  %{accepted: true, answers: %{"3" => true, "5" => true}}
"street_dealt"          %{street: …, board: [...], board_2: [...] | null, pot: …}
"equity_update"         %{runs: [%{run: 1, equity: [...]}, %{run: 2, equity: [...]}]}
"all_in_showdown"       %{board: …, players: …, equity: [%{run: 1, equity: [...]}, …]}
"hand_finished"         %{runs: [%{run: …, board: …, pots: …}], payouts: …, rake: …, showdown: …, shown: …}
```

`board_2: null` и `runs` длины 1 — обычная раздача. Клиент различает случаи
по данным, а не по отдельному флагу режима.

Новые коды в `BlockPoker.ErrorCode`: `run_it_twice_not_offered`,
`not_a_contender`, `already_answered`.

Канал остаётся тем, чем должен: разобрал `%{accept: boolean}`, взял
`user_id` из `assigns`, позвал одну функцию контекста, смапил ошибку.
Ни одного `case` по улицам, ни одной арифметики над фишками.

## 9. Чего в задаче нет

* **Три и более претендентов.** Ограничение heads-up — в `Engine.RunItTwice`
  одной проверкой длины. Слои банка уже посчитаны обобщённо, так что снятие
  ограничения позже — это правка условия и новые тесты, не переделка.
* **Три и более прогонов.** `runs` списочный, но деление зашито пополам,
  а настройка булева. Осознанно: N прогонов требуют другого UI и другого
  правила остатка.
* **Турниры.** Выключено навсегда, см. §3.1.
* **Клиент.** Два ряда карт борда, два процента эквити, окно согласия —
  `.claude/client-tasks/19_RunItTwice.md`.

## 10. Тесты

### Уровень 1 — ядро (`test/block_poker/engine/`), без БД и процессов

* Предложение возникает ровно по §2: по одному тесту на каждое из пяти
  условий, включая полный борд на ривере и запрещённый флаг.
* Отказ любого из двоих даёт борд и выплаты, **идентичные сегодняшним** —
  регрессия на то, что обычный путь не поехал.
* Второй борд не пересекается с первым и с карманными картами ни одной
  картой (проверяется на конкретном seed).
* Ауты второго прогона не содержат карт, лежащих на первом борде, и
  наоборот (§5.3). Тест ставится на конкретном раскладе: у игрока четыре
  аута на флопе, один из них приходит на тёрн первого прогона — во втором
  прогоне их остаётся три. Эквити считается с тем же `dead_cards`.
* Рейк при RIT равен рейку при одном прогоне с тем же банком. Отдельный
  тест — самый дорогой баг задачи.
* Нечётный банк: остаток ушёл победителю первого прогона; разный
  победитель в прогонах делит банк ровно пополам ±1.
* Property (`StreamData`): сумма стеков до раздачи равна сумме после,
  для любого банка, любого числа улиц до олл-ина и обоих исходов согласия.
* Property: `results.rake` не зависит от числа прогонов.
* `Rabbit.runout/1` после раздачи с RIT ведёт себя корректно (§6.4).

### Уровень 2 — процессы (`test/block_poker/tables/`)

* Таймаут окна = отказ; часы инжектируются, `Process.sleep` запрещён.
* Согласие обоих отменяет таймер `:rit`; просроченный тик игнорируется.
* Отказ первого не ждёт второго ответа.
* Реконнект внутри окна: снапшот содержит предложение с остатком времени.
* Дисконнект = отказ.

### Уровень 4 — каналы

* Два сокета, олл-ин, оба принимают → оба получают `street_dealt` с
  `board_2` и `hand_finished` с двумя прогонами.
* `run_it_twice` от не претендента → `not_a_contender`, стол не сдвинулся.

### Инварианты

* Приватность: `board_2` и хвост колоды не утекают до сдачи улицы —
  проверяется на сыром payload.
* Границы слоёв: в `lib/socket/**` и `lib/api/**` нет ни `run_it_twice?`,
  ни `board_2`-арифметики, ни ветвления по `rit.status`.

## 11. Порядок работ

1. Миграция + поле шаблона + `mix cash_game.seed` + колбэк
   `GameMode.run_it_twice?/1` + поле `HandSetup`. Ничего не включает,
   ничего не ломает.
2. Рефакторинг `split_pots/2` на `pot_layers/1` + `resolve_layers/2`,
   `results` → `runs` списочный. **Поведение не меняется**, все существующие
   тесты зелёные. Отдельный коммит — так проще ревьюить денежную часть.
3. `Engine.RunItTwice` + `begin_runout/1` + `answer/3` + `close_offer/1`,
   тесты уровня 1.
4. Второй борд: `board_2`, `deal_street/1`, эквити по прогонам.
5. Деление банка пополам, нечётная фишка, property-тесты.
6. `TableServer`: таймер, снапшот, реконнект; тесты уровня 2.
7. `Tables` API, канал, коды ошибок; тесты уровня 4.
