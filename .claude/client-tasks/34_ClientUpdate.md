# Клиент. Задача 34. Автообновление приложения

Бэкенд и клиент выкатываются часто и парой: изменение протокола на сервере
почти всегда требует новой сборки Electron. Пока обновление зависит от того,
скачает ли игрок инсталлятор вручную, рассинхрон клиента с сервером будет
проявляться как случайные баги у части игроков — самый дорогой вид ошибки,
потому что воспроизвести его у себя невозможно.

Задача закрывает это двумя механизмами: **сервер знает, какая сборка
актуальна и какая минимально допустима**, а клиент умеет **обновиться сам**,
не выходя из приложения.

---

## 1. Что сервер знает о версиях

Две границы, обе живут в конфигурации сервера и поднимаются без передеплоя:

| Граница | Смысл |
|---|---|
| `minimum` | ниже неё сборка в игру **не пускается вообще** |
| `current` | актуальная сборка; всё, что между `minimum` и `current`, играет, но устарело |

Спросить их можно в любой момент, **без токена и без сокета**:

```
GET /api/client/version
```

```json
{
  "current": "1.4.2",
  "minimum": "1.4.0",
  "feed_url": "https://cdn.block-poker.example/client-updates"
}
```

Ручка публичная намеренно. Её спрашивают до логина, до сокета и — главное —
той самой сборкой, которую в игру уже не пускают: иначе обновиться было бы
нечем. `feed_url` приходит с сервера, а не зашивается в сборку, чтобы переезд
раздачи на другой хост не требовал релиза того клиента, который этим релизом
и обновляют. **Не хардкодьте адрес фида.**

`feed_url` может прийти `null` — это рабочее состояние ноды, где раздача
обновлений не настроена. Тогда проверку обновлений просто не запускаем.

## 2. Версия сборки при подключении сокета

К параметрам `connect` добавляется `client_vsn` — версия приложения в semver,
та же, что в `package.json`:

```js
new Socket("wss://.../socket", {
  params: {
    token,
    protocol_vsn: "1",
    client_vsn: app.getVersion()
  }
})
```

`client_vsn` — это версия **сборки**, `protocol_vsn` — версия **формата
сообщений**. Они не связаны: протокол меняется редко, сборка — каждый релиз.
Присылайте оба, не подменяйте одно другим.

Если сборка ниже `minimum`, handshake **отклоняется**:

```json
{ "code": "client_too_old", "message": "Версия приложения устарела, требуется обновление" }
```

Отдельный код, а не `unsupported_protocol_version`: там клиент не понимает
формат сообщений, здесь — понимает, но устарел, и лечится это обновлением.

Проверка версии идёт **раньше проверки токена**. Это важно для вашей
обработки ошибок: устаревшая сборка получит `client_too_old` даже с
протухшим токеном, и уходить в цикл «продлить токен → снова отказ» не надо.
Увидели `client_too_old` — прекращаем попытки подключения и показываем экран
обновления. Никаких ретраев: сколько ни переподключайся, версия не вырастет.

## 3. Само обновление: `electron-updater`

Файлы релиза (`latest.yml` + инсталляторы) лежат по `feed_url` как обычная
статика. Со стороны клиента это generic-провайдер:

```js
const { autoUpdater } = require("electron-updater")

autoUpdater.autoDownload = false          // качаем только по кнопке
autoUpdater.setFeedURL({ provider: "generic", url: feedUrl })

autoUpdater.on("update-available", (info) => showUpdatePrompt(info.version))
autoUpdater.on("download-progress", (p) => renderProgress(p.percent))
autoUpdater.on("update-downloaded", () => autoUpdater.quitAndInstall())
autoUpdater.on("error", (err) => showUpdateFailed(err))
```

`autoDownload = false` — осознанно. Игрок должен нажать «Обновить» и увидеть
прогресс: молчаливая закачка 100 МБ на слабом канале выглядит как «клиент
тормозит посреди раздачи», и виноват в этом будет стол, а не апдейтер.

`quitAndInstall()` закрывает приложение, инсталлятор ставит новую версию и
запускает её. Для игрока это: диалог → прогресс → приложение перезапустилось.

### Когда проверять

* **На старте, до логина** — обязательный шаг. Дёрнули `GET /api/client/version`,
  сравнили с `app.getVersion()`, решили.
* **По отказу в handshake с `client_too_old`** — тот же экран, но выйти из
  него без обновления нельзя.
* Периодический опрос **не нужен**. Сервер ничего не пушит про обновления
  специально: обновление применяется перезапуском приложения, а между
  деплоем и перезапуском игрок доигрывает на старой сборке — это нормально,
  ровно для этого и существует зазор между `minimum` и `current`.

## 4. Два режима на экране обновления

Решение принимается сравнением своей версии с обеими границами:

| Своя версия | Режим | Поведение |
|---|---|---|
| `< minimum` | **обязательное** | Играть нельзя. Экран обновления вместо входа, кнопка «Обновить», закрыть можно только выходом из приложения. |
| `>= minimum`, `< current` | **добровольное** | Ненавязчивый баннер «доступна версия 1.4.2 · Обновить». Игрок продолжает играть. |
| `>= current` | ничего | Экран не показываем. |

Сравнение — по semver, не строкой: `1.10.0` новее, чем `1.9.0`, хотя
лексикографически меньше. Возьмите готовый `semver.lt` — самописное сравнение
на этом и ломается.

---

## 5. Главное правило: не обновляться посреди раздачи

`quitAndInstall()` во время раздачи — это фолд и потерянные деньги. Даже
обязательное обновление применяется только тогда, когда игроку нечего терять:

* игрок **за столом с фишками** — баннер показываем, `quitAndInstall()`
  не зовём; ждём, пока он встанет;
* игрок **в лобби, наблюдателем или не залогинен** — применяем сразу;
* сборка ниже `minimum` — до стола дело и не дойдёт: сокет её не пустил,
  фишек на столе у неё нет, и обновляться можно немедленно.

Скачать обновление в фоне, пока игрок за столом, можно — устанавливать нельзя.
Разделение `downloadUpdate()` и `quitAndInstall()` существует ровно для этого.

---

## 6. Что показывать, когда обновление не удалось

Обновление ходит в сеть и падает: нет места на диске, оборвался канал,
антивирус съел инсталлятор. Экран обновления обязан иметь выход:

* понятный текст ошибки и кнопка «Повторить»;
* ссылка на ручное скачивание того же инсталлятора (адрес берётся из
  `latest.yml` по `feed_url`) — на случай, когда автообновление не работает
  в принципе;
* при **добровольном** обновлении ошибка не должна мешать играть: свернули
  баннер и живём дальше.

Отдельно: на Windows без подписи кода установка вызовет предупреждение
SmartScreen. Это не ошибка клиента и обходить её не нужно — вопрос решается
сертификатом на стороне сборки.

---

## 7. Чек-лист приёмки

* [ ] `client_vsn` уходит в параметрах `connect` рядом с `protocol_vsn`.
* [ ] `feed_url` берётся из `GET /api/client/version`, а не из константы в коде.
* [ ] `feed_url: null` не роняет приложение — проверка обновлений просто
      не запускается.
* [ ] Отказ `client_too_old` ведёт на экран обновления и **не** вызывает
      повторных попыток подключения и продления токена.
* [ ] Версии сравниваются по semver (`1.10.0` > `1.9.0`).
* [ ] Обязательное обновление не даёт войти в игру; добровольное — не мешает.
* [ ] `quitAndInstall()` не вызывается, пока игрок сидит за столом с фишками.
* [ ] Прогресс закачки виден игроку.
* [ ] Провал обновления оставляет выход: повтор и ручная ссылка.
