# Задача 8. Панель администратора (Admin Panel)

Отдельное веб-приложение на Vue, которое запускается на машине администратора и
смотрит на прод или тест по конфигу. В бэкенде появляется новый транспортный
неймспейс `admin/*` и новый контекст ядра `BlockPoker.Admin`.

Панель делает три вещи: **показывает состояние рума** (игроки, деньги, живые
игры всех четырёх режимов), **правит деньги и статус игрока** и **даёт отладочный
god-mode на любой стол** — весь поток сообщений и все карты открытыми.

---

## 1. Цель

По завершении задачи:

* пользователь с `users.role == :admin` входит в панель теми же email/паролем,
  что и в игровом клиенте, но получает **отдельный admin-токен**, не
  взаимозаменяемый с игровым;
* админ видит постраничный список всех пользователей с балансами `main` и
  `play_money`;
* админ видит живые списки всех четырёх режимов: кэш, MTT, Spin & Go
  (`sit_and_go`), OFC (`ofc_cash`) — с составом игроков;
* админ может забанить/разбанить игрока, начислить ему `main` или `play_money`
  и перевести деньги с его кошелька на свой;
* админ может открыть любой стол в режиме наблюдения и видеть в реальном
  времени входящие intent'ы игроков, исходящие события ядра и **все карманные
  карты открытыми**;
* каждое действие админа записано в `admin_audit` и необратимо привязано к
  конкретной админской сессии;
* всё покрыто тестами уровней 3 и 4 (§11 CLAUDE.md).

**Вне объёма:** редактирование `cash_game_settings` и сеток турниров из панели
(правятся в БД, см. §6 CLAUDE.md), рассылки игрокам, тикеты поддержки,
античит-аналитика, метрики и графики, роли кроме `admin`.

---

## 2. Решения, принятые до реализации

| Вопрос | Решение | Почему |
|---|---|---|
| Транспорт | Отдельный HTTP `/admin/*` **плюс** отдельный сокет `/admin/socket` | Списки и деньги — это чтение с пагинацией и транзакционная запись, то есть HTTP (§3 CLAUDE.md). God-mode стола — это push, то есть сокет. Игровой `UserSocket` не трогаем вообще. |
| Аутентификация | Те же email/пароль, но **отдельный токен** и отдельный `refresh` | Игровой токен не должен давать доступ к панели, даже если утёк из Electron'а. |
| Роли | Одна роль `admin` (поле `users.role` уже существует) | Уровни доступа не нужны, пока админ один. |
| Списание на админа | Перевод: `−игроку / +админу` в одной транзакции | Сумма фишек в системе не меняется — инвариант «сохранение фишек» (§11 CLAUDE.md) остаётся в силе и продолжает проверяться тестом. |
| God-mode | Админ видит карты **немедленно**, без задержки и без ограничений | Режим существует **только для отладки до релиза** и вырезается перед публичным запуском (§14). Ограничивать его бессмысленно: отладка требует полной картины. Единственная сопутствующая мера — запись открытия стола в `admin_audit`. |
| Режимы | Все четыре: `cash`, `mtt`, `sit_and_go`, `ofc_cash` | Реализованы в ядре; панель работает через общий контракт «игровая сессия». |

## 3. Модель данных

### `users` — изменений нет

Роль уже есть: `role` (`Ecto.Enum`, `:default | :admin`, default `:default`),
назначается `mix user.role`. Панель её только читает.

Статус `status` (`:active | :blocked`) уже есть — бан панели пишет именно туда.

### `admin_sessions` — новая таблица

Админский вход живёт отдельно от `refresh_tokens`, чтобы отзыв игровых
токенов и отзыв доступа в панель были разными операциями.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `binary_id` | PK |
| `user_id` | `binary_id` | FK → `users`, NOT NULL |
| `token_hash` | `string(255)` | NOT NULL, UNIQUE — хранится **хэш** refresh-токена |
| `ip` | `string(45)` | NOT NULL — IPv4/IPv6 на момент логина |
| `user_agent` | `string(255)` | NULL |
| `expires_at` | `utc_datetime_usec` | NOT NULL |
| `revoked_at` | `utc_datetime_usec` | NULL |
| `last_seen_at` | `utc_datetime_usec` | NOT NULL |
| `inserted_at` / `updated_at` | `utc_datetime_usec` | NOT NULL |

Индексы: `user_id`, `expires_at`, unique на `token_hash`.

### `admin_audit` — новая таблица, append-only

**Ни одна операция панели не выполняется без записи сюда.** Запись делается в
той же транзакции, что и сама операция: не записалось — не произошло.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `binary_id` | PK |
| `admin_id` | `binary_id` | FK → `users`, NOT NULL |
| `session_id` | `binary_id` | FK → `admin_sessions`, NOT NULL |
| `action` | `string` (Ecto.Enum) | см. список ниже |
| `subject_type` | `string` (Ecto.Enum) | `user` / `room` / `tournament` / `wallet` |
| `subject_id` | `string(64)` | id объекта действия |
| `amount` | `integer` | NULL — для денежных действий, в минимальных единицах |
| `currency` | `string` (Ecto.Enum) | NULL — `main` / `play_money` |
| `reason` | `string(500)` | NOT NULL для всех мутирующих действий |
| `meta` | `json` | произвольные детали (before/after) |
| `ip` | `string(45)` | NOT NULL |
| `inserted_at` | `utc_datetime_usec` | NOT NULL |

`action`: `login`, `login_failed`, `logout`, `ban_user`, `unban_user`,
`credit`, `debit_to_admin`, `observe_room_open`, `observe_room_close`,
`force_close_room`, `pause_tournament`, `resume_tournament`, `cancel_tournament`.

Индексы: `admin_id`, `subject_type + subject_id`, `inserted_at`.

Записи `admin_audit` **не удаляются и не редактируются** — ни миграцией, ни
чисткой. Таблица без `updated_at` намеренно.

### `wallet_entries` — новый тип

К `@types` добавляются два значения:

* `admin_credit` — начисление игроку решением админа;
* `admin_transfer` — перевод между кошельком игрока и кошельком админа.

Существующий `adjustment` не переиспользуется: он означает техническую
коррекцию (сверка, исправление бага), а действие живого админа должно
отличаться от неё в выборке одним `WHERE`.

## 4. Контекст ядра `BlockPoker.Admin`

Новый контекст в `lib/block_poker/admin/`. Транспорт зовёт **только** его.

```
lib/block_poker/admin/
  admin.ex             # публичный API контекста
  admin_session.ex     # схема сессии
  admin_audit.ex       # схема аудита
  audit.ex             # запись аудита, вызывается изнутри операций
  auth.ex              # логин, проверка роли, выпуск/отзыв токенов
  people.ex            # список пользователей + карточка
  money.ex             # начисление и перевод
  games.ex             # агрегированный список живых игр всех режимов
  observer.ex          # god-mode подписка на стол
```

### Публичный API

```elixir
# Аутентификация
@spec login(email :: String.t(), password :: String.t(), meta :: map()) ::
        {:ok, %{access: String.t(), refresh: String.t(), admin: User.t()}}
        | {:error, ErrorCode.t()}
@spec refresh(refresh_token :: String.t(), meta :: map()) :: {:ok, map()} | {:error, ErrorCode.t()}
@spec logout(session_id :: Ecto.UUID.t()) :: :ok
@spec authorize(token :: String.t()) :: {:ok, %{admin: User.t(), session: AdminSession.t()}} | {:error, ErrorCode.t()}

# Люди
@spec list_users(params :: map()) :: {:ok, %{entries: [map()], cursor: String.t() | nil}}
@spec user_card(user_id :: Ecto.UUID.t()) :: {:ok, map()} | {:error, ErrorCode.t()}
@spec ban(ctx :: t(), user_id :: Ecto.UUID.t(), reason :: String.t()) :: {:ok, User.t()} | {:error, ErrorCode.t()}
@spec unban(ctx :: t(), user_id :: Ecto.UUID.t(), reason :: String.t()) :: {:ok, User.t()} | {:error, ErrorCode.t()}

# Деньги
@spec credit(ctx :: t(), user_id, currency :: :main | :play_money, amount :: pos_integer(), reason :: String.t(), idem :: String.t()) ::
        {:ok, map()} | {:error, ErrorCode.t()}
@spec take_to_admin(ctx :: t(), user_id, currency, amount :: pos_integer(), reason :: String.t(), idem :: String.t()) ::
        {:ok, map()} | {:error, ErrorCode.t()}

# Игры
@spec live_games(kind :: :cash | :mtt | :sit_and_go | :ofc_cash | :all) :: [map()]
@spec game_card(kind :: atom(), id :: String.t()) :: {:ok, map()} | {:error, ErrorCode.t()}

# God-mode
@spec observe(ctx :: t(), room_id :: Ecto.UUID.t()) :: {:ok, map()} | {:error, ErrorCode.t()}
@spec stop_observing(ctx :: t(), room_id :: Ecto.UUID.t()) :: :ok
```

`ctx` — структура `%Admin.Context{admin_id: ..., session_id: ..., ip: ...}`,
собранная транспортом из `conn.assigns`/`socket.assigns` и переданная
единственным аргументом. Она нужна **исключительно** для аудита: транспорт
отвечает на вопрос «кто это», контекст — на вопрос «можно ли ему».

**Правило проверки прав:** `admin?/1` проверяется внутри каждой публичной
функции `Admin`, а не в плаге и не в канале. Плаг проверяет только подпись
токена. Это делает невозможным вызов операции из ядра без проверки роли.

## 5. HTTP: `/admin/*`

Отдельный scope в `Api.Router` со своим пайплайном.

### Аутентификация

| Метод | Путь | Тело / ответ |
|---|---|---|
| `POST` | `/admin/auth/login` | `{email, password}` → `{access, refresh, expires_in, admin: {id, name, email}}` |
| `POST` | `/admin/auth/refresh` | `{refresh}` → новая пара, старый refresh отзывается |
| `POST` | `/admin/auth/logout` | отзыв текущей сессии |
| `GET` | `/admin/auth/me` | текущий админ + сессия |

* `access` — `Phoenix.Token` с солью `"admin access"`, **TTL 15 минут**;
* `refresh` — `32` случайных байта, в БД лежит хэш, **TTL 12 часов**, ротация
  при каждом `refresh` (использованный refresh отзывается немедленно);
* соль admin-токена **отличается** от игровой, поэтому игровой токен физически
  не проходит верификацию в `/admin/*` и наоборот;
* при `role != :admin` ответ — тот же `invalid_credentials`, что и при неверном
  пароле, и та же задержка: панель не должна быть оракулом «этот email —
  админский»;
* неуспешный вход пишется в `admin_audit` как `login_failed`.

### Данные

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/admin/users?cursor=&limit=&q=&status=&role=&sort=` | список пользователей |
| `GET` | `/admin/users/:id` | карточка |
| `GET` | `/admin/users/:id/ledger?cursor=&limit=&currency=` | выписка по кошелькам |
| `POST` | `/admin/users/:id/ban` | `{reason}` |
| `POST` | `/admin/users/:id/unban` | `{reason}` |
| `POST` | `/admin/users/:id/credit` | `{currency, amount, reason, idempotency_key}` |
| `POST` | `/admin/users/:id/take` | `{currency, amount, reason, idempotency_key}` |
| `GET` | `/admin/games?kind=&status=` | живые игры всех режимов |
| `GET` | `/admin/games/:kind/:id` | карточка игры |
| `GET` | `/admin/audit?cursor=&admin_id=&action=&subject_id=` | журнал действий |

Пагинация — **курсорная**, как в `History` (§3 CLAUDE.md): `limit` ≤ 100,
default 50, курсор непрозрачный для клиента.

### Список пользователей

Одна строка ответа:

```json
{
  "id": "uuid",
  "name": "Player",
  "email": "p@example.com",
  "status": "active",
  "role": "default",
  "avatar": "/users/avatars/default.png",
  "wallets": { "main": 1250000, "play_money": 9800 },
  "seated_at": [{"kind": "cash", "room_id": "uuid", "name": "NL2 6-max"}],
  "online": true,
  "registered_at": "2026-08-01T10:00:00.000000Z",
  "last_seen_at": "2026-08-25T09:12:00.000000Z"
}
```

* `wallets` — баланс из `user_wallets` (денормализованный кэш). Отдельный
  фильтр `?verify=true` считает сумму по `wallet_entries` и подсвечивает
  расхождение — это ровно тот инвариант, который §11 CLAUDE.md требует
  проверять; панель делает его видимым.
* `online` — из `Socket.Presence`, но **не** источник истины о посадке (§5
  CLAUDE.md); занятость мест берётся из `Tables.my_seats/1`.
* Сортировка: по `inserted_at`, `name`, балансу `main`. Поиск `q` — по
  подстроке `name` или `email`.
* Все суммы — целые, в минимальных единицах. Никаких float (§5 CLAUDE.md).

### Живые игры

`GET /admin/games` возвращает один список с полем `kind`, а не четыре разных
эндпоинта. Ядро собирает его через `Admin.Games.live_games/1`, который
опрашивает `Tables.Lobby`, `Tables.SitAndGoLobby` и `Tournaments`:

```json
{
  "kind": "cash",
  "id": "uuid",
  "name": "NL2 6-max",
  "game_type": "holdem",
  "currency": "main",
  "status": "running",
  "players": 4,
  "seats": 6,
  "pot": 3400,
  "hand_no": 128,
  "started_at": "...",
  "observable": true,
  "participants": [
    {"user_id": "uuid", "name": "Player", "seat": 2, "stack": 18400, "state": "acting"}
  ]
}
```

Поля, специфичные для режима, лежат в `extra`:

* `cash` — блайнды, анте, рейк-кап, `code` для приватной комнаты;
* `sit_and_go` — множитель, призовая сетка, уровень блайндов;
* `mtt` — номер уровня, до перерыва, стеки/средний стек, число столов, ITM;
* `ofc_cash` — очко, режим фантазии, номер круга.

`extra` собирается в ядре. Транспорт его только сериализует — арифметики над
фишками во view нет (§3 CLAUDE.md).

### Ответы и ошибки

Коды — из `BlockPoker.ErrorCode`, расширенного новыми значениями:
`admin_required`, `admin_session_expired`, `admin_reason_required`,
`admin_amount_invalid`, `admin_insufficient_funds`, `admin_self_target`,
`admin_room_not_found`. Свободного текста в `code` нет (§5 CLAUDE.md).

## 6. Сокет: `/admin/socket`

Отдельный `Socket.AdminSocket` на том же `Endpoint`, но по другому пути.
Подключение — `wss://.../admin/socket/websocket?token=<admin access token>`.
`connect/3` верифицирует токен админской солью, проверяет, что сессия не
отозвана и `role == :admin`, и кладёт в `assigns` только `admin_id`,
`session_id`, `ip`, `vsn`. Игрового состояния в `assigns` нет (§3 CLAUDE.md).

### Топики

| Топик | Назначение |
|---|---|
| `admin:games` | живой список игр всех режимов: открытие/закрытие комнат, число игроков, старт/финиш турниров |
| `admin:room:<room_id>` | god-mode на конкретный стол |
| `admin:tournament:<id>` | ход конкретного турнира: уровни, перерывы, балансировка, вылеты |

### God-mode: `admin:room:<room_id>`

`join` вызывает `Admin.observe(ctx, room_id)`, который:

1. проверяет роль;
2. пишет `observe_room_open` в `admin_audit`;
3. подписывает канал на два PubSub-топика: обычный `"table:<id>"` и
   **отладочный** `"table_debug:<id>"`;
4. возвращает полный несфильтрованный снапшот стола.

`leave` пишет `observe_room_close`.

Сервер → админ:

```
"room_state"    полный снапшот: стеки, поты, борд, ВСЕ карманные карты, остаток колоды
"room_delta"    доменное событие ядра — тот же список events, что уходит игрокам, но без фильтрации
"intent"        входящий запрос игрока: %{at, user_id, seat, topic, event, payload, seq}
"intent_result" результат: %{at, ref, outcome: "ok"|"error", code, latency_us}
"observers"     кто ещё смотрит этот стол
```

**Лента**. `intent` и `intent_result` — это сырой поток транспорта: **все**
входящие сообщения игроков по этому столу, включая отклонённые, с кодом
ошибки и временем обработки. Именно это делает режим отладочным, а не
«красивым реплеем».

Механика без бизнес-логики в транспорте: `TableChannel` после вызова контекста
делает **один** `Telemetry.execute([:block_poker, :table, :intent], ...)`.
Отдельный обработчик `BlockPoker.Admin.Observer` — процесс ядра — слушает эти
события и ретранслирует в `"table_debug:<id>"`. Канал наблюдателя не знает
ничего о правилах и не заглядывает в состояние стола: он подписчик, как
любой другой.

Приватные данные не «дорисовываются» админскому клиенту: ядро отдаёт
**неотфильтрованный** снапшот через отдельную функцию `Admin.Observer` —
`TableView.render/2` не получает никакого флага «я админ». Тест приватности
игрока (§11 CLAUDE.md) продолжает проверять именно `TableView` и остаётся
зелёным без исключений.

**Хранение:** ленты нет в БД. `Observer` держит кольцевой буфер последних
**500** событий на стол, который отдаётся при `join`, чтобы админ, открывший
стол в середине раздачи, увидел её начало. Буфер живёт в памяти и умирает
вместе с процессом.

**Наблюдение только читает.** Канал `admin:room:*` не принимает от клиента
ни одного мутирующего сообщения. Совсем: единственные входящие — `ping` и
`leave`. Управляющие действия (закрыть стол, пауза турнира) идут по HTTP,
где есть `reason` и аудит.

## 7. Деньги

### Начисление — `POST /admin/users/:id/credit`

`Admin.Money.credit/6` внутри одного `Ecto.Multi`:

1. `admin_audit` запись `credit`;
2. `wallet_entries` запись типа `admin_credit`, `+amount`, `ref_id` = id
   записи аудита, `idempotency_key` = присланный клиентом ключ;
3. пересчёт `user_wallets.amount`;
4. broadcast в `wallet:<user_id>`, чтобы игрок увидел баланс без перезахода.

`idempotency_key` **обязателен** и приходит от панели (UUID, сгенерированный
при открытии формы, а не при отправке). Повторная отправка той же формы —
это тот же ключ, и unique-констрейнт БД гасит второе начисление. Это тот же
механизм, что уже работает в `Wallet`, и он тестируется на настоящей MySQL,
а не на моке (§11 CLAUDE.md).

### Списание на админа — `POST /admin/users/:id/take`

Тот же `Ecto.Multi`, но две записи ledger с общим `ref_id` и типом
`admin_transfer`: `−amount` у игрока, `+amount` у админа, в том же кошельке
по типу валюты (`main` → `main`, `play_money` → `play_money`).

Правила:

* сумма фишек в системе не меняется — инвариант «сохранение фишек» цел;
* нельзя увести кошелёк игрока в минус: `check_constraint` уже стоит
  (`user_wallets_amount_non_negative`), плюс явная проверка с понятной ошибкой
  `admin_insufficient_funds`;
* **фишки, которые сейчас на столе, не трогаются.** Списывается только то, что
  лежит в кошельке. Если игрок сидит за столом, панель показывает
  предупреждение и сумму «в игре», но операция всё равно затрагивает только
  кошелёк — иначе пришлось бы вмешиваться в состояние `TableServer` посреди
  раздачи;
* `admin_self_target` — админ не может ни начислить, ни списать сам себе:
  начисление себе делается через `mix`, где это видно в истории команд.

### Обязательный `reason`

Все четыре мутирующих действия (`ban`, `unban`, `credit`, `take`) требуют
непустой `reason` длиной 3..500. Пустой — `admin_reason_required`, операция
не выполняется. Это не UX-украшение: без причины запись аудита бесполезна.

## 8. Безопасность

Раздел не рекомендательный. Панель — самый привилегированный вход в систему,
и god-mode с открытыми картами в реальном времени означает, что компрометация
админского доступа эквивалентна компрометации всех игр разом.

**Доступ**

* Отдельная соль токена, отдельный TTL (15 мин), отдельный refresh (12 ч) с
  ротацией. Игровой токен в `/admin/*` не работает никогда.
* Все `/admin/*` — только по TLS. `Endpoint` в проде отбивает plain HTTP.
* Rate limit на `/admin/auth/login`: 5 попыток в 15 минут на IP **и** на email,
  дальше `429`. Существующий плаг `Api.Plugs.RateLimit` переиспользуется.
* CORS для `/admin/*` — белый список origin'ов из конфига, `*` запрещена.
  Панель — отдельное приложение на другом origin, поэтому CORS настраивается
  явно, а не отключается.
* Отзыв: `DELETE` сессии в БД мгновенно закрывает и HTTP, и сокет — сокет
  проверяет `session.revoked_at` при каждом `join` и раз в минуту по таймеру.

**God-mode ограничений не имеет**

Наблюдение отдаёт всё: карманные карты всех игроков, остаток колоды, сырой
поток запросов — немедленно, без задержки. Роль админа при этом **не мешает
играть**: тот же аккаунт садится за любой стол на любой валюте.

Это осознанный размен, а не упущение. Режим существует до релиза, на
собственных и тестовых столах, и любое ограничение сделало бы его
бесполезным ровно там, где он нужен. Плата за размен — §14: перед публичным
запуском наблюдение вырезается целиком.

**Аудит**

* Аудит пишется в транзакции операции. Не записалось — операция откатилась.
* `admin_audit` только на вставку: ни контекст, ни миграции не содержат
  `update`/`delete` по этой таблице. Проверяется тестом-грепом по `lib/`.
* Открытие god-mode — тоже действие и тоже в аудите. Отчёт «кто какие столы
  смотрел» строится одним запросом.

**Данные**

* Панель не отдаёт `password_hash`, хэши токенов и сырые refresh-токены ни
  в одном ответе. Проверяется тестом на сыром теле ответа.
* Логи `/admin/*` фильтруют `password`, `token`, `refresh`, `idempotency_key`
  и карты (§9 CLAUDE.md). При этом карты в god-mode **не логируются вообще**:
  они идут в сокет, но не в Logger.
* `admin:room:*` не отдаёт seed RNG. Остаток колоды — отдаёт (это отладка),
  seed — нет: по seed воспроизводится будущее, по остатку колоды только
  настоящее.

## 9. Границы слоёв

Правило §3 CLAUDE.md действует без послаблений, и админский неймспейс —
самое вероятное место, где его нарушат.

Разрешено в `lib/api/controllers/admin/*` и `lib/socket/channels/admin/*`:

1. распарсить параметры и проверить их форму (лимит — число, валюта — из
   списка, сумма — положительное целое в границах `int`);
2. собрать `%Admin.Context{}` из `conn.assigns` / `socket.assigns`;
3. вызвать **одну** функцию `BlockPoker.Admin`;
4. отрендерить результат;
5. смапить `{:error, code}` в ответ.

Запрещено, в дополнение к общему списку §3:

* решать, админ ли это (роль проверяет `Admin`, не плаг);
* считать балансы, суммировать `wallet_entries`, сравнивать кэш с ledger;
* собирать список живых игр обходом `Registry` или `Lobby` — это
  `Admin.Games.live_games/1`;
* фильтровать или, наоборот, «раскрывать» карты — снапшот приходит из ядра
  уже в нужном виде;
* ветвиться по `kind` игры (`case kind do :cash -> ... :mtt -> ...`) —
  различия режимов живут в `GameMode` и в `Admin.Games`.

Автотест границ слоёв (§11 CLAUDE.md) расширяется на новые каталоги: в
`lib/api/controllers/admin/**` и `lib/socket/channels/admin/**` нет `Repo`,
`Ecto.Query` и доменных состояний раздачи.

## 10. Клиент (Vue)

Отдельный репозиторий/каталог, не собирается в бэкенд и не раздаётся им.

* Vue 3 + Vite, TypeScript, Pinia, Vue Router, `phoenix` js-клиент для сокета.
* Адрес бэкенда — из `.env` (`VITE_API_URL`), выбирается на сборке: прод или
  тест. Никаких хардкодов и никакого переключателя в UI, чтобы нельзя было
  случайно выполнить операцию не в том окружении. Окружение показывается
  крупной плашкой в шапке: `PROD` красным, `TEST` серым.
* Токены: `access` — только в памяти Pinia; `refresh` — в `sessionStorage`,
  то есть умирает с вкладкой. `localStorage` не используется.
* Автообновление `access` за 60 секунд до истечения; при неудаче — редирект
  на логин с очисткой стора.
* Экраны:
  1. **Логин.**
  2. **Пользователи** — таблица с пагинацией, поиском, сортировкой, балансами
     обеих валют; строка раскрывается в карточку.
  3. **Карточка игрока** — балансы, выписка ledger, текущие посадки, история
     банов, кнопки: бан/разбан, начислить, списать себе. Каждая — модалка с
     обязательным полем причины и подтверждением суммы прописью.
  4. **Игры** — четыре вкладки (Кэш / Турниры / Spin & Go / OFC) поверх одного
     эндпоинта, живое обновление по `admin:games`.
  5. **Стол (god-mode)** — слева визуализация стола со всеми открытыми
     картами, справа лента `intent` / `intent_result` / `room_delta` с
     фильтром по игроку и типу, автоскролл и пауза, экспорт видимого куска
     ленты в JSON.
  6. **Журнал** — `admin_audit` с фильтрами.
* Денежные суммы вводятся и показываются в человеческих единицах, но в API
  уходят целыми минимальными единицами. Конвертация — одно место в клиенте,
  покрытое тестом.

## 11. Тестирование

Уровни — по §11 CLAUDE.md. БД не мокаем.

**Уровень 3 (контексты, Sandbox):**

* логин админа выдаёт токен; логин игрока с `role: :default` по тем же
  правильным паролю и email — `invalid_credentials`, и в `admin_audit` есть
  `login_failed`;
* игровой socket-токен не проходит `Admin.authorize/1`, и наоборот;
* отозванная сессия немедленно перестаёт авторизовывать;
* `credit` с одним и тем же `idempotency_key` дважды создаёт **одну** запись
  ledger — падает именно констрейнт БД;
* `take_to_admin` не меняет сумму фишек в системе: сумма всех `wallet_entries`
  до и после равна (это существующий инвариант-тест, дополненный новым типом);
* попытка списать больше, чем в кошельке, возвращает `admin_insufficient_funds`
  и не оставляет частичных записей после отката `Ecto.Multi`;
* операция без `reason` не выполняется и не пишет ни ledger, ни аудит;
* каждая успешная мутация оставляет ровно одну запись в `admin_audit`;

**Уровень 4 (каналы и HTTP насквозь, `:shared`, `async: false`):**

* `GET /admin/users` без токена → `401`; с игровым токеном → `401`;
  с админским → список с балансами обеих валют;
* курсорная пагинация: два подряд идущих запроса не дублируют и не теряют
  строк при вставке нового пользователя между ними;
* `admin:room:<id>`: два игрока играют раздачу, админ подключается в середине
  и получает в снапшоте **обе** пары карманных карт и буфер предыдущих
  событий; при этом `TableView` каждого игрока по-прежнему не содержит чужих
  карт (существующий тест приватности запускается в том же сценарии);
* отклонённое действие игрока (ход не в свою очередь) появляется в ленте
  админа как `intent_result` с `outcome: "error"` и кодом;
* канал `admin:room:*` игнорирует любое мутирующее сообщение от клиента;
* `admin:games` показывает игры всех четырёх режимов и обновляется при
  открытии новой комнаты.

**Инварианты, добавляемые в постоянный набор:**

* **Ответ панели не содержит секретов.** Проверяется на сыром теле ответа:
  нигде нет `password_hash`, `token_hash`, refresh-токена.
* **Сохранение фишек с админскими операциями.** Существующий тест расширяется:
  `admin_transfer` не меняет сумму, `admin_credit` меняет её ровно на
  указанную величину и только с записью в аудите.
* **Границы слоёв в `admin/*`.** Как в §9.
* **Аудит неудаляем.** Грепом по `lib/` нет `Repo.delete`/`Repo.update` по
  `AdminAudit`.

## 12. Порядок реализации

1. Миграции: `admin_sessions`, `admin_audit`, новые типы `wallet_entries`.
2. Контекст `BlockPoker.Admin`: `auth` + `audit` + тесты уровня 3.

8. `AdminSocket` и канал `admin:room:*` + тесты god-mode.
9. `GET /admin/audit`.
10. Vue-приложение по экранам из §10.

Пункты 1–5 самодостаточны: после них панель уже полезна, и её можно катить
до того, как готов god-mode.

## 13. Снятие god-mode перед релизом

Наблюдение — временный отладочный инструмент. Чтобы его удаление было
операцией на один коммит, а не археологией, оно изолируется с самого начала:

* весь код наблюдения живёт в трёх файлах и нигде больше:
  `lib/block_poker/admin/observer.ex`, `lib/socket/channels/admin/room_channel.ex`,
  `lib/socket/views/admin/room_view.ex`;
* `Admin.Observer` — единственный потребитель telemetry-события
  `[:block_poker, :table, :intent]`. Само событие остаётся: оно полезно для
  метрик и не раскрывает карт;
* ядро **не получает** ни одной функции вида «отдай состояние без фильтрации»
  за пределами `Admin.Observer`. `TableView` и `RoomState` не меняются;
* режим включается флагом конфига `config :block_poker, :admin_observer, enabled: false`,
  по умолчанию **выключенным**. В проде он не включён ни разу до тех пор, пока
  это сознательно не сделано;
* при `enabled: false` канал `admin:room:*` отвечает на `join` кодом
  `admin_observer_disabled`, а вкладка «Стол» в панели не отображается;
* удаление после релиза — снос трёх файлов, топика `admin:room:*`, флага
  конфига и соответствующих тестов. Ни списки, ни деньги, ни аудит от этого
  не страдают: пункты 1–6 из §12 самодостаточны.

Записи `observe_room_open` / `observe_room_close` в `admin_audit` остаются
после удаления функционала — история того, кто и когда смотрел столы, живёт
дольше самого режима.
