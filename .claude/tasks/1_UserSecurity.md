# Задача 1. Пользователь и кошельки (User & Security)

Первый вертикальный срез: регистрация, вход, обновление токена и кошельки игрока.
Игровой логики здесь нет — только контексты `accounts` и `wallet` плюс тонкий HTTP
слой аутентификации из §3 CLAUDE.md.

---

## 1. Цель

По завершении задачи:

* пользователь может зарегистрироваться, войти и получить socket-токен;
* при регистрации ему атомарно создаются два кошелька (`main` = 0,
  `play_money` = 10 000) с записью в истории транзакций;
* `UserSocket.connect/3` пускает соединение только по валидному токену;
* всё покрыто тестами уровней 3 и 4 (§11 CLAUDE.md).

Вне объёма: столы, лобби, операции buy-in / cash-out, восстановление пароля,
верификация email, 2FA, загрузка аватаров.

---

## 2. Модель данных

### `users`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `binary_id` (UUID v4) | PK |
| `name` | `string(25)` | NOT NULL, UNIQUE (с учётом регистра) |
| `email` | `string(160)` | NOT NULL, UNIQUE (хранится в нижнем регистре) |
| `avatar` | `string(255)` | NOT NULL, default `/users/avatars/default.png` |
| `password_hash` | `string(255)` | NOT NULL |
| `status` | `string` (Ecto.Enum) | `active` / `blocked`, default `active` |
| `inserted_at` / `updated_at` | `utc_datetime_usec` | NOT NULL |

**Валидация `name`**

* длина 3..25 символов;
* регулярка `~r/\A[A-Za-z0-9_-]+\z/` — латиница, цифры, `_`, `-`, ничего больше;
* уникальность **с учётом регистра**: `Player` и `player` — разные ники.
  MySQL по умолчанию сравнивает строки регистронезависимо, поэтому колонке
  явно задаётся бинарная/чувствительная к регистру collation
  (`utf8mb4_0900_as_cs`, при недоступности — `utf8mb4_bin`), иначе UNIQUE-индекс
  молча схлопнет два разных ника в один. Плюс `unique_constraint(:name)`;
* `unsafe_validate_unique/3` — чтобы отдать понятную ошибку до попытки вставки.

**Валидация `email`**

* нормализуется в нижний регистр перед вставкой;
* базовая проверка формата (`~r/\A[^\s@]+@[^\s@,]+\.[^\s@,]+\z/`), длина ≤ 160;
* UNIQUE-индекс + `unique_constraint(:email)`.

**Валидация `password`**

* виртуальное поле `password`, в БД только `password_hash`;
* длина 8..72 (72 — предел входной строки для Argon2/bcrypt);
* хэш — Argon2 (§9 CLAUDE.md). Ограничение окружения: `argon2_elixir` — C-NIF,
  и на Windows `elixir_make` требует `nmake` из Visual C++ Build Tools (§13).
  Перед началом работы нужно либо поставить Build Tools, либо принять решение
  об альтернативе без NIF (`pbkdf2_elixir`) — см. вопрос 2 в §7;
* `password` и `password_hash` помечены `redact: true`, чтобы не утекали
  в логи и `inspect`.

### `user_wallets`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `binary_id` | PK |
| `user_id` | `binary_id` | FK → `users.id`, `on_delete: :delete_all`, NOT NULL |
| `type` | `string` (Ecto.Enum) | `main` / `play_money`, NOT NULL |
| `amount` | `bigint` | NOT NULL, default 0, CHECK `amount >= 0` |
| timestamps | `utc_datetime_usec` | NOT NULL |

* UNIQUE-индекс `(user_id, type)` — один кошелёк каждого типа на игрока.
* `amount` — **целое в минимальных единицах** (центы/фишки), никаких float (§5).
  Для `play_money` минимальная единица — сама фишка, дробной части нет.
* Дефолты при регистрации: `main` = `0`, `play_money` = `10_000`.

Отношение к §6 CLAUDE.md: `user_wallets` занимает место таблицы `wallets` —
это **денормализованный кэш** текущего баланса, источник истины — `wallet_entries`
(ниже). Фиксируем инвариант: `amount` меняется
**только** через контекст `BlockPoker.Wallet`, никогда напрямую из транспорта.

### `wallet_entries` — история транзакций (append-only)

Источник истины по деньгам. Разрешён только `INSERT`; `UPDATE` и `DELETE`
не делает никто и никогда — ошибки компенсируются обратной записью `adjustment`.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `binary_id` | PK |
| `wallet_id` | `binary_id` | FK → `user_wallets.id`, NOT NULL |
| `amount` | `bigint` | NOT NULL, знаковое: `+` пополнение, `−` списание, `0` запрещён |
| `type` | `string` (Ecto.Enum) | `deposit` / `buy_in` / `cash_out` / `rake` / `adjustment` |
| `balance_after` | `bigint` | NOT NULL — баланс кошелька после операции |
| `ref_id` | `string(64)` | NULL — на что ссылается операция (стол, раздача, платёж) |
| `idempotency_key` | `string(120)` | NOT NULL, **UNIQUE** |
| `meta` | `json` | NULL — произвольный контекст для разбора |
| `inserted_at` | `utc_datetime_usec` | NOT NULL (без `updated_at` — строка неизменяема) |

* Ledger ведётся **по кошельку**, а не по пользователю: у `main` и `play_money`
  независимые истории, и вопрос «сколько у него игровых фишек» не требует
  фильтрации по типу.
* `idempotency_key` — единственная защита от двойного списания. Формат —
  `"<операция>:<стабильный id>"`, например `"signup:<user_id>"`,
  `"buyin:<seat_session_uuid>"`. Ключ должен выводиться из самой операции,
  а не генерироваться заново при ретрае.
* `balance_after` — денормализация ради читаемости выписки и быстрой сверки:
  позволяет найти точку расхождения, не суммируя весь журнал.
* Индексы: UNIQUE `(idempotency_key)`, `(wallet_id, inserted_at)` — для выписки.

**Инвариант, действующий с первого дня:**
`user_wallets.amount == SUM(wallet_entries.amount) WHERE wallet_id = ...`

Регистрация записывает стартовые фишки как обычную операцию:
`amount: +10_000, type: :deposit, idempotency_key: "signup:<user_id>"`.
Кошелёк `main` создаётся с `amount: 0` и **без** записей — пустой журнал даёт
нулевую сумму, инвариант выполняется.

## 3. Контексты

### `BlockPoker.Accounts`

```elixir
@spec register(map()) :: {:ok, User.t()} | {:error, Ecto.Changeset.t()}
@spec authenticate(email :: String.t(), password :: String.t()) ::
        {:ok, User.t()} | {:error, :invalid_credentials | :user_blocked}
@spec get_user(id :: Ecto.UUID.t()) :: {:ok, User.t()} | {:error, :not_found}
```

* `register/1` — `Ecto.Multi`: вставка `users` + вставка обоих кошельков.
  Либо всё, либо ничего. Кошельки добавляет `Wallet.create_default_wallets/2`
  (принимает и возвращает `Multi`), чтобы дефолтные суммы жили в кошельковом
  контексте, а не в `Accounts`.
* `authenticate/2` при отсутствии пользователя всё равно выполняет
  `Argon2.no_user_verify/0` — защита от timing-перебора email.
* Наружу — коды из `BlockPoker.ErrorCode`, не свободный текст.

### `BlockPoker.Accounts.Tokens`

* **Socket-токен**: `Phoenix.Token.sign(Socket.Endpoint, "user socket", user_id)`,
  TTL 1 час, stateless, в БД не хранится.
* **Refresh-токен**: 32 байта из `:crypto.strong_rand_bytes/1`, клиенту —
  Base64URL, в `refresh_tokens` хранится **SHA-256 хэш**.
  Поля: `user_id`, `token_hash` (UNIQUE), `expires_at` (30 дней), `revoked_at`.
* `refresh/1` — ротация в одной транзакции: старый токен отзывается, выдаётся
  новый. Повторное предъявление отозванного токена → отзыв всей цепочки токенов
  пользователя + `{:error, :token_reused}`.
* Чистка просроченных токенов — задача Oban (§2), периодическая.

### `BlockPoker.Wallet`

```elixir
@spec create_default_wallets(Ecto.Multi.t(), user_key :: atom()) :: Ecto.Multi.t()
@spec list_wallets(user_id) :: [UserWallet.t()]
@spec get_wallet(user_id, type :: :main | :play_money) ::
        {:ok, UserWallet.t()} | {:error, :not_found}
@spec list_entries(wallet_id, opts :: keyword()) :: [WalletEntry.t()]
```

Дефолты (`@main_default`, `@play_money_default`) — константы модуля контекста
и **нигде не дублируются** в транспорте (§3).

Внутренняя функция записи операции (private, наружу пока не нужна, но это
единственный путь изменения денег — публичные `buy_in` / `cash_out` появятся
в следующей задаче поверх неё):

```elixir
# внутри одной транзакции:
#   1. блокировка строки кошелька (SELECT ... FOR UPDATE)
#   2. проверка, что итоговый баланс >= 0
#   3. INSERT в wallet_entries (UNIQUE на idempotency_key)
#   4. UPDATE user_wallets.amount
@spec record_entry(Ecto.Multi.t(), name :: atom(), attrs :: map()) :: Ecto.Multi.t()
```

Нарушение UNIQUE по `idempotency_key` — **не ошибка**, а сигнал «операция уже
выполнена»: возвращается существующая запись, `{:ok, entry}`. Иначе ретрай
клиента превратится в видимую ошибку при фактически успешной операции.

`FOR UPDATE` нужен потому, что «прочитать баланс → проверить → записать» без
блокировки строки допускает гонку двух параллельных списаний, каждое из которых
по отдельности проходит проверку. CHECK `amount >= 0` на `user_wallets` — второй
рубеж на случай, если блокировку где-то забудут.

## 4. Транспорт

### HTTP (`lib/api`) — только то, что нельзя по сокету

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| `POST` | `/api/auth/register` | `name`, `email`, `password` | `201` + токены + профиль |
| `POST` | `/api/auth/login` | `email`, `password` | `200` + токены + профиль |
| `POST` | `/api/auth/refresh` | `refresh_token` | `200` + новая пара токенов |

Формат успешного ответа:

```json
{
  "token": "<socket token>",
  "refresh_token": "<opaque>",
  "expires_in": 3600,
  "user": {
    "id": "…", "name": "…", "email": "…",
    "avatar": "/users/avatars/default.png"
  }
}
```

Ошибка: `{"code": "...", "message": "..."}`, коды пополняют `BlockPoker.ErrorCode`:
`invalid_credentials`, `validation_failed` (+ `errors` по полям), `token_expired`,
`token_reused`, `rate_limited`, `user_blocked`.

`AuthController` не знает про Argon2, `Repo` и правила валидации: парсит payload,
вызывает **одну** функцию контекста, рендерит результат (§3). Каждый экшен — до ~15 строк.

**Rate limiting** (`Api.Plugs.RateLimit`): `login` и `register` — 10 попыток
за 5 минут на IP, `refresh` — 30 за 5 минут. Хранилище — ETS со скользящим
окном, отдельного сервиса не заводим.

### Сокет

`UserSocket.connect/3` верифицирует `token` (TTL 1 час), кладёт `user_id`
в `assigns` и проверяет `vsn` протокола. Невалидный/просроченный токен или
несовместимая версия → `:error` в handshake с понятным кодом. В `assigns` —
только `user_id`, подписки и версия протокола, ничего больше (§3).

## 5. Миграции

1. `create_users` — таблица + UNIQUE-индексы на `name` и `email`.
2. `create_refresh_tokens` — UNIQUE на `token_hash`, индексы на `user_id` и `expires_at`.
3. `create_user_wallets` — FK, композитный UNIQUE `(user_id, type)`, CHECK на `amount`.
4. `create_wallet_entries` — FK на `user_wallets`, UNIQUE на `idempotency_key`,
   индекс `(wallet_id, inserted_at)`, только `inserted_at`.

Все таблицы — InnoDB, `utf8mb4`, timestamps `utc_datetime_usec` (§6, §11).

## 6. Тесты

**Уровень 3 — контексты (Sandbox, реальная MySQL):**

* регистрация создаёт ровно два кошелька с правильными типами и суммами;
* падение любого шага `Multi` не оставляет ни пользователя, ни кошельков;
* `Player` и `player` — два разных пользователя, оба создаются успешно
  (тест на то, что collation колонки действительно чувствительна к регистру);
* точный дубликат `name` отвергается **базой**, а не только changeset'ом;
* дубликат `email` в другом регистре (`A@x.io` / `a@x.io`) отвергается базой —
  email нормализуется в нижний регистр;
* попытка создать второй кошелёк того же типа ловится UNIQUE-констрейнтом;
* после регистрации `play_money` имеет ровно одну запись `deposit` на `+10_000`,
  а `main` — пустой журнал и баланс 0;
* **инвариант баланса**: для каждого кошелька `amount == SUM(entries.amount)`;
* **идемпотентность**: повторная запись операции с тем же `idempotency_key`
  не создаёт вторую строку и не меняет баланс — проверяется, что срабатывает
  именно constraint БД (§11 CLAUDE.md), а не предварительный `SELECT`;
* **конкурентность**: два параллельных списания с одного кошелька не уводят
  баланс в минус (два процесса, `Sandbox` в режиме `:shared`);
* попытка `UPDATE`/`DELETE` записи журнала в коде отсутствует — проверяется
  архитектурным тестом (грепом по `wallet_entries` вне `Wallet`);
* `authenticate/2`: верный пароль, неверный пароль, несуществующий email,
  заблокированный пользователь;
* ротация refresh-токена: старый перестаёт работать, повтор → `:token_reused`
  и отзыв цепочки; просроченный токен не проходит.

**Уровень 4 — функциональные:**

* `POST /register` → полученным `token` успешно открывается сокет;
* подделанный/просроченный токен → отказ в handshake;
* rate limit на `login` срабатывает после N попыток;
* тело ответа `/register` и `/login` **не содержит** `password_hash` —
  проверяется на сыром JSON, а не на структуре (по аналогии с privacy-тестом §11).

**Property (`StreamData`), без БД:** генераторы валидных и невалидных ников —
changeset принимает ровно то, что описано регуляркой и границами длины.

**Границы слоёв:** архитектурный тест — в `lib/api/**` и `lib/socket/**` нет
`Repo`, `Ecto.Query` и `Argon2`.

## 7. Решённое и открытые вопросы

**Зафиксировано:**

* минимальная длина ника — 3, максимум — 25;
* ники **регистрозависимы**: `Player` и `player` — разные пользователи;
* стартовый `play_money` — ровно `10_000` (это уже минимальные единицы);
* вход — **только по email + password**, ник для логина не используется;
* **история транзакций ведётся с первого дня**: `wallet_entries` (append-only),
  `user_wallets.amount` — кэш поверх неё, стартовые 10 000 записываются
  операцией `deposit`. Обоснование — §8.

**Открытые вопросы:**

1. **Аватар.** Только строка-путь, загрузки файлов не делаем — верно? Если
   загрузка планируется, это отдельная задача (хранилище, лимиты, ресайз).
2. **Чем хэшируем пароли.** По §9 CLAUDE.md — Argon2, но на этой машине он
   не собирается без Visual C++ Build Tools (§13). Ставим Build Tools
   (правильно, но требует установки ~2 ГБ) или берём `pbkdf2_elixir` —
   чистый Elixir, без NIF, слабее Argon2 против GPU-перебора, но приемлемо?
   Предлагаю поставить Build Tools и остаться на Argon2.
3. **Канал `wallet:<user_id>`.** Поднимать сейчас или отложить до buy-in?
   Предлагаю **отложить** — пушить пока нечего, балансы приезжают в ответе логина.
4. **Верификация email и восстановление пароля** — подтверждаю, что вне объёма
   первой задачи?

## 8. Приложение: почему история транзакций, а не одно число

**Проблема.** Если баланс хранится одним числом (`user_wallets.amount`), то любая
операция — это `UPDATE ... SET amount = amount - 500`. После такого `UPDATE`
прошлое значение утеряно безвозвратно. Когда игрок пишет «у меня пропало 3000»,
ответить нечего: в базе лежит только текущее число и ноль информации о том,
как оно таким стало. Баг в коде списания, двойное нажатие кнопки, гонка двух
запросов — всё это молча искажает единственное число, и заметить это можно
только по жалобе.

**Ledger (журнал операций)** — это подход из бухгалтерии: балансы не изменяют,
а только **дописывают операции**. Таблица `wallet_entries` — append-only:
в неё разрешён `INSERT`, но не `UPDATE` и не `DELETE`.

| wallet_id | amount | type | ref_id | idempotency_key |
|---|---|---|---|---|
| W1 | +10000 | `deposit` | — | `signup:<user_id>` |
| W1 | −2000 | `buy_in` | table 7 | `buyin:<uuid>` |
| W1 | +3500 | `cash_out` | table 7 | `cashout:<uuid>` |

Баланс = `SELECT SUM(amount)`. Каждая строка отвечает на вопросы «сколько,
почему, когда и в связи с чем». История операций для игрока и разбор жалобы —
это просто выборка из этой таблицы, а не восстановление по логам.

**Что это даёт помимо истории:**

* **Идемпотентность.** `idempotency_key` с UNIQUE-индексом: повторный запрос
  (клиент нажал дважды, сеть ретраила) вставит строку-дубль → база отклонит →
  деньги списались один раз. С одним числом `amount` такой защиты нет в принципе:
  два `UPDATE` просто спишут дважды.
* **Сверка.** Денормализованный `amount` — это кэш ради скорости. Фоновая
  задача сравнивает его с `SUM(wallet_entries.amount)`; расхождение = сигнал
  о баге, который иначе никто бы не заметил.
* **Неудаляемость.** Ошибку не «затирают» — её компенсируют обратной записью
  `adjustment`. След остаётся.

Именно это описано в §6 CLAUDE.md: `wallets` — денормализованный текущий баланс,
**кэш поверх ledger**, а `wallet_entries` — источник истины.

**Почему я предлагаю вводить его сразу.** Инвариант «баланс = сумма записей»
можно объявить только с того момента, когда журнал ведётся. Если запустить
кошельки без него, то у ранних пользователей баланс будет уже накопленным,
а записей под ним не будет — и при подключении ledger придётся выдумывать
синтетическую строку «начальный остаток», которая ничего не объясняет.
Ввести журнал сейчас — это одна дополнительная таблица и одна запись `deposit`
при регистрации, потому что кроме стартовых 10 000 пока никаких операций нет.

**Цена решения:** +1 миграция, +1 схема, регистрация оборачивается в транзакцию
(она и так `Ecto.Multi`), тесты на идемпотентность и сходимость баланса.
Если выбираем вариант А — ничего страшного, но переезд позже обойдётся дороже
именно из-за исторических данных.
