# Клиент. Задача 33. История раздач и статистика

Документ для разработчика Electron-клиента. Серверная часть — задача 6
бэкенда.

Новый раздел приложения: кнопка **«История»** в лобби, под профилем
пользователя рядом с «Настройками». Внутри — четыре вкладки по режимам,
таблица раздач с сортировками и выделением, графики и сводка показателей.
Ориентир по составу и духу — PokerCraft.

---

## 1. Главное отличие от всего, что было раньше

**Это единственный экран, который ходит по HTTP, а не по WebSocket.**

Всё остальное в приложении — сокет: стол, лобби, кошелёк, турниры. История
работает иначе, и это не оплошность архитектуры, а решение. У неё нет ни
одного свойства, ради которых существует канал: сервер ничего не пушит,
данные не меняются под игроком, задержка в сотню миллисекунд ничего не
ломает. Зато есть свойства, которых у канала нет: постраничное чтение с
фильтрами, кэшируемый ответ и объём выдачи, который не должен делить
пропускную способность с игровым сокетом — тяжёлый ответ по каналу это
лишние миллисекунды у чужого таймера хода за столом.

Практические следствия:

* запросы — обычный `fetch`, с заголовком `Authorization: Bearer <token>`;
* токен — **тот же самый**, которым авторизуется сокет (`/api/auth/login`).
  Второго механизма нет. Протух — обнови через `/api/auth/refresh`, как
  делаешь для сокета, и повтори запрос;
* `401` означает ровно «токен не годится», а не «нет доступа к истории»;
* открытая история не мешает игре за столом и не требует выхода из неё.

## 2. Где живёт в интерфейсе

```
Лобби
 └─ профиль пользователя
     ├─ [Настройки]
     └─ [История]      ← новый экран
         ├─ Cash Games
         ├─ Spin & Go
         ├─ Tournament
         └─ OFC
```

Вкладка = режим игры, и это соответствие однозначное:

| Вкладка | `game_mode` в ответах |
|---|---|
| Cash Games | `cash` |
| Spin & Go | `sit_and_go` |
| Tournament | `mtt` |
| OFC | `ofc_cash` |

**Вкладки не взаимозаменяемы, и смешивать их нельзя** — не из-за вёрстки,
а потому что величины в них измеряются в разном. В кэше и OFC результат
считается в деньгах; в турнирах за столом играют **турнирными фишками**,
которые деньгами не являются: разные турниры имеют разный номинал
стартового стека, и складывать их бессмысленно. Поэтому в турнирных
вкладках сервер денежный результат раздач наружу вообще не отдаёт, а
деньги приходят отдельно — призами за турниры. Не пытайся собрать «общий
банкролл по всем режимам»: сервер такого числа не отдаёт, и получить его
сложением нельзя.

## 3. Эндпоинты

Все — `GET`, все требуют заголовок авторизации.

| Путь | Что отдаёт |
|---|---|
| `/api/history/hands` | страница списка раздач |
| `/api/history/hands/:id` | одна раздача целиком — реплей |
| `/api/history/stats` | сводка показателей за период |
| `/api/history/graph` | точки графиков по дням |
| `/api/history/tournaments` | страница списка сыгранных турниров |
| `/api/history/tournaments/:id` | один турнир: входы и его раздачи |

Общие параметры фильтра, которые понимают все ручки:

| Параметр | Формат | Смысл |
|---|---|---|
| `from`, `to` | ISO 8601 (`2026-08-01T00:00:00Z`) | период |
| `game_mode` | `cash`, `sit_and_go`, `mtt`, `ofc_cash`; можно списком через запятую | вкладка |
| `setting_id` | UUID лимита, либо `none` | разрез по лимиту |

Дополнительно у списков: `limit` (по умолчанию 25, максимум 100), `cursor`
(см. §4), `only_won=true` (только выигранные раздачи). У списка турниров —
`format=sit_and_go,mtt` вместо `game_mode`.

Неверный параметр — `422` с кодом `validation_failed`. Не гадай, что
именно не понравилось: собирай запрос из значений, которые сам же получил
от сервера.

## 4. Пагинация: курсор, а не номер страницы

```
GET /api/history/hands?limit=50
→ { "items": [...50 штук...], "cursor": "MjAyNi0wOC0yNFQx..." }

GET /api/history/hands?limit=50&cursor=MjAyNi0wOC0yNFQx...
→ { "items": [...], "cursor": null }
```

`cursor: null` — страниц больше нет.

**Курсор непрозрачен.** Это строка, которую сервер выдал; её нельзя
разбирать, собирать самому или сохранять между сессиями как «позицию».
Единственное правильное обращение с ней — вернуть как есть.

Почему не «страница 3»: пока игрок листает, сверху появляются новые
раздачи и сдвигают нумерацию — часть раздач он увидел бы дважды, а часть
не увидел бы вовсе. Курсор от этого защищён по построению: он привязан к
конкретной раздаче, а не к смещению.

Отсюда правило для UI: **бесконечная лента с догрузкой, а не нумерованные
страницы.** Нумерации сервер не поддерживает и поддерживать не будет.

## 5. Список раздач

Один и тот же эндпоинт отдаёт раздачи всех режимов, а форма элемента
различается — её объявляет поле `kind`. Ветвись по нему, а не по вкладке:
это позволит потом показать общую ленту без фильтра.

### `kind: "holdem"` — кэш, Spin & Go, турниры

```json
{
  "kind": "holdem",
  "id": "8f2c...",
  "ended_at": "2026-08-24T11:09:30.898000Z",
  "game_mode": "cash",
  "setting_id": "1a2b...",
  "tournament_id": null,
  "level_number": null,
  "hand_number": 143,
  "variant": "texas_holdem",
  "small_blind": 50, "big_blind": 100, "ante": 0,
  "board": [{"rank": 12, "suit": "s"}, ...],
  "board_2": null,
  "pot": 3400,
  "seat": 3,
  "position": "co",
  "hole_cards": [{"rank": 14, "suit": "s"}, {"rank": 14, "suit": "h"}],
  "starting_stack": 10000,
  "invested": 1700, "won": 3400, "net": 1700,
  "ev_amount": 1520,
  "status": "showdown",
  "showdown": true
}
```

* `hole_cards` — **только свои**. Чужих карт в списке нет ни у кого и
  никогда, даже показанных: список короткий, и они там не нужны. Хочешь
  показать вскрытие — открывай реплей.
* `board_2` — второй прогон run it twice, либо `null`. Есть только в кэше.
* `position` — `btn`, `sb`, `bb`, `utg`, `utg1`, `utg2`, `mp`, `lj`, `hj`,
  `co`. Считается по фактическому составу раздачи: впятером за
  девятимаксным столом позиции пятимаксные. В хедз-апе позиций всего две —
  `btn` и `bb`, малого блайнда как позиции там не существует.
* `ev_amount` — сколько игрок «должен был» получить из банка по эквити на
  момент олл-ина. `null` означает, что олл-ина в раздаче не было и EV для
  неё не определён. **«Удачу» считай сам**: `net − (ev_amount − invested)`;
  сервер её не хранит.
* `level_number` и `tournament_id` заполнены только у турнирных раздач.

### `kind: "ofc"` — китайский покер

```json
{
  "kind": "ofc",
  "id": "3d4e...",
  "ended_at": "...",
  "game_mode": "ofc_cash",
  "hand_number": 12,
  "point_value": 100,
  "seat": 2,
  "box": { "top": [...], "middle": [...], "bottom": [...] },
  "discards": [{"rank": 3, "suit": "c"}, ...],
  "foul": false,
  "royalties": { "top": 0, "middle": 4, "bottom": 2 },
  "royalty_total": 6,
  "fantasy": false,
  "fantasy_next": true,
  "points": 6,
  "net": 600,
  "scoop_count": 1
}
```

* `points` — очки, `net` — они же в фишках (`points * point_value`).
  Показывай оба: игрок сравнивает результаты между лимитами в очках, а
  банкролл считает в деньгах.
* `fantasy` — входил ли игрок в **эту** раздачу в фантазии;
  `fantasy_next` — заработал или удержал её по итогам. Пара флагов, а не
  одна сущность: фантазия не длится дольше раздачи, каждая решает её
  судьбу заново.
* `discards` — свои. Чужие сбросы не приходят никогда и нигде: за столом
  их не видит никто, и история не показывает больше, чем показал стол.

## 6. Реплей одной раздачи

`GET /api/history/hands/:id`. Форма ответа снова зависит от `kind`.

### Холдем

```json
{
  "kind": "holdem",
  "hand": { "id": "...", "button_seat": 1, "board": [...], "pot": 3400,
            "rake": 60, "pots": [...], "small_blind": 50, ... },
  "players": [
    { "seat": 1, "user_id": "...", "position": "btn",
      "starting_stack": 10000, "hole_cards": [...],
      "card_visibility": "showdown",
      "invested": 1700, "won": 0, "net": -1700,
      "ev_amount": 1880, "status": "showdown",
      "rank": { "category": "flush", "cards": [...] } },
    ...
  ],
  "actions": [
    { "seq": 1, "street": "preflop", "seat": 2, "action": "post_blind",
      "amount": 50, "to_amount": 50, "pot_before": 0,
      "stack_after": 9950, "elapsed_ms": 0, "auto": false },
    ...
  ]
}
```

**Про карты.** `card_visibility` принимает три значения:

| Значение | Что было |
|---|---|
| `showdown` | открыл по правилам вскрытия |
| `voluntary` | показал сам — мукнув или выиграв без вскрытия |
| `hidden` | не показывал никогда |

Карты игрока со значением `hidden` **не приходят вовсе** — `hole_cards`
будет пустым списком, `rank` будет `null`. Это не ошибка загрузки и не
повод показывать «рубашки со знаком вопроса на месте карт»: рисуй так же,
как за столом рисуется мукнувший. Единственное исключение — свои карты:
их игрок видит всегда, при любой видимости.

Не пытайся вывести видимость из `status`: «дошёл до вскрытия» и «показал
карты» — разные вещи, и решает первое не оно.

**Про действия.** Вынужденные ставки (`post_blind`, `post_ante`,
`straddle`, `post`, `dead_post`) идут такими же строками, как решения
игроков, — с них лог и начинается. Не пропускай их: без них банк в реплее
появляется из ниоткуда.

* `amount` — вложено этим действием; `to_amount` — до скольки поднялась
  ставка улицы. Оба уже посчитаны, вычитать ничего не надо.
* `pot_before` — банк **до** действия. Шансы банка бери отсюда, а не
  пересчитывай.
* `elapsed_ms` — сколько игрок думал. Материал для «тайминга»; ноль у
  вынужденных ставок нормален.
* `auto: true` — сработал преселект или таймаут, живого решения не было.
  Полезно отметить в реплее: это не то же самое, что осознанный чек.

Ответ неизменяем и отдаётся с `ETag` и `Cache-Control: private, immutable`
— кэшируй смело, повторно не запрашивай.

### OFC

```json
{
  "kind": "ofc",
  "hand": { "id": "...", "button_seat": 1, "point_value": 100, ... },
  "players": [
    { "seat": 1, "user_id": "...", "box": {...}, "discards": [],
      "foul": false, "royalties": {...}, "royalty_total": 6,
      "fantasy": false, "fantasy_next": true,
      "points": 6, "net": 600, "scoop_count": 1,
      "line_results": [ { "opponent": 2, "points": 6 } ] }
  ]
}
```

Сетки (`box`) приходят у **всех** — они были открыты за столом целиком, и
это основное содержимое OFC-реплея. Сбросы (`discards`) приходят только
свои; у остальных список пуст.

`line_results` — попарный счёт против каждого соперника: из него рисуется
таблица «кто кому сколько». Сумма очков всех участников раздачи всегда
равна нулю — это можно использовать как проверку своей отрисовки.

## 7. Сводка показателей

`GET /api/history/stats` с фильтром периода. Ответ:

```json
{
  "modes": {
    "cash": { "hands": 12043, "vpip": 26, "pfr": 19, "three_bet": 7,
              "wtsd": 31, "af": 2.3, "aggressive_actions": 2310, "calls": 1004,
              "net": 184000, "ev_net": 151000, "rake_paid": 9800,
              "winrate_ppm": 1520000, "ev_winrate_ppm": 1240000 },
    "mtt":  { "hands": 3400, "vpip": 22, "pfr": 18, ... },
    "ofc_cash": { "hands": 800, "net": 42000, "points": 420, ... }
  },
  "tournaments": {
    "tournaments": 84, "entries": 111,
    "cost": 122100, "income": 168000, "profit": 45900,
    "roi_ppm": 375921,
    "itm": 23, "wins": 4,
    "prize": 160000, "bounty_paid": 8000,
    "average_place_ppm": 244000
  }
}
```

### Дроби приходят в промилле-миллионных

`winrate_ppm`, `roi_ppm`, `average_place_ppm`, `*_per_hand_ppm` — целые
числа, домноженные на 1 000 000. Делить на миллион и форматировать —
работа клиента:

* `winrate_ppm: 1520000` → **1.52 bb/100**;
* `roi_ppm: 375921` → **+37.6% ROI**;
* `average_place_ppm: 244000` → игрок в среднем финиширует в **верхних
  24.4%** поля.

Сервер отдаёт целые не из вредности: деньги в проекте — целые числа в
минимальных единицах, и float в них запрещён на всех уровнях.

### Набор полей зависит от режима, и это важно

**Показатель, которого в режиме не существует, не приходит вовсе.** Не
подставляй вместо отсутствующего ключа ноль — это разные утверждения:
`0` означает «показатель посчитан и равен нулю», отсутствие ключа —
«показатель к этому режиму неприменим».

| Режим | Чего нет и почему |
|---|---|
| `mtt`, `sit_and_go` | нет `winrate_ppm` — величина большого блайнда меняется по уровням, среднее было бы ложью. Нет `net` — он в турнирных фишках, служебный. Деньги смотри в блоке `tournaments` |
| `ofc_cash` | нет `vpip`, `pfr`, `three_bet`, `wtsd`, `af` — торговли в этой игре нет, и нули означали бы «пассивный игрок», а не «неприменимо» |

Также `null` в любом показателе означает «нет знаменателя» — например,
`af: null`, когда коллов не было вовсе. Рисуй прочерк, а не «0.0».

### OFC-разрез

```json
"ofc_cash": {
  "hands": 800, "net": 42000, "points": 420,
  "points_per_hand_ppm": 525000, "net_per_hand_ppm": 52500,
  "fantasy_rate": 12, "fantasy_entry_rate": 9, "fantasy_hold_rate": 34,
  "foul_rate": 4, "scoops": 96,
  "royalty_top_ppm": 1200000, "royalty_middle_ppm": 2400000,
  "royalty_bottom_ppm": 3100000
}
```

`fantasy_entry_rate` — доля заходов среди раздач **без** фантазии,
`fantasy_hold_rate` — доля удержаний среди раздач **в** фантазии. Разные
знаменатели, и это осознанно: заходить и удерживаться — разные умения.

## 8. Графики

`GET /api/history/graph` отдаёт **точки по дням**, а не готовые кривые:

```json
{ "points": [
  { "day": "2026-08-01", "hands": 412, "net": 18400,
    "ev_net": 15100, "bb_sum": 41200, "ofc_points": 0 },
  ...
] }
```

Каждая точка — итог **за этот день**, не нарастающим итогом. Все кривые
PokerCraft-стиля строятся из этих полей на клиенте:

| График | Как построить |
|---|---|
| Банкролл | накопительная сумма `net` |
| EV-линия | накопительная сумма `ev_net` |
| Удача | разность двух предыдущих |
| Winrate по времени | `net / bb_sum * 100` на скользящем окне |
| Объём | `hands` столбиками |
| OFC в очках | накопительная сумма `ofc_points` |

Так сделано намеренно: одна выборка кормит все кривые сразу, а
переключение между ними не требует нового запроса. Фильтры (`from`, `to`,
`game_mode`, `setting_id`) применяются к точкам так же, как к спискам.

**Турнирный график строится не отсюда.** В турнирном разрезе `net` — это
фишки, и рисовать по ним банкролл нельзя. График турнирных денег строй по
призам из `/api/history/tournaments`: точка — турнир, значение —
`prize + bounty_paid + refund − buy_in − entry_fee − addons_cost`.
Смешивать две шкалы на одном полотне — прямая ложь игроку.

## 9. Турниры

`GET /api/history/tournaments` — список, курсорный, как и раздачи.

**Строка на каждый вход, а не на турнир.** Три ре-энтри в один турнир —
три элемента списка с одинаковым `tournament_id` и разным `entry_index`
(нумерация с нуля). Группируй их по `tournament_id` при отрисовке.

```json
{
  "id": "...", "entry_id": "...", "tournament_id": "...",
  "title": "Вечерний мейджор",
  "format": "mtt", "bounty": true,
  "entry_kind": "reentry", "entry_index": 2,
  "buy_in": 1000, "entry_fee": 100, "addons_count": 1, "addons_cost": 500,
  "prize": 5000, "bounty_paid": 800, "bounty_final": 1600, "refund": 0,
  "place": 2, "entrants": 90, "itm": true,
  "outcome": "busted",
  "hands_played": 214,
  "started_at": "...", "finished_at": "..."
}
```

* `outcome`: `busted` (вылетел), `won` (выиграл), `cancelled` (турнир
  отменили, пока игрок был жив), `unregistered` (снялся до старта).
  Последние два имеют `place: null` — мест в них не бывает; показывай
  «отменён» / «снят», а не «место —».
* `entrants` — сколько всего было входов. Без него «2-е место» ничего не
  значит: второе из девяноста и второе из девяти — разные достижения.
  Показывай их всегда парой: **2 / 90**.
* `bounty_paid` — головы, которые игрок **получил**. `bounty_final` —
  цена его собственной головы на момент вылета: справочная величина, в
  доход её включать нельзя (эти деньги он никогда не держал). Сервер её в
  ROI и не включает — не включай и ты.
* `refund` — возврат при отмене или снятии.

`GET /api/history/tournaments/:id` отдаёт `{ "entries": [...], "hands": [...] }`
— все входы игрока в этот турнир и его раздачи там.

**Важно:** `hands` может быть пустым при заполненном `entries` — и это
нормальный ответ, а не ошибка. Раздачи хранятся 90 дней, а результаты
турниров — вечно. Через три месяца турнир останется в списке с местом и
призом, но открыть его раздачи будет нельзя. Экран обязан это пережить:
покажи итог и подпись «раздачи больше не доступны» вместо пустой таблицы.

## 10. Срок хранения — предупредить заранее

Раздачи живут **90 дней**, потом удаляются. Не удаляется ничего из того,
что игрок считает «своей статистикой»: пожизненные winrate, VPIP, EV,
объём и все турнирные результаты остаются навсегда.

Из этого два требования к UI:

1. В фильтре периода не предлагай для списка раздач диапазоны глубже 90
   дней — вернётся пусто, и это будет выглядеть как баг.
2. На экране сводки, наоборот, глубокие периоды («за всё время») работают
   всегда: она читается из агрегатов, а не из раздач. Разница между двумя
   экранами должна быть проговорена в интерфейсе, иначе игрок решит, что
   часть его истории пропала.

## 11. Таблица: сортировки и выделение

Требование задачи — «как PokerCraft»: сортировки по всем колонкам,
выделение нескольких раздач, «выбрать все».

**Сортировка — на клиенте, в пределах загруженного.** Сервер отдаёт
раздачи строго по времени, от новых к старым, и другого порядка не
поддерживает: курсорная пагинация привязана именно к времени. Сортируй
загруженную ленту у себя, но не выдавай это за сортировку всей истории —
если загружено 200 из 12 000 раздач, «самая большая раздача» найдётся
только среди двухсот. Для честной сортировки по всей истории сначала
догрузи всё (или сузь период фильтром).

**Выделение — состояние клиента.** Сервер ни о каком «выбранном» не
знает. «Выбрать все» должно означать «все загруженные», и это стоит
писать явно рядом с чекбоксом.

**Экспорта в этой задаче нет.** Кнопок «скачать» и «выгрузить в трекер»
не делаем — эндпоинта под них на сервере не существует. Появится
отдельной задачей.

## 12. Порядок работ

1. HTTP-клиент с авторизацией и обновлением токена; общий разбор `422`.
2. Экран истории, вкладки, фильтр периода и лимита.
3. Список раздач с курсорной догрузкой — сначала холдем (`kind: "holdem"`).
4. Реплей холдема: борд, действия по порядку, правильная работа с
   `card_visibility`.
5. Сводка показателей: разные наборы полей по режимам, `ppm`-форматирование.
6. Графики из точек `/graph`.
7. Вкладка Tournament: группировка входов, ROI/ITM, пустой список раздач у
   старых турниров.
8. Вкладка OFC: своя строка списка, свой реплей, свой набор показателей.
9. Сортировки и выделение в таблице.
