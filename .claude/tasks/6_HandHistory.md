# Задача 6. История раздач и статистика игрока

Новый контекст `lib/block_poker/history/` и новый раздел `api/`. Всё, что
раздача уже вычислила в памяти `TableServer`, по её завершении уезжает в MySQL
одним batch-инсертом; спустя минуты или недели игрок открывает свою историю,
листает раздачи, разворачивает любую до пошагового вида и смотрит сводку
показателей — winrate, VPIP/PFR/агрессия, EV-adjusted winnings.

Ядру раздачи эта задача не добавляет ни строчки правил: `Engine.Hand` уже
считает всё, что нужно записать, а `Engine.Stats`, `Engine.Reveal` и
`Engine.Equity` существуют. Работа — в трёх местах: схема хранения, момент и
форма записи, выдача с корректной фильтрацией чужих карт.

**Чего в задаче нет.** Клиентский экран истории (отдельный документ в
`client-tasks/`). Оценка решений относительно оптимальной стратегии — это
солвер, отдельный проект. Античит-аналитика поверх записанного (§9 CLAUDE.md
оставляет её на потом; эта задача лишь обеспечивает достаточный объём данных).

---

## 1. Цель

* Сыгранная раздача сохраняется целиком: борд (оба прогона), все действия
  в порядке возникновения, карманные карты **всех** участников, банки,
  сайд-поты, рейк, вскрытие, результат каждого игрока.
* В историю и реплей уходят карты **только тех, кто их реально открыл** —
  по правилам вскрытия или добровольным показом. Мукнувший спрятал карты
  навсегда, независимо от того, что лежит в БД.
* Игрок видит свою статистику: winrate в bb/100, EV-adjusted winnings,
  VPIP / PFR / 3-Bet / AF / WTSD / W$SD, график банкролла по времени.
* Раздачи хранятся 90 дней; статистика — вечно, за счёт предварительной
  свёртки в дневные агрегаты.
* Кэш и Sit&Go пишутся в одну таблицу, но статистика по ним не смешивается.
* Запись раздачи **не блокирует** следующую (§6 CLAUDE.md).
* Ноль знания об истории в `socket/*`; в `api/*` — только парсинг параметров
  и рендер (§3).

## 2. Транспорт: почему здесь HTTP, и правка §3 CLAUDE.md

§3 сейчас говорит: «Игровая логика, лобби, кошелёк и история через HTTP не
доступны в принципе». Это правило для истории **отменяется**, и документ
правится в рамках этой задачи — иначе код и CLAUDE.md разойдутся, а
архитектурный тест границ (§11) окажется формально прав, запрещая то, что
решено делать.

Обоснование, которого §3 требует от каждого нового эндпоинта:

* История — **не real-time**. У неё нет ни одного свойства, ради которых
  существует канал: сервер ничего не пушит, состояние не меняется под
  игроком, задержка в сотню миллисекунд ничего не ломает.
* Это чтение с **пагинацией и фильтрами** — курсор, лимит, диапазон дат,
  лимит стола, режим. По каналу это пришлось бы изобретать поверх
  push-сообщений, с ручным учётом «какая страница уже у клиента».
* Ответ **кэшируется и идемпотентен**: раздача неизменна с момента записи.
  HTTP умеет это из коробки (`ETag`, `Cache-Control`), канал — нет.
* Объём выдачи (страница истории, реплей) не должен делить пропускную
  способность с игровым сокетом: тяжёлый ответ по каналу — это лишние
  миллисекунды у чужого таймера хода за столом.
* Выгрузка своей истории файлом — естественная HTTP-операция и неудобная
  канальная.

Формулировка, на которую §3 меняется: **история и статистика — единственное
чтение, вынесенное в HTTP; всё, что меняет состояние игры или требует пуша,
остаётся в сокете.** Инвариант «в `api/*` нет бизнес-логики» при этом не
ослабляется ни на йоту: контроллер достаёт `user_id` из `conn.assigns`,
парсит параметры страницы, зовёт одну функцию контекста `History` и рендерит.

Эндпоинты:

| Метод и путь | Назначение |
|---|---|
| `GET /api/history/hands` | страница списка своих раздач, курсорная пагинация, фильтры |
| `GET /api/history/hands/:id` | одна раздача целиком: реплей |
| `GET /api/history/stats` | сводка показателей за период |
| `GET /api/history/graph` | точки графика банкролла (накопительный результат) |

Авторизация — тем же токеном, что и остальной `api`. Чужая раздача — `404`,
а не `403`: существование чужой раздачи не подтверждается.

## 3. Схема хранения

Три таблицы раздачи плюс одна таблица агрегатов. Все денежные величины —
целые в минимальных единицах (§5 CLAUDE.md). Все таймстемпы —
`utc_datetime_usec`.

### 3.1 `hands` — сыгранная раздача

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `binary_id` | PK, он же идентификатор раздачи в протоколе |
| `room_id` | `string` | комната (`RoomState.room_id`), не FK: комнаты живут в памяти |
| `game_mode` | `Ecto.Enum` | `cash` \| `tournament` |
| `setting_id` | `binary_id` | шаблон: `cash_game_settings.id` либо настройка Sit&Go |
| `tournament_id` | `binary_id` \| null | экземпляр турнира; `null` для кэша |
| `hand_number` | `integer` | порядковый номер раздачи в комнате (`hands_played`) |
| `variant` | `Ecto.Enum` | `Variant.id()` — холдем, Short Deck и т.д. |
| `button_seat` | `tinyint` | |
| `bet_unit` | `bigint` | номинал структуры ставок на момент раздачи |
| `small_blind` / `big_blind` / `ante` | `bigint` | фактические, а не из шаблона: в турнире уровень растёт |
| `board` | `json` | борд первого прогона |
| `board_2` | `json` \| null | второй прогон run it twice; `null` — обычная раздача |
| `bomb_pot` | `bigint` \| null | взнос бомб-пота, если раздача им была |
| `pot` | `bigint` | итоговый банк до рейка |
| `rake` | `bigint` | взятый рейк |
| `pots` | `json` | слои банка: сумма, состав претендентов, победители |
| `started_at` / `ended_at` | `utc_datetime_usec` | |

Индексы: `(ended_at)` — для чистки; `(room_id, ended_at)`.

`setting_id` намеренно **не** внешний ключ с каскадным удалением: удаление
шаблона не должно стирать историю. Если шаблон удалён, раздача остаётся
читаемой — все существенные параметры (блайнды, вариант, номинал) скопированы
в строку, а не берутся по ссылке. Это же снимает вопрос «шаблон
отредактировали — история поехала».

### 3.2 `hand_players` — участник раздачи

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `binary_id` | PK |
| `hand_id` | `binary_id` | FK → `hands`, каскадное удаление |
| `user_id` | `binary_id` | FK → `users`, при удалении аккаунта обнуляется |
| `seat` | `tinyint` | |
| `position` | `Ecto.Enum` | `btn`, `sb`, `bb`, `utg`, `mp`, `co`… — вычисляется ядром при записи |
| `starting_stack` | `bigint` | стек до вынужденных ставок |
| `hole_cards` | `json` | **карты всех**, кому они пришли, независимо от показа |
| `card_visibility` | `Ecto.Enum` | `showdown` \| `voluntary` \| `hidden` — см. §4 |
| `invested` | `bigint` | всего вложено за раздачу, включая блайнды и анте |
| `won` | `bigint` | всего получено из банков |
| `net` | `bigint` | `won - invested`, денормализация ради дешёвых выборок |
| `ev_amount` | `bigint` \| null | EV-доля банка при олл-ине; `null` — олл-ина не было |
| `status` | `Ecto.Enum` | `folded` \| `showdown` \| `won_uncontested` \| `all_in` |
| `rank` | `json` \| null | комбинация на вскрытии, если до него дошло |

Индексы: `(user_id, hand_id)` unique; `(user_id, inserted_at)` — основная
выборка истории.

Ключевая денормализация: `net`, `invested`, `won` и `ev_amount` лежат рядом с
`user_id`, поэтому и список, и график, и сводка читаются **по одной таблице**,
без join к `hands` в горячем пути.

### 3.3 `hand_actions` — упорядоченный лог

| Поле | Тип | Смысл |
|---|---|---|
| `hand_id` | `binary_id` | FK → `hands`, каскадное удаление |
| `seq` | `integer` | порядок внутри раздачи; `(hand_id, seq)` — PK |
| `street` | `Ecto.Enum` | `preflop` \| `flop` \| `turn` \| `river` |
| `seat` | `tinyint` | |
| `action` | `Ecto.Enum` | `post_blind`, `post_ante`, `straddle`, `fold`, `check`, `call`, `bet`, `raise`, `all_in` |
| `amount` | `bigint` | вложено этим действием (не «до скольки») |
| `to_amount` | `bigint` | итоговая ставка улицы после действия — чтобы реплей не пересчитывал |
| `pot_before` | `bigint` | банк до действия: из него читаются шансы банка без пересчёта |
| `stack_after` | `bigint` | |
| `elapsed_ms` | `integer` | время на решение — материал для тайминг-теллов и античита |
| `auto?` | `boolean` | сработал преселект или таймаут, а не живое решение |

Вынужденные ставки пишутся такими же строками — иначе реплей начинается с
необъяснимого банка, а VPIP приходится считать вычитанием.

### 3.4 `player_stats_daily` — агрегаты, переживающие чистку

| Поле | Тип |
|---|---|
| `user_id` | `binary_id` |
| `day` | `date` (UTC) |
| `game_mode` | `Ecto.Enum` |
| `setting_id` | `binary_id` \| null — разрез по лимиту |
| счётчики `Engine.Stats` | `hands`, `vpip`, `pfr`, `three_bet_chances`, `three_bets`, `saw_flop`, `showdowns`, `aggressive`, `calls` |
| денежные | `net`, `invested`, `won`, `rake_paid`, `ev_net`, `bb_sum` |

PK — `(user_id, day, game_mode, setting_id)`.

Строка обновляется **инкрементально по завершении каждой раздачи**
(`INSERT … ON DUPLICATE KEY UPDATE col = col + VALUES(col)`), а не пересчётом
из `hands` перед чисткой. Причина принципиальная: агрегат, посчитанный на
лету, невозможно потерять при сбое джоба чистки и невозможно рассинхронизировать
с уже удалёнными данными. Свёртка «перед удалением» ломается ровно один раз —
и восстановить её будет уже неоткуда.

`bb_sum` — сумма больших блайндов по раздачам; winrate = `net / bb_sum * 100`.
Хранится сумма, а не среднее, по той же причине, по которой `Engine.Stats`
хранит числители и знаменатели раздельно: **проценты и средние не
складываются**, а агрегаты обязаны суммироваться по любому набору дней.

## 4. Карты: пишем всё, показываем показанное

Это центральное требование задачи и главный источник ошибок.

**В БД пишутся карманные карты всех**, кто их получил, включая сфолдивших на
префлопе. Без этого невозможны ни EV, ни разбор жалоб, ни последующая
античит-аналитика.

**Наружу карты отдаются, только если игрок их открыл.** Источник истины — не
«дошёл ли до шоудауна», а решение `Engine.Reveal`, уже принятое в раздаче,
плюс добровольный показ через окно `RoomState.reveal`. Отсюда три значения
`card_visibility`:

* `showdown` — вскрыл по правилам, включая олл-ин-вскрытие, где мука нет ни
  у кого;
* `voluntary` — показал сам: мукнув или выиграв без вскрытия;
* `hidden` — не показывал никогда.

Правило выдачи, одно и без исключений: **карты чужого игрока со значением
`hidden` не покидают сервер ни при каких параметрах запроса.** Свои карты
игрок видит всегда — он их и так знал.

Тонкость, которую легко упустить: показ бывает **после** записи раздачи. Окно
добровольного показа живёт паузу между раздачами, а запись уходит в БД сразу
по завершении. Значит `card_visibility` обновляется вторым, маленьким апдейтом
по закрытию окна показа, и запись раздачи не имеет права ждать окно — иначе
следующая раздача упрётся в предыдущую.

Инвариант, проверяемый тестом на сыром JSON ответа (по образцу теста
приватности `TableView` из §11): в ответе `/api/history/hands/:id` нет ни одной
карты игрока со значением `hidden`, кроме карт самого запрашивающего.

## 5. EV: считает ядро, наружу уходит число

EV-adjusted winnings отвечает на вопрос «сколько игрок должен был получить в
среднем» и требует карт оппонента — тех самых, которые тот мог не показать.
Разрешение конфликта: **эквити считается на сервере по настоящим картам, а
наружу уходит только итоговая сумма.**

* В момент, когда торговля прекратилась, а борд ещё не доведён (тот же
  `begin_runout/1`, на котором держится run it twice), `Engine.Equity` даёт
  доли претендентов. Модуль уже есть — новой математики задача не вносит.
* `ev_amount` игрока — его доля эквити от банка, считается **по слоям банка
  отдельно**: в каждом слое свой состав претендентов, и общая доля от общего
  банка при сайд-потах даёт неверный ответ. Рейк вычитается до умножения,
  как и при реальной выплате.
* Разница между фактом и ожиданием — это «удача»; клиент считает её сам из
  двух отданных чисел, сервер её не хранит.
* Одно число не позволяет восстановить руку оппонента: тот же EV даёт
  бесконечное множество раскладов. Именно поэтому EV можно показывать там,
  где карты показывать нельзя.
* Раздача без олл-ина: `ev_amount = null`, а в `ev_net` агрегата такая
  раздача входит своим фактическим `net`. Иначе EV-график разошёлся бы с
  реальным банкроллом на всех неолл-инных руках, что бессмысленно.
* Run it twice: EV считается **один раз, до разделения на прогоны** — эквити
  не зависит от того, сколько раз доводили борд. Это ровно то свойство, ради
  которого RIT и существует, и запись обязана его отражать.

## 6. Момент и форма записи

```
TableServer.finish_hand(state, hand)
  │  hand.results уже посчитан, стеки разъехались
  ├─▶ record_stats            (как сейчас, в память комнаты)
  └─▶ History.persist_async   (вне процесса стола)
         │
         ▼
      Ecto.Multi: insert      hands
                  insert_all  hand_players
                  insert_all  hand_actions
                  upsert      player_stats_daily (инкремент)
```

Требования к записи:

* **Не блокирует раздачу.** `TableServer` не ждёт БД ни микросекунды: отказ
  MySQL останавливает историю, но не игру.
* **Одна транзакция на раздачу.** Частично записанная раздача хуже
  незаписанной: она даст неверную статистику и сломанный реплей.
* **Идемпотентность по `hands.id`.** Повтор задачи (ретрай, рестарт) не
  создаёт вторую копию — `id` раздачи генерируется в момент её старта, а не
  в момент записи.
* **Материал берётся из событий, а не из состояния.** `hand_actions`
  собирается из того же списка событий, который уходит в broadcast (§7
  CLAUDE.md: «одни и те же факты, два потребителя»). Второго источника правды
  о ходе раздачи не заводим.
* Ретраи — Oban с экспоненциальной паузой; исчерпанная задача пишет ошибку в
  лог с `hand_id`, но никогда не роняет стол.

Позиция (`position`) вычисляется **ядром при записи**, из `button_seat` и
состава мест: это доменное знание, и в `api/` его быть не может.

## 7. Выдача

### `GET /api/history/hands`

Параметры: `cursor`, `limit` (≤ 100), `from`, `to`, `game_mode`, `setting_id`,
`only_won`. Курсор — пара `(ended_at, hand_id)`, не offset: offset на растущей
таблице даёт дубли и пропуски при листании.

Строка списка — это строка `hand_players` плюс несколько полей раздачи: время,
лимит, позиция, свои карты, борд, `net`, дошёл ли до вскрытия. Чужих карт в
списке нет вообще, даже показанных: список короткий, и незачем.

### `GET /api/history/hands/:id`

Полный реплей: раздача, все участники (с фильтром §4), все действия по
порядку. Ответ неизменяем — `ETag` и `Cache-Control: private, immutable`,
кроме случая, когда окно показа ещё не закрылось.

### `GET /api/history/stats`

Сводка за период. Читается из `player_stats_daily`, поэтому работает одинаково
и за вчера, и за год, и не зависит от того, живы ли ещё сами раздачи. Отдаёт
счётчики и производные, разрезом по режиму:

* **кэш**: раздач, `net`, winrate в bb/100, `ev_net` и EV-winrate,
  VPIP / PFR / 3-Bet / AF / WTSD / W$SD, уплаченный рейк;
* **турнир**: раздач, сыграно турниров, ITM, ROI, средняя финишная позиция.
  bb/100 в турнирном разрезе **не отдаётся**: величина большого блайнда
  меняется по уровням, и средневзвешенная цифра будет ложью.

Разрез сессий — по правилу проекта: в кэше сессия равна отрезку за одним
местом, в турнире — весь турнир, включая пересадки.

### `GET /api/history/graph`

Точки накопительного результата: время, `net` нарастающим итогом, `ev`
нарастающим итогом, число раздач. Гранулярность — день из
`player_stats_daily` за длинные периоды, отдельные раздачи за короткие, пока
все раздачи периода ещё живы.

## 8. Хранение 90 дней

* Oban-джоб раз в сутки удаляет `hands` старше 90 дней; `hand_players` и
  `hand_actions` уезжают каскадом по внешнему ключу.
* Удаление — **пачками с ограничением** (порядка 5 000 раздач за проход, с
  паузой), а не одним `DELETE`: длинный `DELETE` на MySQL держит блокировки
  и растит undo-лог.
* `player_stats_daily` не трогается никогда. Пожизненные winrate, VPIP и EV
  у игрока остаются; теряется только возможность открыть конкретную старую
  раздачу.
* Срок — конфиг (`config :block_poker, :history_retention_days, 90`), а не
  константа в коде джоба: он почти наверняка будет меняться.
* Удаление аккаунта: `hand_players.user_id` обнуляется, сама раздача остаётся —
  она общая для всех, кто сидел за столом, и вычёркивать из неё игрока значит
  ломать чужую историю. Персональные агрегаты удаляются вместе с аккаунтом.

## 9. Тесты

**Уровень 3 (контексты, реальная MySQL под Sandbox):**

* повторный `persist` той же раздачи не создаёт второй строки;
* `player_stats_daily` после N раздач совпадает с суммой по `hand_players`;
* каскад: удаление `hands` уносит игроков и действия, не оставляя сирот;
* инвариант §11 «фишки не возникают и не исчезают» проверяется **на
  записанном**: сумма вложенного равна сумме полученного плюс рейк, для
  каждой раздачи.

**Уровень 4 (функциональные, HTTP насквозь):**

* чужой `hand_id` → `404`;
* **приватность на сыром JSON**: в ответе реплея нет карт игроков со
  значением `hidden`, кроме своих;
* мукнувший победитель без вскрытия: его карты скрыты и в списке, и в
  реплее, при том что в БД они лежат;
* добровольный показ после записи меняет выдачу — то есть `card_visibility`
  действительно обновляется вторым апдейтом;
* пагинация курсором не теряет и не дублирует раздачи, если между запросами
  страниц добавились новые.

**Уровень 1 (ядро, без БД и процессов):**

* позиция по `button_seat` и составу мест — таблично, включая хедз-ап, где
  кнопка совпадает с малым блайндом;
* EV по слоям банка при нескольких олл-инах: сумма `ev_amount` всех
  претендентов равна банку после рейка;
* EV при run it twice не зависит от числа прогонов.

Архитектурный тест границ (§11) обновляется: `api/*` получает разрешение на
контекст `History` — но по-прежнему не на `Repo`, `Ecto.Query` и доменные
состояния улиц.

## 11. Чего эта задача не имеет права замедлить

Стол — один процесс, и всё, что выполняется в нём синхронно, задерживает
таймеры хода живых игроков. Поэтому три отдельных требования, каждое со
своей причиной.

**Запись в БД.** `finish_hand/2` идёт внутри процесса стола. `persist_async`
обязан быть именно асинхронным: собрать данные и отдать их наружу, не
дожидаясь ни транзакции, ни коннекта из пула. Проверка при ревью простая —
после вызова записи в коде стола не должно остаться ни одного `Repo`-вызова
и ни одного `GenServer.call` в сторону БД. Пул коннектов Ecto в момент
пиковой нагрузки конечен, и ожидание коннекта — это ровно то место, где
стол встанет.

**EV не считается второй раз.** Здесь главный риск задачи. Эквити уже
считается при олл-ине — `Hand.equity_for/4` (`hand.ex:747`), Монте-Карло на
20 000 итераций, синхронно в процессе стола. Это существующее поведение, у
него есть основание: стол в этот момент всё равно стоит на паузе доводки
борда, и результат нужен клиентам немедленно.

Задача **не добавляет второго расчёта.** `ev_amount` получается из уже
посчитанного и уже разосланного результата эквити: доля игрока умножается
на слой банка. Это арифметика над готовыми числами — микросекунды, а не
перебор. Отдельный вызов `Equity.equity/4` ради истории — прямая ошибка
реализации, и в ревью его быть не должно.

Отсюда следствие для структуры кода: результат эквити, посчитанный в момент
олл-ина, должен **дожить до конца раздачи** (он и так живёт в
`RoomState.showdown`), а не быть выброшенным сразу после broadcast.

**Сборка строк — вне процесса стола.** `hand_actions` строится из списка
событий, который у стола уже есть. Сам обход дешёвый, но выполняться он
должен в фоновом процессе: стол отдаёт наружу сырые данные раздачи, всё
преобразование в строки, вычисление позиций и агрегатов происходит уже там.

**Что проверяется тестом.** Время, проведённое в `finish_hand/2`, не зависит
от того, включена запись истории или нет: тест на процессном уровне
завершает раздачу при недоступном (или искусственно медленном) хранилище и
убеждается, что следующая раздача стартует в обычный срок, а таймеры хода
не сдвинулись.
