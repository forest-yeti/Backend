# Задача 3. Кэш-игра: настройки, комнаты, посадка

Шаблон игры (`CashGameSetting`) и живые сетевые комнаты, которые из него
разворачиваются. Игрок видит лобби, садится на место, заносит фишки из кошелька
и встаёт из-за стола.

**Раздача не входит в эту задачу.** Ставки, улицы, вскрытие, таймеры хода —
следующая задача. Здесь комната умеет ровно одно: принимать и отпускать игроков,
корректно двигая деньги. Раздачи в ней ещё не идут.

---

## 1. Цель

* `CashGameSetting` — шаблон в БД, редактируемый без деплоя.
* Под каждый шаблон автоматически поддерживается пул комнат: **всегда есть
  ровно одна комната со свободными местами**.
* Игрок садится, деньги переезжают «кошелёк → стол» одной транзакцией
  через ledger задачи 1; встаёт — переезжают обратно.
* Лобби показывает актуальную картину и обновляется пушем, а не опросом.

---

## 2. `CashGameSetting`

### Поля из постановки

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `binary_id` | PK |
| `small_blind` | `bigint` | > 0, минимальные единицы |
| `big_blind` | `bigint` | > `small_blind` |
| `ante` | `bigint` | >= 0, `0` = нет анте |
| `ante_type` | `Ecto.Enum` | `big_blind` \| `per_player`, значимо при `ante > 0` |
| `game_type` | `Ecto.Enum` | `holdem` (пока единственный) |
| `max_players` | `integer` | 2..9 |

`game_type` — это `Variant.id()` из задачи 2. Один и тот же атом, чтобы шаблон
напрямую выбирал модуль варианта, а не переводил одно перечисление в другое.

### Что предлагаю добавить

Разбито по причине, а не по алфавиту — каждая опция здесь потому, что без неё
что-то ломается или становится невозможным.

**Без этого нельзя посадить игрока:**

* `currency` (`Ecto.Enum`: `main` | `play_money`) — **из какого кошелька
  бай-ин**. У игрока их два (задача 1), и стол обязан знать свой. Без этого поля
  реальные и игровые фишки смешаются в первый же день.
* `min_buy_in` / `max_buy_in` — в **больших блайндах**, не в абсолютных
  единицах: `min: 40`, `max: 100` — это классический 100bb-стол, и такая запись
  переживает смену лимитов. Абсолютные значения считаются от `big_blind`.
* `max_buy_in` может быть `nil` — стол без верхнего лимита (deep).

**Рейк — комиссия рума, единственный источник дохода:**

* `rake_percent` — доля банка, которую забирает рум. Стандарт — 5%. Хранится
  целым в сотых долях процента (`500` = 5%): float в деньгах запрещён (§5).
* `rake_cap_by_players` — потолок рейка на раздачу, в **фишках**, ключ —
  число игроков, реально участвовавших в раздаче:
  `%{"2" => 100, "3" => 200, "5" => 300}` — применяется ближайший меньший ключ.
  Значения задаются оператором на каждый шаблон, значений по умолчанию в коде
  нет. Без потолка 5% от банка в 500bb превращаются в 25bb — за такими столами
  не играют; зависимость от числа игроков нужна потому, что на хедз-апе банки
  меньше и единый кап был бы непропорционально тяжёлым.
  Валидация: ключи — числа 2..`max_players`, значения неотрицательны,
  обязателен ключ `2`.
* `no_flop_no_drop` (boolean, default `true`) — не брать рейк, если раздача
  закончилась до флопа. Иначе рум зарабатывает на раздачах, где игры
  фактически не было.
* **На `play_money`-столах рейк не берётся.** Поля в шаблоне присутствуют,
  но при `currency: :play_money` игнорируются — проверяется тестом.
  Ветвление живёт в расчёте рейка в ядре, не в настройке.

**Без этого стол зависает:**

* `action_timeout_ms` — время на ход. Без него первый же ушедший игрок
  останавливает стол навсегда.
* `time_bank_ms` / `time_bank_refill` — банк времени сверх основного таймера.
* `disconnect_grace_ms` — окно реконнекта из §5 CLAUDE.md.
* `sit_out_max_hands` — сколько раздач можно просидеть вне игры, прежде чем
  место освобождается.
* `rebuy_prompt_ms` — сколько времени даётся на докупку игроку, у которого
  стек обнулился (§4, «нулевой стек»).
* `button_draw_animation_ms` — пауза на анимацию розыгрыша кнопки (§5),
  по умолчанию 3000.
* `allow_post_blind` (boolean, default `true`) и `blind_dodge_window_hands`
  (default 10) — вход в игру и защита от уклонения от блайндов (§6).

**Управление и витрина:**

* `name` — как стол называется в лобби; если пусто, генерируется из лимитов.
* `enabled` (boolean) — выключенный шаблон не порождает новых комнат;
  существующие доигрывают и закрываются. Нужен, чтобы убирать лимиты
  из лобби без удаления строки и потери истории.
* `visibility` (`Ecto.Enum`: `public` | `private`) — задел под приватные столы;
  в этой задаче реализуется только `public`, поле заводится сразу.
* `sort_order` — порядок в лобби.
* `max_rooms` — потолок числа комнат на шаблон, по умолчанию **100**.
  Достигнут потолок и все комнаты полны — новые не создаются, игрок получает
  `no_seats_available`. Предохранитель от того, что поток заходов наплодит
  процессов быстрее, чем кто-либо это заметит.

**Про `ante_type`.** Появился потому, что в сетке есть столы с анте (§6),
а одного числа для описания анте недостаточно — платят его по-разному:

* `big_blind` — всю сумму вносит один игрок на большом блайнде. Современный
  стандарт онлайн-кэша: меньше действий на раздачу, проще считать, банк тот же.
* `per_player` — вносит каждый игрок за столом. Классика оффлайна.

Разница видна и в банке, и в стеках, поэтому это не косметика, а правило.
Принято: `ante_type: :big_blind`, сумма — **половина большого блайнда**
(`ante = big_blind / 2`). Для нечётных `big_blind` округление вниз, но в сетке
§6 все большие блайнды чётные, кроме NL5 (bb = 5 → анте 2).

**Сознательно НЕ добавляю сейчас** (каждое — отдельная механика, а не флажок):
straddle, run-it-twice, ante-типы кроме простого, лист ожидания, бонусы
и джекпоты. Если что-то из этого нужно — скажи, вынесу в отдельную задачу.

### Отношение к `table_configs` из CLAUDE.md

Таблица называется **`cash_game_settings`**. В §6 CLAUDE.md она поименована
`table_configs` — формулировка в документе правится в рамках этой задачи,
чтобы код и документ не разъезжались.

### Валидация

* `big_blind > small_blind`, `ante >= 0`, `max_players` в 2..9;
* `min_buy_in >= 20` bb и `max_buy_in >= min_buy_in` (или `nil`);
* `rake_percent` в 0..1000 (0..10%);
* правило «`min_buy_in` в фишках >= 2 больших блайнда» — иначе игрок садится
  с невозможностью поставить блайнд.

## 3. Комнаты

### Что такое комната

Комната (`Room`) — **процесс, а не строка в БД** (§1.3 CLAUDE.md).
`TableServer` под `DynamicSupervisor`, адресуется через `Registry`.
Переживать рестарт ноды комната не обязана: после рестарта пул поднимается
заново из `cash_game_settings` пустым, фишки возвращаются в кошельки
recovery-шагом (§8 CLAUDE.md).

Состояние комнаты в этой задаче: ссылка на шаблон, места, занятость, стеки,
статус каждого игрока (`playing` / `sitting_out` / `disconnected`) и счётчик
`action_seq`.

### Пул комнат: правило масштабирования

Инвариант, который поддерживается всегда:

> Для каждого включённого шаблона существует **ровно одна** комната
> со свободными местами.

Из него следуют оба направления:

* **Открытие.** Игрок занял последнее свободное место в комнате → комната
  перестала быть «той самой со свободными местами» → немедленно создаётся
  новая пустая. Твой пример: `0.1/0.2 → 9/9` порождает `0.1/0.2 → 0/9`.
* **Закрытие.** Комната опустела, и она не единственная свободная для шаблона →
  закрывается. Иначе после вечернего пика останутся десятки пустых комнат.

Почему именно инвариант, а не «создать новую, когда заполнилась»: вторая
формулировка описывает событие, и её легко нарушить в обход — при выключении
шаблона, при падении комнаты, при массовом уходе игроков. Инвариант проверяется
в одном месте после любого изменения состава и самовосстанавливается.

**Кто следит.** `BlockPoker.Tables.Lobby` — единственный владелец пула:
он знает список комнат по каждому шаблону, подписан на их события и отвечает
за создание и закрытие. Комната сама себя не порождает и не убивает: иначе
две комнаты, освободившиеся одновременно, обе решат, что вправе закрыться.

**Порядок операций при заполнении.** Новая комната создаётся **до** того, как
игроку отвечено об успешной посадке. Иначе между «место занято» и «комната
создана» есть окно, в котором лобби показывает шаблон без свободных мест.

**Закрытие с оговорками.** Комната закрывается, только если: пуста, не идёт
раздача, нет мест в grace-периоде реконнекта и нет фишек, не вернувшихся
в кошельки. Иначе — помечается `:draining` и закрывается по завершении.

### Старт ноды

При запуске приложения `Lobby` читает все включённые шаблоны и **сразу**
поднимает по одной пустой комнате на каждый. Лениво — при первой попытке сесть —
не делаем: лобби с нулём комнат выглядит как сломанный рум, а пустой `GenServer`
стоит несколько килобайт.

### Идентификация

* Шаблон — стабильный UUID из БД, живёт вечно.
* Комната — UUID, выданный при запуске, живёт до закрытия. Клиент подписывается
  на топик `table:<room_id>`.

Номер комнаты для UI (`0.1/0.2 #2`) — производная от порядка запуска;
хранить его в состоянии не нужно, лобби вычисляет при рендере.

## 4. Посадка и деньги

### Сценарий `join_seat`

```
"join_seat" %{room_id: ..., seat: 3, buy_in: 20_00}
```

Ровно один вызов контекста из канала (§3 CLAUDE.md):
`Tables.join_seat(room_id, user_id, seat, buy_in)`.

Внутри — строгий порядок, и он важен:

1. **Резерв места** в `TableServer` (`handle_call`, значит атомарно):
   место свободно → помечается `:reserved` за этим `user_id` с коротким TTL.
   Резерв нужен, потому что следующий шаг ходит в БД, а место всё это время
   не должно достаться другому.
2. **Списание из кошелька** — транзакция ledger задачи 1: запись `buy_in`
   на нужный кошелёк, `idempotency_key = "buyin:<reservation_id>"`.
3. **Подтверждение** резерва: место занято, стек = сумма бай-ина.
4. Если шаг 2 упал (не хватило денег, кошелёк заморожен) — резерв снимается,
   игроку уходит код ошибки. Фишки не появились из воздуха ни в одном исходе.

Обратный порядок (сначала посадить, потом списать) даёт стол, на котором
сидит игрок без денег. Порядок «списать, потом сажать» — деньги, списанные
в никуда, если место успели занять.

### Правила посадки

* `buy_in` в границах `[min_buy_in, max_buy_in]` шаблона, пересчитанных
  в фишки от `big_blind`.
* Один пользователь — **одно место в комнате**. Проверяется в `TableServer`,
  а не в канале.
* За разными комнатами — хоть одного шаблона, хоть разных — один игрок сидеть
  **может**: мультитейблинг разрешён. Ограничение ровно одно и проверяется
  в `TableServer`: в пределах одной комнаты у игрока одно место.
### Быстрый вход

Кнопка «сесть» без выбора комнаты и места. Запрос адресуется **шаблону**,
а не комнате — игрок выбирает лимит (NL2, NL10), а не конкретный стол:

```
"quick_seat" %{setting_id: ..., buy_in: 20_00}
```

`Tables.quick_seat(setting_id, user_id, buy_in)` сам находит комнату
со свободными местами (по инварианту §3 она ровно одна) и сажает на первое
свободное место. Дальше — тот же путь §4: резерв, ledger, подтверждение.

**Исключение для Heads-Up.** При `max_players: 2` правило выбора комнаты
другое: сначала комната, где **уже кто-то ждёт соперника**, и только если
такой нет — пустая. Инвариант §3 сам по себе даёт обратное: третий желающий
открыл бы вторую комнату и сел ждать в одиночестве рядом с таким же ждущим.
На столах 6-max и 9-max этой проблемы нет — там игроки собираются в общую
комнату естественным образом.

Обычный `join_seat` с явными `room_id` и `seat` остаётся — он нужен, когда
игрок открыл конкретную комнату из лобби и выбрал место мышью.

Отдельно: если между выбором комнаты и резервом места её успели заполнить,
`quick_seat` **повторяет попытку** на следующей комнате, а не возвращает
ошибку. Игрок нажал «сесть за NL10» — его волнует лимит, а не комната.

### `leave_seat` и `add_chips`

* `leave_seat` — если раздача не идёт, место освобождается сразу и стек уходит
  в кошелёк записью `cash_out`. Если игрок в раздаче — она доигрывается
  (в этой задаче раздач ещё нет, но поведение закладывается),
  затем cash-out.
* `add_chips` (докупка) — **между раздачами, в любой момент**, независимо
  от текущего стека; верхняя граница — `max_buy_in`. Тот же путь через ledger.
  Запрет во время раздачи обязателен: докупка на ходу меняет размер
  эффективного стека посреди торговли и ломает уже сделанные ставки.
* Разрыв соединения — **не** cash-out: место держится `disconnect_grace_ms`,
  затем игрок переводится в `sitting_out`, а по `sit_out_max_hands` встаёт
  из-за стола с автоматическим cash-out.

### Нулевой стек

Игрок проиграл весь стек — место **не освобождается сразу**. Ему уходит
предложение докупиться с таймером `rebuy_prompt_ms`:

* игрок переводится в `sitting_out` и раздачи пропускает — с нулевым стеком
  играть нельзя, а держать раздачу ожиданием его решения недопустимо;
* докупил в пределах `[min_buy_in, max_buy_in]` → возвращается в игру
  со следующей раздачи;
* таймер истёк или игрок отказался → встаёт из-за стола, место освобождается.
  Cash-out на ноль записи в ledger не порождает: движения денег нет.

Почему не подъём сразу: игрок, проигравший стек в большой раздаче, почти всегда
хочет продолжить, и отобранное место он получит обратно уже не факт что за этим
столом. Почему не автодокупка: молча списывать деньги из кошелька без явного
подтверждения нельзя.

### Инвариант денег

Для любого момента времени:

```
фишки в комнате + баланс кошелька == баланс до посадки
```

Проверяется тестом на каждом сценарии (§11 CLAUDE.md, «сохранение фишек»).
Фишки создаются только записью `buy_in` и уничтожаются только `cash_out`.

## 5. Розыгрыш баттона при старте игры

Когда за столом впервые собирается достаточно игроков, кнопка дилера
не назначается молча — она **разыгрывается на глазах у всех**: каждому
участнику открыто сдаётся по одной карте, кнопку получает старшая.

Смысл не в механике (её можно было бы решить одним `rand`), а в доверии:
позиция — это деньги, и игрок должен видеть, что она досталась не по решению
сервера. Ровно поэтому карты открытые и одинаковые для всех зрителей.

### Правила

* Розыгрыш проводится **только при старте игры за столом** — когда раздач
  ещё не было или стол простаивал без игры и собирается заново. Дальше кнопка
  просто двигается по часовой стрелке от раздачи к раздаче.
* Карты сдаются по одной, по часовой стрелке, начиная с места слева
  от условной первой позиции. Каждая карта видна всем.
* Старшая карта берёт кнопку. **Ранг сравнивается первым; при равенстве
  рангов — масть**, в порядке `♠ > ♥ > ♦ > ♣`. Масть как тайбрейк —
  общепринятое решение: оно детерминировано и не требует пересдачи.
* Пересдача при равенстве не нужна вовсе — с мастевым тайбрейком полного
  совпадения не бывает.
* Колода для розыгрыша — **отдельная**, из `Variant.deck/0` (Short Deck
  разыгрывает баттон своими 36 картами). После розыгрыша она отбрасывается
  целиком: первая раздача тасуется заново.

### Реализация

Чистая функция в ядре, потому что это правило игры, а не транспорт:

```elixir
@spec draw(seats :: [seat], variant :: module(), rng) ::
        {button_seat :: seat, [%{seat: seat, card: Card.t}]}
```

RNG — тот же инжектируемый источник, что и для раздачи (§9 CLAUDE.md):
`:crypto.strong_rand_bytes/1` в проде, детерминированный в тестах. Тест
подставляет seed и проверяет, что кнопка досталась ожидаемому месту.

Функция **универсальна** — она ничего не знает про кэш: турнирный стол
разыгрывает кнопку так же (§8). Вызывает её `GameMode` в момент, когда решает
запустить первую раздачу.

### Показ клиенту

`TableServer` рассылает событие в топик `table:<room_id>`:

```json
"button_draw" {
  "cards": [ {"seat": 3, "card": {"rank": 14, "suit": "S"}}, ... ],
  "button_seat": 3,
  "animation_ms": 3000
}
```

Раздача **не начинается**, пока идёт анимация: `TableServer` ставит таймер
на `button_draw_animation_ms` и запускает первую раздачу по его срабатыванию.
Значение — поле шаблона (`button_draw_animation_ms`, по умолчанию 3000).

Порядок сдачи клиент восстанавливает из порядка элементов `cards` — отдельного
поля с индексом не нужно. Игрок, подключившийся в середине анимации, получает
обычный `table_state` с уже назначенной кнопкой: догонять анимацию не нужно,
результат от неё не зависит.

Таймер — обычный `Process.send_after` с `deadline_ref` (§4 CLAUDE.md);
просроченный ref игнорируется, поэтому падение и перезапуск комнаты во время
анимации не приводят к двойному старту раздачи.

## 6. Вход в игру: ожидание большого блайнда

Сев на место, игрок **не начинает играть немедленно**. Иначе вход за стол
становится способом не платить.

### Зачем это нужно

Блайнды — обязательная плата за круг, и каждый сидящий вносит её раз в круг.
Игрок, которому позволено вступить в любой момент, сядет сразу за кнопкой,
сыграет самые выгодные позиции круга бесплатно и встанет перед блайндами.
Повторяя это, он играет покер, в котором не платит блайнды вообще, а остальные
платят за него. Правило существует ровно для того, чтобы стоимость входа
в игру равнялась стоимости для тех, кто уже сидит.

### Как это работает

Сев, игрок получает выбор:

* **Ждать большого блайнда** (по умолчанию) — он в `waiting_for_bb`, карты
  ему не сдаются, стек не трогается. Как только очередь большого блайнда
  доходит до его места, он ставит блайнд и вступает в игру обычным образом.
* **Войти немедленно (post)** — вносит сумму, равную большому блайнду,
  и получает карты в ближайшей раздаче. Если место находится между кнопкой
  и большим блайндом (то есть круг блайндов он в этой раздаче пропускает),
  внесённая сумма — **мёртвая**: она уходит в банк, но не считается его
  ставкой и не даёт права чека. Так вход стоит ровно столько же, сколько
  сидящему обходится круг.

Отдельный случай без выбора: сев **на большой блайнд или сразу за него**
(следующий по кругу), игрок вступает сразу и платит обычный блайнд — ждать
нечего, круг и так начинается с него.

**Heads-Up** — исключение: за двухместным столом ожидание бессмысленно,
второй севший игрок вступает немедленно, и блайнды начинаются со следующей
раздачи.

### Пропущенные блайнды и уход из-за стола

То же правило закрывает вторую дыру — уход перед блайндом и возвращение
после него:

* у каждого места есть счётчик `missed_blinds` — какие обязательные ставки
  игрок пропустил, будучи в `sitting_out` или отключённым;
* вернувшийся в игру с непогашенными пропусками либо ждёт своего большого
  блайнда, либо доплачивает их и вступает сразу — тот же выбор;
* игрок, **вставший из-за стола и севший обратно в ту же комнату** в пределах
  `blind_dodge_window_hands` раздач, теряет право «ждать большого блайнда»
  и может войти только через post. Без этого окна вся конструкция обходится
  циклом «встал — сел».

### Поля шаблона

* `allow_post_blind` (boolean, default `true`) — разрешён ли немедленный вход
  за post. При `false` единственный путь — дождаться большого блайнда.
* `blind_dodge_window_hands` (integer, default 10) — окно, в котором повторная
  посадка в ту же комнату требует post.

### Протокол

```
"join_seat" %{room_id: ..., seat: 3, buy_in: 20_00, entry: "wait_bb" | "post"}
```

Значение `entry` — **намерение**, а не решение: если правила требуют иного
(место на большом блайнде, хедз-ап, непогашенные пропуски, окно возврата),
контекст решает сам и сообщает результат. Канал ничего из этого не проверяет
(§3 CLAUDE.md) — он лишь передаёт поле.

Состояние места в снапшоте: `waiting_for_bb`, `missed_blinds`, а также
`can_post` — можно ли прямо сейчас войти за post. Клиент рисует по ним кнопку
«Ждать BB / Войти сейчас», но правом решать не обладает.

### Куда это ложится в коде

Расчёт «что должен внести вступающий» — правило игры, а не политика режима:
турнир на ребай-этапе устроен так же. Значит, это часть будущего движка
раздачи и `Engine.HandSetup`: в него игроки приходят уже с признаком
«участвует / ждёт» и с суммой обязательного взноса. `GameMode.Cash`
отвечает лишь за окно возврата и за то, что post списывается со стека,
а не из кошелька.

## 7. Лобби

Топик `lobby`, канал `Socket.Channels.LobbyChannel`.

**Что показываем.** Список **шаблонов**, а не комнат: игрок выбирает лимиты,
а не конкретную комнату. Показываются **все** включённые шаблоны, включая
пустые: игрок должен видеть, за какой лимит он в принципе может сесть,
а не только тот, где уже кто-то сидит. Сортировка — `sort_order`, затем
по числу игроков. Под каждым шаблоном — агрегат:

```json
{
  "setting_id": "...",
  "name": "NL Hold'em 0.1/0.2",
  "small_blind": 10, "big_blind": 20, "ante": 0,
  "game_type": "holdem",
  "currency": "play_money",
  "max_players": 9,
  "players_total": 14,
  "rooms": [
    { "room_id": "...", "seats_taken": 9, "max_players": 9 },
    { "room_id": "...", "seats_taken": 5, "max_players": 9 }
  ]
}
```

Разворачивать список комнат игрок может, но по умолчанию ему достаточно
кнопки «сесть» — сервер сам выбирает комнату (ту самую, со свободными местами).

**Обновления** — `table_delta`-подобные пуши в топик `lobby` при изменении
занятости, открытии и закрытии комнаты. Опроса нет.

**Источник данных** — `Lobby` GenServer, который и так владеет пулом.
Отдельной read-модели в БД не заводим — прямой запрет §7 CLAUDE.md.

## 8. Управление шаблонами

Шаблоны правятся **напрямую в БД** — HTTP-эндпоинтов для админки нет.
Приложение строки только читает. Единственное исключение — задача первичного
наполнения (ниже): руками набивать три десятка строк с блайндами, бай-инами
и капами рейка — это гарантированная опечатка в одной из них.

### `mix cash_game.seed` — генерация сетки лимитов

Задача разворачивает **стандартную лестницу лимитов** одной командой:

```
mix cash_game.seed                      # обе валюты целиком: 72 шаблона
mix cash_game.seed --currency play_money
mix cash_game.seed --only NL2,NL5,NL10  # часть лестницы
mix cash_game.seed --dry-run            # показать, что будет создано
```

Разворачиваются **обе валюты**: `main` и `play_money`. Реальные столы
существуют и видны, но сесть за них можно только на пополненный кошелёк —
пополнения появятся вместе с платежами.

Рейк сид проставляет **нулевой** (`rake_percent: 0`, капы пустые) — значения
задаются в БД оператором. Чтобы нулевой рейк не оказался забытой настройкой,
при старте `Lobby` логирует предупреждение по каждому включённому шаблону
с `currency: :main` и `rake_percent = 0`.

Сетка задаётся не в коде задачи, а в файле `priv/cash_games/grid.exs` —
структурой данных. Менять лестницу должно быть правкой данных, а не кода.

**Правило вывода лимитов.** Уровень называется по максимальному бай-ину:
`NLx` = бай-ин 100bb равен `x`, значит `bb = x / 100`, `sb = bb / 2`.
Одно правило на обе валюты, никаких таблиц-исключений — кроме NL5, где
отраслевой стандарт `0.02 / 0.05`, то есть `sb = 0.4 × bb` (пополам не делится).

**Реальные деньги** (суммы в центах), 12 уровней:

| Уровень | SB / BB | | Уровень | SB / BB |
|---|---|---|---|---|
| NL2 | 1 / 2 | | NL200 | 100 / 200 |
| NL5 | 2 / 5 | | NL500 | 250 / 500 |
| NL10 | 5 / 10 | | NL800 | 400 / 800 |
| NL20 | 10 / 20 | | NL1000 | 500 / 1000 |
| NL50 | 25 / 50 | | NL2000 | 1000 / 2000 |
| NL100 | 50 / 100 | | NL5000 | 2500 / 5000 |

**Play money** (суммы в фишках), 6 уровней:

| Уровень | SB / BB |
|---|---|
| NL1000 | 5 / 10 |
| NL5000 | 25 / 50 |
| NL10000 | 50 / 100 |
| NL30000 | 150 / 300 |
| NL50000 | 250 / 500 |
| NL100000 | 500 / 1000 |

Нижний уровень play money выбран так, чтобы стартовых 10 000 фишек (задача 1)
хватало на десять бай-инов по 1 000 — игрок не остаётся ни с чем после первой
неудачной сессии.

**Форматы столов.** На каждый уровень — четыре шаблона:

| Формат | `max_players` | `ante` |
|---|---|---|
| 6-max | 6 | 0 |
| 6-max Ante | 6 | `big_blind / 2`, тип `big_blind` |
| 9-max | 9 | 0 |
| Heads-Up | 2 | 0 |

Итого: 12 × 4 = **48** шаблонов на реальные деньги и 6 × 4 = **24** на play
money, всего 72. Каждый — отдельный пул комнат, и при старте ноды это 72 пустых
`GenServer`'а (§3). Само по себе это ничего не стоит, но лобби из 72 пустых
столов — реальный вопрос к первому экрану: пустые уровни в списке лучше
сворачивать, а не показывать наравне с живыми (вопрос 2 в §9).

**Имя в лобби** генерируется из уровня и формата: `NL10 6-max`,
`NL10 6-max Ante`, `NL10 9-max`, `NL10 HU`.

**Идемпотентность.** Задача обязана быть безопасной при повторном запуске:
второй прогон не создаёт дублей и не сбрасывает правки оператора. Для этого
у шаблона есть естественный ключ и **UNIQUE-индекс** на
`(game_type, currency, small_blind, big_blind, ante, max_players)`.
Существующая строка не трогается вовсе — вывод сообщает, что она пропущена.
Перезапись только по явному `--force`, и она не касается `enabled`:
выключенный оператором лимит не должен воскресать от повторного сида.

Из этого следует одно требование, которое иначе легко упустить: приложение
**не узнаёт об изменении строки само**. `Lobby` держит шаблоны в памяти,
и запись в MySQL мимо приложения его не будит. Нужен явный способ перечитать:

* **`Lobby.reload/0`** — перечитывает `cash_game_settings` и приводит пул комнат
  в соответствие: под новые включённые шаблоны поднимает комнаты, под
  выключенные — переводит комнаты в `:draining`.
* Вызывается из `iex` на ноде и по периодическому таймеру (интервал в конфиге,
  ориентир — 60 секунд). Периодический — чтобы правка в БД доезжала сама,
  без похода в консоль.

**Правка шаблона на лету:** изменения не применяются к уже запущенным комнатам.
Комнаты доигрывают на старых условиях, новые запускаются на новых. Иначе игрок
садился на 0.1/0.2, а обнаружил себя на 1/2. Практически это значит, что
`TableServer` при запуске **копирует** значения шаблона себе в состояние,
а не ходит за ними в `Lobby` по ходу игры.

**Удаление строки** шаблона запрещено — на неё ссылается история раздач.
Выключение делается через `enabled = false`.

## 9. Граница «комната / раздача»: задел под турниры и другие виды покера

Раздача в этой задаче не реализуется, но **швы прорезаются здесь** — потом
резать по живому дороже. Требование: порядок ходов, набор доступных решений
и течение улиц должны быть одним и тем же кодом для кэша, турниров, Short Deck
и всего, что появится дальше.

### Что универсально, а что нет

Наблюдение, на котором держится всё разделение: **сама раздача везде
одинакова, различия живут между раздачами.**

Внутри раздачи — от постановки блайндов до вскрытия — кэш и турнир неотличимы:
тот же порядок хода по часовой от кнопки, те же `fold / check / call / bet /
raise / all-in`, тот же min-raise, те же правила закрытия круга торговли,
те же сайд-поты при all-in. Short Deck меняет колоду и силу комбинаций — но
это уже спрятано за `Variant` из задачи 2 и на порядок ходов не влияет вообще.

Различаются вещи **вокруг** раздачи:

| Вопрос | Кэш | Турнир |
|---|---|---|
| Откуда фишки | бай-ин из кошелька | стартовый стек, докупок нет |
| Проигрыш стека | предложение докупиться | вылет |
| Блайнды | постоянные, из шаблона | растут по уровням |
| Уход из-за стола | в любой момент, с фишками | невозможен |
| Комиссия | рейк с банка | бай-ин при регистрации |
| Состав стола | кто пришёл, тот и сел | балансировка столов |

### Как это отражается в коде

**`Engine.HandSetup` — вход раздачи.** Чистая структура, не знающая ни про
кэш, ни про турниры:

```elixir
%Engine.HandSetup{
  variant:      module(),      # Variant.TexasHoldem и т.д. (задача 2)
  players:      [%{seat: seat, id: id, stack: chips}],
  button_seat:  seat,
  small_blind:  chips,
  big_blind:    chips,
  ante:         chips,
  ante_type:    :big_blind | :per_player
}
```

Блайнды приходят **числами**, а не ссылкой на `CashGameSetting`. Кэш берёт их
из шаблона, турнир — из текущего уровня структуры; движку раздачи это
безразлично, и именно поэтому он одинаков для обоих.

**`Engine.Rules.apply_action(state, action)` (задача 4)** — единственное место,
где живут порядок хода и легальность решений. Ни `CashGameSetting`, ни кошельки,
ни `Repo` в него не приходят. Проверяемое следствие: модуль раздачи не должен
компилироваться со ссылкой ни на один модуль контекста `CashGames` — это ловится
архитектурным тестом наравне с §11 CLAUDE.md.

**`GameMode` behaviour — то, что различается.** Политика *между* раздачами:

```elixir
@callback hand_setup(room_state) :: {:ok, HandSetup.t()} | {:error, :not_enough_players}
@callback on_hand_finished(room_state, results) :: room_state
@callback on_zero_stack(room_state, player) :: room_state
@callback can_leave?(room_state, player) :: boolean()
```

В этой задаче реализуется один модуль — `GameMode.Cash`: бай-ин из кошелька,
докупка, предложение ребая, свободный уход, рейк. `GameMode.Tournament`
не пишется и не проектируется в деталях — от него нужно ровно то, что таблица
выше уже перечислила: он обязан уметь подставить свои блайнды, запретить уход
и превратить нулевой стек в вылет, ничего не меняя в раздаче.

**`TableServer` остаётся один.** Он владеет состоянием комнаты и вызывает
`GameMode` там, где начинается политика, и `Engine.Rules` там, где идёт
раздача. Заводить отдельный процесс под турнирный стол не нужно — отличается
поведение, а не топология.

### Чего это стоит сейчас

Почти ничего: одна структура (`HandSetup`), одно behaviour из четырёх коллбэков
и дисциплина «блайнды передаются числом». Плата за отсутствие этого шва —
турнир, который позже придётся встраивать в код, где `TableServer` напрямую
читает `CashGameSetting`, а «проиграл стек» жёстко означает «предложить
докупиться».

## 11. Тесты

**Уровень 2 (процессы, без БД):**

* нулевой стек: игрок уходит в `sitting_out`, по истечении `rebuy_prompt_ms`
  освобождает место; докупка внутри окна возвращает его в игру;
* инвариант пула: заполнение последней комнаты порождает новую;
  опустевшая лишняя закрывается; последняя свободная не закрывается никогда;
* выключение шаблона: новые комнаты не создаются, существующие уходят
  в `:draining`;
* два одновременных `join_seat` на одно место: ровно один успех,
  второму — `seat_taken`;
* реконнект внутри grace-периода возвращает игрока на место;
* по истечении grace-периода место освобождается (часы инжектируются,
  `Process.sleep` запрещён — §10 CLAUDE.md);
* падение комнаты не задевает другие комнаты того же шаблона;
* розыгрыш кнопки (§5): с фиксированным seed кнопка достаётся ожидаемому месту;
  при равных рангах решает масть; событие `button_draw` содержит карты всех
  участников и назначенное место;
* раздача не стартует раньше `button_draw_animation_ms` — таймер прогоняется
  вручную через инжектируемые часы;
* повторный сбор игроков после простоя запускает розыгрыш заново,
  а между обычными раздачами кнопка просто сдвигается по часовой;
* севший игрок по умолчанию в `waiting_for_bb` и карт не получает, пока
  очередь большого блайнда не дойдёт до его места;
* вход за post между кнопкой и большим блайндом делает взнос **мёртвым**:
  сумма в банке, права чека нет;
* сев на большой блайнд или сразу за него — вступление немедленное;
  на Heads-Up ожидания нет вовсе;
* повторная посадка в ту же комнату внутри `blind_dodge_window_hands`
  не даёт права ждать блайнда — только post;
* `missed_blinds` копятся в `sitting_out` и при отключении, и вернувшийся
  игрок либо гасит их, либо ждёт своего блайнда;
* при `allow_post_blind: false` вход за post невозможен ни при каких условиях.

**Уровень 3 (БД, Sandbox):**

* бай-ин создаёт ровно одну запись ledger; повтор с тем же ключом — ноль новых;
* неуспешный бай-ин (нет денег) не оставляет ни резерва места, ни записи;
* `leave_seat` возвращает **ровно** стек, а не сумму бай-ина;
* валидация шаблона: `big_blind <= small_blind` отвергается, `max_players = 10`
  отвергается.

**Уровень 4 (каналы насквозь, `async: false`):**

* два сокета садятся в одну комнату, оба видят обновление лобби;
* игрок, севший последним, вызывает появление новой комнаты в лобби
  у **всех** подписчиков;
* попытка сесть с чужим `user_id` в payload игнорируется — источник истины
  `socket.assigns` (§5 CLAUDE.md).

**Инвариант денег** — отдельным тестом на каждом сценарии §4.

## 12. Решённое и открытые вопросы

**Зафиксировано:**

* таблица — **`cash_game_settings`**; §6 CLAUDE.md правится под неё;
* **мультитейблинг разрешён** — игрок может сидеть за сколькими угодно
  комнатами; в пределах одной комнаты у него ровно одно место;
* **рейк на `play_money` не берётся**; поля рейка в шаблоне есть, но при
  `currency: :play_money` игнорируются; значения капов задаёт оператор,
  дефолтов в коде нет;
* шаблоны правятся **напрямую в БД**; первичное наполнение — командой
  `mix cash_game.seed` из `priv/cash_games/grid.exs` (§6);
* сетка — **72 шаблона**: 12 уровней реальных денег (NL2…NL5000) и 6 уровней
  play money (NL1000…NL100000), каждый в четырёх форматах — 6-max, 6-max Ante,
  9-max, Heads-Up (§6);
* поднимаем **обе валюты** сразу: `main` и `play_money`;
* `Lobby.reload/0` — по таймеру **раз в минуту**;
* при старте ноды **сразу** поднимается по одной пустой комнате на каждый
  включённый шаблон;
* `max_rooms` — **100** на шаблон по умолчанию;
* при нулевом стеке — **предложение докупиться с таймером** `rebuy_prompt_ms`,
  игрок на это время в `sitting_out`; по истечении встаёт из-за стола;
* `add_chips` разрешён **в любой момент между раздачами**, до `max_buy_in`;
* **быстрый вход** — `quick_seat` по `setting_id` (лимиту), не по комнате;
  на Heads-Up приоритет отдаётся комнате, где уже кто-то ждёт соперника;
* анте — тип `big_blind`, сумма **`big_blind / 2`**;
* лобби показывает **все** включённые шаблоны, включая пустые;
* сид проставляет **нулевой рейк**; значения задаются в БД, а `Lobby` при
  старте предупреждает о `main`-шаблонах с нулём;
* раздача проектируется **универсальной** — общий код для кэша, турниров
  и любых вариантов; различия вынесены в `GameMode` behaviour (§9);
* при старте игры за столом кнопка **разыгрывается открытой сдачей по карте**
  (§5); тайбрейк по масти `♠ > ♥ > ♦ > ♣`, пересдачи нет;
* севший игрок **ждёт большого блайнда** либо входит немедленно за post
  с мёртвым взносом (§6); пропущенные блайнды учитываются, повторная посадка
  внутри окна `blind_dodge_window_hands` — только через post.
