# Клиент. Задача 1. Аккаунт, токены, кошельки

Документ для разработчика Electron-клиента. Описывает **всё, что сервер умеет
на текущий момент**: регистрация, вход, продление токена, открытие WebSocket
и балансы кошельков. Игровых точек (лобби, столы, ставки) ещё нет — они
появятся в следующих задачах.

Читать вместе с §5 `CLAUDE.md` (транспорт и протокол).

---

## 1. Общая картина

Сервер — **server-authoritative**. Клиент это тонкий рендерер и источник
намерений: он не вычисляет игровое состояние и не хранит ничего, что сервер
может посчитать сам.

HTTP используется ровно в трёх местах — там, где сокета физически не может
быть (соединения ещё нет либо токен уже протух). Всё остальное, начиная
со следующей задачи, идёт по WebSocket.

```
1. POST /api/auth/register  или  POST /api/auth/login
        │
        ├── token          → открыть WebSocket
        └── refresh_token  → сохранить, обновлять по нему пару токенов
                                    │
2.  ws://host/socket/websocket?token=<token>
        │
        └── дальше вся игра — сообщениями канала (задача 2+)
```

**База (dev):** `http://localhost:4000`, WebSocket — `ws://localhost:4000/socket`.

---

## 2. Общие правила

* Все запросы и ответы — JSON, `Content-Type: application/json`.
* **Все денежные суммы — целые числа в минимальных единицах** (фишки/центы).
  Никаких дробных. `10000` для `play_money` — это ровно 10 000 фишек.
* `id` — UUID-строка.
* Ошибка **всегда** имеет одинаковую форму (см. §4). Ветвиться нужно по полю
  `code`, а не по `message` и не по HTTP-статусу: `message` — текст для
  показа, статус — транспортная деталь.
* Лишние поля в теле запроса сервер игнорирует, недостающие — отвергает
  кодом `validation_failed`.

## 3. HTTP-точки

### 3.1 `POST /api/auth/register`

Регистрация. Создаёт игрока и оба его кошелька одной транзакцией и **сразу**
возвращает готовую сессию — отдельный вход после регистрации не нужен.

Запрос:

```json
{
  "name": "Player_1",
  "email": "player@example.com",
  "password": "correct horse battery"
}
```

Ответ `201 Created`:

```json
{
  "token": "SFMyNTY.g2gDbQAAACQ...",
  "refresh_token": "0Y7Xk2m...",
  "expires_in": 3600,
  "user": {
    "id": "6f1c6f4e-...",
    "name": "Player_1",
    "email": "player@example.com",
    "avatar": "/users/avatars/default.png"
  },
  "wallets": [
    { "type": "main",       "amount": 0 },
    { "type": "play_money", "amount": 10000 }
  ]
}
```

**Правила полей.** Валидируются на сервере; продублируй их в UI ради мгновенной
подсказки, но своей проверкой не считай ответ сервера предсказуемым.

| Поле | Правило |
|---|---|
| `name` | 3–25 символов, только `A-Z a-z 0-9 _ -`. **Регистрозависим**: `Player` и `player` — разные игроки, оба могут существовать одновременно |
| `email` | ≤ 160 символов, обычный формат. **Нормализуется в нижний регистр**: `A@X.IO` и `a@x.io` — один и тот же адрес, зарегистрировать оба нельзя. В ответе email придёт уже в нижнем регистре — показывай то, что пришло, а не то, что ввели |
| `password` | 8–72 **байта**. Верхняя граница — предел входной строки Argon2, а не каприз. Осторожно с кириллицей и эмодзи: там байтов больше, чем символов |

Ошибки: `validation_failed` (422), `rate_limited` (429).

### 3.2 `POST /api/auth/login`

Вход **только по email и паролю**. Ник для входа не используется.

```json
{ "email": "player@example.com", "password": "correct horse battery" }
```

Ответ `200 OK` — тело идентично ответу регистрации (§3.1), включая актуальные
балансы кошельков.

Email сравнивается без учёта регистра: пользователь может ввести его как угодно.

Ошибки: `invalid_credentials` (401), `user_blocked` (403),
`validation_failed` (422, если поля не переданы), `rate_limited` (429).

> `invalid_credentials` приходит и на неизвестный email, и на неверный пароль —
> это намеренно. Не показывай «такого пользователя нет»: сервер эту информацию
> не раскрывает, и клиент не должен её домысливать.

### 3.3 `POST /api/auth/refresh`

Продление сессии без разрыва сокета.

```json
{ "refresh_token": "0Y7Xk2m..." }
```

Ответ `200 OK` — снова полное тело сессии: **новый** `token` и **новый**
`refresh_token`.

**Ротация — обязательное правило.** Каждый успешный refresh отзывает
предъявленный токен и выдаёт новый. Старый мгновенно перестаёт работать.
Клиент обязан немедленно заменить сохранённый `refresh_token` на пришедший,
иначе следующее продление провалится.

**Повторное предъявление уже отозванного токена трактуется как компрометация:**
сервер отзывает *всю цепочку* токенов пользователя и отвечает `token_reused`.
Практический вывод: гонки недопустимы — не запускай два refresh параллельно.
Держи одну общую in-flight-промису, остальные вызовы ждут её результата.

Ошибки: `token_invalid` (401), `token_expired` (401), `token_reused` (401),
`user_blocked` (403), `validation_failed` (422), `rate_limited` (429).

Реакция на все токенные ошибки одна: **разлогинить, стереть сохранённые токены,
показать экран входа**. Восстанавливать сессию уже нечем.

### 3.4 `GET /health`

Проверка доступности сервера, аутентификации не требует.

```json
{ "status": "ok", "version": "0.1.0" }
```

Годится для экрана «сервер недоступен» и для выбора момента повторной попытки.

## 4. Ошибки

Единый формат для HTTP и для отказа в handshake (§6.2):

```json
{ "code": "invalid_credentials", "message": "Неверный email или пароль" }
```

У `validation_failed` добавляется разбор по полям:

```json
{
  "code": "validation_failed",
  "message": "Данные не прошли валидацию",
  "errors": {
    "name": ["should be at least 3 character(s)"],
    "email": ["has already been taken"]
  }
}
```

`errors` — карта «поле → список сообщений». Она нужна, чтобы понять, **какое
поле** подсветить. Тексты частично приходят от Ecto по-английски, поэтому свои
формулировки подставляй по имени поля, а не показывай пришедшую строку.

Полный список кодов, который может увидеть клиент на этом этапе:

| `code` | HTTP | Когда | Что делать клиенту |
|---|---|---|---|
| `validation_failed` | 422 | данные формы не прошли проверку | подсветить поля из `errors` |
| `invalid_credentials` | 401 | неверный email или пароль | остаться на форме входа, общая ошибка |
| `user_blocked` | 403 | учётка заблокирована | экран «аккаунт заблокирован», не ретраить |
| `token_invalid` | 401 | токен не наш или испорчен | разлогинить |
| `token_expired` | 401 | токен просрочен | попробовать refresh, при неудаче — разлогинить |
| `token_reused` | 401 | предъявлен отозванный refresh | разлогинить, стереть токены |
| `rate_limited` | 429 | превышен лимит попыток | «попробуйте позже», прекратить ретраи |
| `unsupported_protocol_version` | 426 | версия протокола клиента не поддерживается | предложить обновление приложения |
| `not_found` | 404 | ресурса нет | — |

Коды — закрытый список на сервере (`BlockPoker.ErrorCode`). Незнакомый код
считай фатальным и логируй, но не падай.

## 5. Ограничение частоты запросов

Действует по IP, скользящим окном:

| Точки | Лимит |
|---|---|
| `/api/auth/register` + `/api/auth/login` (**общий счётчик**) | 10 запросов за 5 минут |
| `/api/auth/refresh` | 30 запросов за 5 минут |

Превышение — `429` с кодом `rate_limited`. Учитывай общий счётчик: сценарий
«не смог войти → пошёл регистрироваться» тратит попытки из одного запаса.

Отсюда требование к клиенту: **никакого автоматического повторения запроса
в цикле**. Ретрай — только по явному действию пользователя либо с
экспоненциальной задержкой.

## 6. WebSocket

### 6.1 Подключение

```
ws://localhost:4000/socket/websocket?token=<token>&protocol_vsn=1
```

С `phoenix.js`:

```js
import { Socket } from "phoenix"

const socket = new Socket("ws://localhost:4000/socket", {
  params: { token, protocol_vsn: "1" }
})

socket.connect()
```

* `token` — тот самый `token` из ответа `/register`, `/login` или `/refresh`.
  **Не** `refresh_token`.
* `protocol_vsn` — версия прикладного протокола, сейчас `"1"`. Параметр
  необязателен (без него сервер считает версию текущей), но передавать его
  стоит: при смене протокола клиент получит внятный отказ вместо странного
  поведения. Имя именно `protocol_vsn` — короткое `vsn` занято самим Phoenix
  под версию его wire-формата, перетирать его нельзя.
* `user_id` в параметрах и в сообщениях сервер **игнорирует**. Личность
  определяется исключительно токеном.

### 6.2 Отказ в подключении

Отказ происходит на этапе HTTP-upgrade — WebSocket не открывается вовсе.
Сервер отвечает статусом из таблицы §4 и телом `{"code": ..., "message": ...}`.

Ожидаемые коды: `token_invalid`, `token_expired`, `user_blocked`,
`unsupported_protocol_version`.

Важная особенность: `phoenix.js` не отдаёт тело неудавшегося upgrade в
`onError` — он видит только факт обрыва и уходит в переподключение. Поэтому:

* **не оставляй слепой автореконнект** на этапе аутентификации, либо
* при `onError` / `onClose` до первого успешного `onOpen` сходи обычным `fetch`
  на `/health` и `/api/auth/refresh`, чтобы отличить протухший токен (обновить
  и переподключиться) от устаревшего клиента (предложить обновление).

Рекомендуемая стратегия: держать `token` заведомо свежим — обновлять его по
`refresh` **до** истечения `expires_in`, а не по факту отказа.

### 6.3 Жизненный цикл токенов

* `token` живёт **1 час** (`expires_in: 3600`; бери значение из ответа, не
  хардкодь).
* Уже открытое соединение при истечении токена **не рвётся**: проверка
  происходит один раз, при подключении. Но следующее подключение — после
  реконнекта, сна ноутбука, смены сети — потребует свежий токен.
* `refresh_token` живёт **30 дней** и ротируется при каждом использовании.

Практическая схема для Electron:

1. `refresh_token` — в защищённое хранилище ОС (`safeStorage`/keytar),
   не в `localStorage` рендерера.
2. `token` — только в памяти main-процесса.
3. Таймер обновления на `expires_in - 5 минут`.
4. Сетевые вызовы — из main-процесса через IPC, чтобы токены не жили
   в рендерере вообще.

### 6.4 Каналы

**Каналов пока нет.** `lobby`, `table:<id>` и `wallet:<user_id>` появятся
в следующих задачах. Сейчас соединение можно только открыть — это и есть
проверка, что аутентификация работает насквозь.

## 7. Кошельки

У игрока ровно два кошелька, создаются при регистрации:

| `type` | Стартовая сумма | Смысл |
|---|---|---|
| `main` | `0` | реальный баланс |
| `play_money` | `10000` | игровые фишки |

Балансы приезжают в ответе `/register`, `/login` и `/refresh`. Отдельной ручки
для них нет: по мере появления игровых операций баланс начнёт приходить пушем
по сокету.

Клиент **никогда** не пересчитывает баланс сам — не вычитает бай-ин, не
прибавляет выигрыш. Показывается ровно то число, которое прислал сервер. Любое
расхождение — баг сервера, и его надо видеть, а не маскировать клиентской
арифметикой.

---

## 8. Чего на сервере ещё нет

Не закладывайся и не имитируй заглушками:

* восстановление пароля, подтверждение email, 2FA;
* загрузка аватара — `avatar` это просто строка-путь, всегда дефолтная;
* пополнение и вывод, любые операции с балансом (`buy_in` / `cash_out`);
* лобби, столы, любые игровые сообщения;
* выписка по кошельку для UI: журнал операций на сервере ведётся с первого дня,
  но наружу пока не отдаётся;
* серверный `logout`: ручки отзыва токенов нет. Локальный выход — просто стереть
  сохранённые токены.

## 9. Минимальный чек-лист приёмки клиента

1. Регистрация с валидными данными → показан профиль и два баланса (0 и 10 000).
2. Регистрация с занятым ником → подсвечено поле `name`, форма не сброшена.
3. Ник из 2 символов и ник с кириллицей → отклонены до отправки, а при отправке
   корректно обработан `validation_failed`.
4. Вход с неверным паролем → общее сообщение, без намёка на существование email.
5. 11 неудачных входов подряд → «попробуйте позже», ретраи прекращены.
6. После входа WebSocket открывается и держится.
7. Токен принудительно испорчен → соединение не открывается, клиент уходит на
   экран входа, а не в бесконечный реконнект.
8. `refresh` вызван дважды с одним и тем же `refresh_token` → второй раз
   `token_reused`, клиент разлогинен и токены стёрты.
9. Приложение перезапущено → сессия восстановлена по сохранённому
   `refresh_token` без ввода пароля.
10. Сервер выключен → экран «сервер недоступен» по `/health`, а не зависание.
