# Задача 2. Правила покера: калькулятор комбинаций, победителя и эквити

Чистое ядро `lib/block_poker/engine/`. Ни процессов, ни Ecto, ни Phoenix,
ни `send/2` (§3 CLAUDE.md). Всё — детерминированные функции над структурами,
тесты уровня 1: мгновенные, `async: true`, без БД.

Ставки, поты, улицы и порядок хода — **не** эта задача. Здесь только «что сильнее»,
«кто выиграл» и «сколько процентов».

---

## 1. Цель

* Оценка любой покерной руки → сравнимое значение.
* Определение победителей на вскрытии (с учётом ничьих и hi-lo сплитов).
* Расчёт эквити между N игроками в момент all-in + список аутов для каждого.
* **Главное:** архитектура, в которой добавление нового вида покера — это
  один новый модуль, реализующий behaviour, и ноль изменений в остальном коде.

**Реализуем в этой задаче только Texas Hold'em.** Omaha, Short Deck, Omaha Hi-Lo
и китайский покер — не пишем; behaviour проектируется так, чтобы каждый из них
добавлялся одним модулем без правок существующего кода (§4, §9).

---

## 2. Базовые типы

### `Engine.Card`

Карта — не структура, а **целое число 0..51** (`rank * 4 + suit`). Причина
прямая: калькулятор эквити прогоняет миллионы комбинаций, и структура на каждую
карту — это миллионы аллокаций и работа GC вместо арифметики. Структуры остаются
на границе: парсинг и вывод.

```elixir
@type t :: 0..51                       # внутреннее представление
@spec rank(t) :: 0..12                 # 0 = двойка, 12 = туз
@spec suit(t) :: 0..3
```

Ранги внутри нумеруются от младшего к старшему (0 = двойка), чтобы сравнение
было обычным `>` без таблиц перевода.

**Внешнее представление** (протокол, тесты, логи разбора) — объект:

```json
{ "rank": 14, "suit": "S" }
```

* `rank` — число **2..14**, как его называет игрок: `2`…`10`, валет `11`,
  дама `12`, король `13`, туз `14`. Внутреннее 0..12 наружу не протекает:
  смещение — деталь оптимизации, а не часть контракта.
* `suit` — заглавная буква: `"S"` (пики), `"H"` (черви), `"D"` (бубны),
  `"C"` (трефы).

```elixir
@spec from_map(map()) :: {:ok, t} | {:error, :invalid_card}
@spec to_map(t) :: %{rank: 2..14, suit: String.t()}
```

Конвертация живёт **только** на границе. Внутри калькулятора карта — число,
иначе миллионы map'ов на каждый расчёт эквити.

### `Engine.Deck`

```elixir
@spec new(Variant.t()) :: [Card.t]     # состав колоды задаёт вариант
@spec shuffle([Card.t], rng) :: [Card.t]
```

Тасовка — Fisher–Yates на `:crypto.strong_rand_bytes/1`; `:rand` для карт
запрещён (§9 CLAUDE.md). RNG передаётся **аргументом** (behaviour + Mox),
чтобы раздача воспроизводилась по seed в тестах.

### `Engine.CardSet`

Набор карт — 52-битная маска в одном integer. Даёт O(1) операции, которые
в калькуляторе выполняются в самом горячем цикле: «карта уже занята?»
(`band`), «убрать известные карты из колоды» (`bxor`), «объединить руку с бордом»
(`bor`). Список карт для этого пришлось бы обходить каждый раз.

## 3. Оценка комбинации

### Представление силы руки

```elixir
%Engine.HandRank{
  score:    non_neg_integer(),   # единственное, по чему сравнивают
  category: atom(),              # :flush, :full_house — только для отображения
  cards:    [Card.t]             # пять карт, составивших комбинацию
}
```

Сравнение — целочисленное `>=` по `score`. Равные `score` = **точная** ничья.

Почему число, а не кортеж `{категория, кикеры}`: порядок категорий зависит
от варианта. В Short Deck флеш сильнее фулл-хауса, а в hi-lo младшая рука
считается по перевёрнутой шкале. Если ordering зашит в форму кортежа, каждый
такой вариант ломает сравнение и требует ветвления в местах сравнения. Когда
ordering вшивается в число **вариантом при оценке**, сравнение остаётся одной
операцией и не знает про правила вовсе.

`score` собирается как `категория * 2^20 + тайбрейкеры` — категория берётся из
таблицы **конкретного варианта**, тайбрейкеры кодируются рангами по 4 бита.

### Ядро оценки

```elixir
@spec best_of_five([Card.t]) :: HandRank.t          # ровно 5 карт
@spec best_hand([Card.t], category_order) :: HandRank.t   # 5..7 карт, перебор C(n,5)
```

`best_of_five/1` не знает ни про борд, ни про карманные карты, ни про количество
игроков — на входе просто пять карт. Это принципиально: китайский покер
раскладывает 13 карт на три ряда без борда вообще, и если примитив оценки
завязан на «hole + board», такой вариант в архитектуру не влезает.

Реализация: сначала наивный перебор `C(7,5) = 21` комбинаций — корректность
важнее скорости. После того как тесты зафиксируют поведение, ускоряем
lookup-таблицами, генерируемыми на этапе компиляции; тесты при этом не меняются
и служат гарантией эквивалентности.

## 4. Абстракция варианта — ключевая часть задачи

```elixir
defmodule BlockPoker.Engine.Variant do
  @callback id() :: atom()
  @callback deck() :: [Card.t]
  @callback hole_cards_count() :: pos_integer()
  @callback board_size() :: non_neg_integer()

  # Как из карт игрока и борда собираются кандидаты на пятёрку.
  # Hold'em: любые 5 из 7. Omaha: ровно 2 из руки + ровно 3 с борда.
  @callback candidate_hands(hole :: [Card.t], board :: [Card.t]) :: [[Card.t]]

  # Порядок силы категорий именно этого варианта.
  # Short Deck: флеш выше фулл-хауса.
  @callback category_order() :: [atom()]

  # Считается ли A-6-7-8-9 стритом (Short Deck), A-2-3-4-5 (везде).
  @callback straight_sequences() :: [[0..12]]

  # Делится ли банк, и по какой второй шкале.
  @callback pot_split() :: :high | {:hi_lo, low_evaluator :: module()}
end
```

Всё, что отличает один вид покера от другого, живёт **за этим behaviour**.
Ни `Showdown`, ни `Equity`, ни `HandRank` не содержат `case` по типу игры —
это прямое следствие §3 CLAUDE.md («ветвление по правилам игры вне engine
запрещено»), продолженное внутрь самого engine: ветвление по *виду* игры
допустимо ровно в одном месте — при выборе модуля варианта.

Реализация задачи — единственный модуль `Variant.TexasHoldem`.
Требования, которые остальные варианты предъявляют к behaviour, — §9.

**Критерий приёмки архитектуры:** добавление нового варианта не меняет ни одного
существующего файла, кроме реестра вариантов. Проверяется искусственным
вариантом в `test/support` (§9) — `Showdown` и `Equity` работают с ним,
ничего о нём не зная.

## 5. Определение победителя

```elixir
@spec showdown([{player_id, [Card.t]}], board :: [Card.t], Variant.t()) ::
        [%{player_id: id, rank: HandRank.t, place: pos_integer()}]
```

Возвращает игроков, сгруппированных по силе: одинаковый `place` = абсолютная
ничья, банк делится. Для `{:hi_lo, _}` — две независимые ранжировки (high и low),
где low может не квалифицироваться ни у кого.

**Границы:** сайд-поты и раздача фишек — **не здесь**. `Showdown` отвечает
на вопрос «кто сильнее», `Engine.Pot` (следующая задача) — «кому сколько».
Смешивать нельзя: правила сравнения от вариантов зависят, правила деления
банка — нет.

## 6. Эквити

```elixir
@spec equity([hand_spec], board :: [Card.t], Variant.t(), opts) :: EquityResult.t()

# hand_spec — известные карты игрока, либо :unknown
# opts: :mode (:exact | :monte_carlo | :auto), :iterations, :rng, :dead_cards
```

Результат:

```elixir
%EquityResult{
  players: [%{id: id, win: float, tie: float, equity: float, outs: [Out.t]}],
  simulations: pos_integer(),
  mode: :exact | :monte_carlo
}
```

`equity` = `win + tie / (число делящих)` — доля банка, а не только доля побед.

### Когда считается

Ровно один сценарий: **торговля завершена, оставшиеся игроки в all-in, карты
вскрыты и идёт раздача борда**. Пока кто-то ещё принимает решения, эквити
не считается и не показывается — иначе проценты раскрывают силу рук игрокам,
которые ещё не сходили.

Из этого следует важное для реализации: **все руки в расчёте известны**.
`hand_spec` со значением `:unknown` в продакшене не встречается — он остаётся
в API ради тестов и будущего разбора истории, но оптимизировать под него
не нужно.

Само правило «когда показывать» — не дело калькулятора: он чистая функция
и вызывается тем, кто владеет состоянием стола (`TableServer`, следующие
задачи). Здесь оно записано, потому что определяет, какие входы вообще
реалистичны.

### Точный перебор vs Монте-Карло

Число неизвестных карт борда решает всё:

| Улица | Неизвестных | Комбинаций (Hold'em, 2 игрока) | Режим |
|---|---|---|---|
| Ривер | 0 | 1 | точно |
| Тёрн | 1 | 44 | точно |
| Флоп | 2 | 990 | точно |
| Префлоп | 5 | ~1.7 млн | Монте-Карло |

Правило `:auto` — точный перебор, пока пространство ≤ порога (порядка 200 000
раскладов), иначе Монте-Карло с фиксированным числом итераций. **All-in
на флопе и тёрне считается точно**, приблизительных чисел игрок там не увидит.

**Префлоп-all-in — единственный тяжёлый случай, и он частый.** `C(48,5)` ≈
1.7 млн раскладов, на каждом — оценка руки каждого игрока. С наивным перебором
`C(7,5)` это ~70 млн оценок на двух игроков, что на порядки выше бюджета
из §8. Поэтому на префлопе `:auto` уходит в Монте-Карло: 100 000 итераций
дают погрешность порядка ±0.15 п.п. — при отображении с точностью до целого
процента это невидимо. Точный режим для префлопа остаётся доступен явным
`mode: :exact` (тесты, разбор), но в игровом пути не используется.

Если после lookup-таблиц (§8) точный префлоп уложится в бюджет — порог
`:auto` просто поднимается, и больше ничего менять не нужно.

Монте-Карло: RNG передаётся аргументом, тот же seed → тот же результат.
Недетерминированного теста в проекте быть не должно (§10).

### Мёртвые карты

**Сброшенные карты в расчёт не берутся** — ушли в пас и остаются в колоде
как обычные неизвестные. Никакого специального учёта фолдов калькулятор
не делает: на входе только карты живых игроков и борд.

Параметр `:dead_cards` в API оставляем (карты, гарантированно не выходящие —
засвеченные, изъятые), по умолчанию пустой. Добавить его в сигнатуру сейчас
ничего не стоит, а дописывать позже — менять все вызовы.

## 7. Ауты

```elixir
%Engine.Out{
  rank: 2..14,             # внешняя шкала: 14 = туз
  cards: [Card.t],         # конкретные карты этого ранга, дающие улучшение
  count: pos_integer()     # длина cards — то самое «3 туза»
}
```

Определение, которое реализуем:

> Аут игрока P — неизвестная карта, которая, придя **следующей** картой борда,
> переводит P из «не лидирует» в «лидирует или делит банк» против текущих
> известных рук оппонентов.

Тонкости, зафиксированные явно:

* Ауты считаются **на одну карту вперёд** — иначе «3 туза» перестаёт быть
  списком карт и становится комбинацией из двух улиц.
* Ауты считаются **только для игроков с известными картами**. Против `:unknown`
  оппонента понятие лидерства не определено.
* На ривере аутов нет ни у кого — карт больше не будет.
* Карта считается аутом и тогда, когда она даёт **сплит** из проигрыша.
  Половина банка — тоже улучшение.
* Группировка по рангу (`3 туза`, `3 короля`) — представление; вычисляется
  из списка конкретных карт, а не наоборот.

«Анти-ауты» (карты, отбирающие лидерство у лидера) **не реализуем** — у лидера
список аутов пустой.

## 8. Производительность

Это единственная часть ядра, где скорость — требование, а не пожелание:
эквити считается в момент all-in, при живых игроках, ожидающих анимацию.

* Бюджет: **эквити на флопе для двух известных рук — < 50 мс**; для 9 игроков
  на флопе — < 300 мс.
* Бенчмарк (`benchee`, задача `mix bench`) — часть задачи, не факультатив:
  без него оптимизация превращается в угадывание.
* Оптимизации по порядку: битовые маски вместо списков → lookup-таблица
  для 5-карточной оценки → отсечение заведомо проигранных ветвей.
  Каждый шаг — только после того, как бенчмарк показал, что он нужен.
* Параллелизм (`Task.async_stream` по чанкам симуляций) — на усмотрение,
  но чистота функций от этого не меняется: RNG на чанк порождается
  детерминированно из общего seed.

## 9. Что готовим, но не реализуем

Код этих вариантов не пишется. Они существуют в задаче как **список требований
к behaviour**: если абстракция спроектирована так, что любой из них потребует
правки общего кода — абстракция неверна, и это видно уже сейчас, а не через
полгода.

| Вариант | Что ломает наивную архитектуру |
|---|---|
| **Omaha** | ровно 2 из 4 карманных + ровно 3 с борда — `candidate_hands` |
| **Omaha Hi-Lo** | два победителя на банк, low «8 или лучше», может не быть |
| **Short Deck** | колода 36 карт, флеш > фулл-хауса, `A6789` — стрит |
| **Китайский покер** | борда нет вообще; 13 карт, три ряда, роялти, фолы |

Первые три ложатся в behaviour §4 целиком. **Китайский покер — нет**: у него
нет ни борда, ни улиц, ни единой пятёрки, а есть попарное сравнение рядов
и своя система очков вместо банка. Его вклад в эту задачу — одно требование:
`best_of_five/1` и `HandRank` не должны ничего знать про борд и карманные карты,
чтобы позже переиспользоваться как есть. Собственный слой сравнения рядов
и подсчёта очков — отдельная задача, когда до неё дойдёт продукт.

Проверка абстракции без реализации вариантов — **искусственный вариант
в `test/support`**: колода нестандартного состава и переставленный порядок
категорий. Он проходит через `Showdown` и `Equity` без единой правки в `lib`.
Это дешевле полноценной Omaha и ловит ровно то же: не протекли ли допущения
Hold'em в общий код.

## 10. Тесты

Уровень 1 целиком: без БД, без процессов, `async: true`, мгновенно.

**Unit:**

* каждая категория комбинации распознаётся; граничные случаи — стрит от туза
  вниз (`A2345`), стрит-флеш против флеша, две пары против сета, кикеры;
* эталонные наборы рук с заранее известным порядком силы;
* `showdown` при полной ничьей возвращает одинаковый `place`;
* известные сценарии эквити сверяются с опубликованными числами
  (AA vs KK ≈ 81/19 префлоп, классические флоп-дро) с допуском.

**Property (`StreamData`) — инварианты, которые ломаются именно на частных случаях:**

* сравнение рук **тотально и транзитивно**: для случайных троек рук
  порядок непротиворечив;
* оценка не зависит от порядка карт на входе (перестановка → тот же `score`);
* `best_hand` из 7 карт всегда `>=` любой из 21 своей пятёрки;
* сумма эквити всех игроков = 1.0 (с плавающей погрешностью);
* эквити не зависит от порядка игроков в списке;
* каждый аут действительно улучшает: подставив его в борд, `showdown`
  показывает лидерство — проверяется прямым прогоном, а не повтором
  той же формулы;
* точный режим и Монте-Карло на достаточном числе итераций сходятся
  в пределах доверительного интервала.

**Архитектурный тест:** искусственный вариант, объявленный в `test/support`,
проходит через `Showdown` и `Equity` без единого изменения в `lib`.

## 11. Зафиксированные решения

Постановка закрыта, открытых вопросов нет.

* Реализуем **только Texas Hold'em**. Omaha, Short Deck, Omaha Hi-Lo и китайский
  покер не пишем — они существуют как требования к behaviour (§9).
* Абстракция проверяется **искусственным вариантом** в `test/support`,
  а не реализацией настоящего второго вида покера.
* Карта наружу — `{"rank": 14, "suit": "S"}`, шкала рангов **2..14**
  (валет 11, дама 12, король 13, туз 14). Внутри — целое 0..51.
* Оценка — **наивный перебор `C(7,5)`**. Lookup-таблицы только после того,
  как бенчмарк покажет необходимость; тесты корректности при этом не меняются
  и становятся гарантией эквивалентности.
* Карты сфолдивших игроков **не учитываются** — остаются неизвестными картами
  колоды. Параметр `:dead_cards` в API есть, по умолчанию пуст.
* **Анти-ауты не реализуем**: у лидера список аутов пуст.
* Эквити считается **только при all-in**, когда торговля завершена и идёт
  раздача борда. Во время торгов не считается и не показывается.
  Следствие: все руки в расчёте известны, `:unknown` — только для тестов.
* Префлоп-all-in считается Монте-Карло (§6), флоп и тёрн — точно.

## 12. Состав работ

1. `Engine.Card`, `Engine.CardSet`, `Engine.Deck` + RNG behaviour.
