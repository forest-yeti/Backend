# Block Poker — Backend

Бэкенд покерного рума. Elixir/OTP + Phoenix Channels (WebSocket) + MySQL.
Клиент — Electron-приложение, общается с сервером почти исключительно по WebSocket.

Документ описывает **архитектуру и правила работы с кодом**. Бизнес-логика раздачи
(порядок улиц, сравнение комбинаций, сайд-поты) здесь намеренно не расписана —
она проектируется отдельно.

---

## 1. Принципы

1. **Server-authoritative.** Клиент — это тонкий рендерер и источник намерений.
   Любое действие игрока приходит как *запрос* (intent), сервер его валидирует
   и рассылает *результат*. Клиент никогда не вычисляет игровое состояние сам.
2. **Клиент не получает данных, которых не должен видеть.** Карты оппонентов,
   остаток колоды, seed RNG не покидают сервер до вскрытия. Фильтрация происходит
   при формировании персонального снапшота, а не на клиенте.
3. **Стол — это процесс.** Один активный стол = один `GenServer`, единственный
   владелец своего состояния. Никаких распределённых блокировок и гонок за строку в БД.
4. **MySQL — не игровой цикл.** БД хранит аккаунты, кошелёк, конфигурацию столов и
   историю раздач. Ход игры в БД не читается и не пишется по ходу улицы.
5. **Деньги ≠ игровое состояние.** Фишки на столе живут в процессе; движение денег
   между кошельком и столом — транзакционная запись в ledger (append-only).
6. **Функциональное ядро, императивная оболочка.** Правила покера — чистые функции
   над структурами, без процессов и I/O. Процессы только оркеструют.
7. **Транспорт тупой, ядро умное.** Вся бизнес-логика — в `lib/block_poker/*`.
   В `lib/socket/*` и `lib/api/*` её нет вообще: они парсят, вызывают контекст
   и сериализуют ответ. Подробности и критерии ревью — §3.

## 3. Структура проекта

Umbrella **не используем** — одно приложение, три верхнеуровневых слоя.
Приложение — `:block_poker`, корневой модуль — `BlockPoker`.

```
lib/
  block_poker.ex              # корневой модуль
  block_poker/                # ЯДРО (бизнес). Не знает про HTTP, сокеты и Phoenix.
    application.ex            # дерево супервизоров
    repo.ex
    error_code.ex             # единый список кодов ошибок для обоих транспортов

    accounts/                 # контекст: пользователи, токены
      accounts.ex             # публичный API контекста
      user.ex
      refresh_token.ex
    wallet/                   # контекст: баланс, ledger, buy-in / cash-out
      wallet.ex
      wallet_entry.ex         # запись ledger (append-only)
    engine/                   # ЧИСТОЕ ядро правил. Без процессов, без Ecto.
      card.ex
      deck.ex                 # колода, тасовка (принимает RNG-источник)
      hand_rank.ex            # оценка комбинации 5..7 карт
      betting.ex              # легальные действия, min-raise, all-in
      pot.ex                  # основной пот и сайд-поты
      table_state.ex          # структура состояния стола (данные)
      rules.ex                # apply_action(state, action) -> {:ok, state, events}
    tables/                   # ОБОЛОЧКА над engine: процессы столов
      tables.ex               # публичный API: list / join / leave / act
      table_server.ex         # GenServer: один стол
      table_supervisor.ex     # DynamicSupervisor
      table_registry.ex       # Registry (:via кортежи)
      table_config.ex
      seat.ex
      lobby.ex                # агрегированный список столов
    history/                  # контекст: сохранение сыгранных раздач
      history.ex
      hand_record.ex

  socket/                     # ТРАНСПОРТ: всё real-time. Основной канал связи.
    endpoint.ex               # Phoenix.Endpoint (обслуживает и socket, и api)
    user_socket.ex            # аутентификация соединения по токену
    presence.ex
    channels/
      lobby_channel.ex        # топик "lobby"
      table_channel.ex        # топик "table:<id>"
      wallet_channel.ex       # топик "wallet:<user_id>"
    views/
      table_view.ex           # state -> персональный снапшот для игрока
      lobby_view.ex
    protocol/
      message.ex              # разбор/валидация входящих payload
      version.ex              # согласование версии протокола

  api/                        # ТРАНСПОРТ: тонкий HTTP. Только то, что нельзя по сокету.
    router.ex
    controllers/
      auth_controller.ex      # register / login / refresh
      health_controller.ex
    plugs/
      rate_limit.ex

priv/repo/migrations/
test/
  block_poker/engine/         # property + unit тесты правил (быстрые, без БД)
  block_poker/tables/         # тесты процессов
  socket/                     # интеграционные тесты каналов
  api/
```

**Правило зависимостей**

```
socket ─┐
        ├──▶ block_poker ──▶ block_poker/engine
api ────┘
```

* `socket` и `api` **не знают друг о друге** и общаются с ядром только через
  публичные API контекстов (`Accounts`, `Wallet`, `Tables`, `History`).
* `block_poker` не знает ни про `socket`, ни про `api`: никаких `Phoenix.*`,
  никаких вызовов каналов. Наружу ядро говорит только через `Phoenix.PubSub`
  (broadcast события), а кто на них подписан — его не касается.
* `engine` не импортирует `BlockPoker.Repo`, не делает I/O и не вызывает `send/2`.
* Модули именуются по каталогам: `BlockPoker.*`, `Socket.*`, `Api.*`.
  `Socket` и `Api` — верхнеуровневые неймспейсы; при конфликте с зависимостью
  из hex переезжаем на `BlockPoker.Socket` / `BlockPoker.Api` без изменения структуры.

### Граница «транспорт / бизнес-логика» — жёсткое правило

**Вся бизнес-логика живёт в `lib/block_poker/*`. В `lib/socket/*` и `lib/api/*`
бизнес-логики нет вообще.** Это не рекомендация, а инвариант: если правило
нарушено — правится код, а не документ.

Транспортному слою разрешено ровно пять вещей:

1. Распарсить входящее сообщение / запрос и провалидировать его **форму**
   (поле есть, тип верный, число в границах `int`).
2. Достать `user_id` из `socket.assigns` / `conn.assigns` — то есть ответить
   на вопрос «кто это», но не «можно ли ему».
3. Вызвать **одну** публичную функцию контекста ядра.
4. Отрендерить результат или событие в JSON для конкретного получателя.
5. Смапить `{:error, code}` в ответ клиенту.

Всё остальное — в ядре. В частности, **в `socket/*` и `api/*` запрещено**:

* решать, чья сейчас очередь ходить, легально ли действие, хватает ли стека;
* считать суммы, поты, рейк, комиссии, минимальный рейз;
* обращаться к `Repo`, писать `Ecto.Query`, открывать транзакции;
* проверять права и владение («это его место?», «его ли кошелёк?») —
  авторизация действия принадлежит контексту, а не каналу;
* держать игровое состояние в `socket.assigns` — там только `user_id`,
  подписки и версия протокола;
* `case`/`cond` по доменным состояниям (`:preflop`, `:showdown`, ...) —
  ветвление по правилам игры вне `engine` запрещено;
* дублировать доменные константы (размеры блайндов, лимиты, тайминги).

Практический критерий при ревью: **если правило покера или денег изменилось,
файлы в `socket/*` и `api/*` меняться не должны.** Меняется только `block_poker/*`
(и `views/`, если поменялся набор полей на экране). Обратный критерий: канал,
из которого убрали Phoenix, должен читаться как список вызовов контекста.

Отдельно: `views/` в `socket/` — это транспорт, а не логика. Ему можно решать,
*какие* поля показать конкретному игроку (в т.ч. скрыть чужие карты), но нельзя
*вычислять* новые доменные значения. Если во view появилась арифметика над
фишками — значение должно приходить из `engine` уже посчитанным.

### Зачем нужен `api`, если есть сокет

Сокет — основной и почти единственный канал. HTTP оставлен только там, где
сокет физически не работает:

| Ручка | Почему не по сокету |
|---|---|
| `POST /api/auth/register` | соединения ещё нет |
| `POST /api/auth/login` | выдаёт токен, которым авторизуется само соединение |
| `POST /api/auth/refresh` | продление без разрыва сокета |
| `GET /health` | healthcheck деплоя и балансировщика |

**Правило:** любой новый эндпоинт в `api` требует обоснования, почему это не
сообщение канала. По умолчанию — всё новое идёт в `socket`. Игровая логика,
лобби, кошелёк и история через HTTP не доступны в принципе.

Альтернатива «анонимный сокет + сообщение `login`» отвергнута: она создаёт пул
неаутентифицированных соединений, который надо отдельно таймаутить и защищать
от флуда, — это дороже одного REST-эндпоинта.

## 4. Дерево процессов

```
BlockPoker.Supervisor (:one_for_one)
├── BlockPoker.Repo
├── Phoenix.PubSub
├── Socket.Presence
├── BlockPoker.Tables.Registry        (Registry, keys: :unique)
├── BlockPoker.Tables.TableSupervisor (DynamicSupervisor, :one_for_one)
│   └── BlockPoker.Tables.TableServer (по одному на активный стол)
├── BlockPoker.Tables.Lobby           (GenServer: агрегированный список столов)
├── Oban
└── Socket.Endpoint
```

### TableServer

* Адресация: `{:via, Registry, {BlockPoker.Tables.Registry, {:table, table_id}}}`.
* Состояние: `%BlockPoker.Engine.TableState{}` + метаданные (таймеры, подписчики).
* Все мутации — `handle_call`/`handle_cast`, внутри вызывается **чистая**
  `Engine.Rules.apply_action/2`, возвращающая новое состояние и список событий.
* Таймеры хода — `Process.send_after/3` с монотонным `deadline_ref`;
  просроченный таймер игнорируется, если ref устарел.
* После обработки: события уходят в `PubSub` на топик `"table:<id>"`,
  плюс адресные сообщения игрокам с приватными картами.
* Падение процесса стола не роняет остальные столы (`:one_for_one`).
  Незавершённая раздача при падении — см. §8.

## 5. Транспорт и протокол

### Аутентификация

1. REST `POST /api/auth/login` → short-lived socket-токен
   (`Phoenix.Token.sign/4`, TTL ~1 час) + refresh-токен.
2. Клиент подключается: `wss://.../socket/websocket?token=...`.
   `UserSocket.connect/3` верифицирует токен и кладёт `user_id` в `socket.assigns`.
   Неверный токен → отказ в handshake.
3. Каналы никогда не доверяют `user_id` из payload — только `socket.assigns`.

### Каналы

| Топик | Назначение |
|---|---|
| `lobby` | список столов, количество игроков, фильтры, уведомления о новых столах |
| `table:<uuid>` | посадка, действия, стрим состояния конкретного стола |

### Формат сообщений

Клиент → сервер:

```
"join_seat"   %{seat: 3, buy_in: 10_000}
"leave_seat"  %{}
"action"      %{type: "raise", amount: 800, hand_id: "...", action_seq: 42}
"sit_out"     %{}
"chat"        %{text: "..."}
```

Сервер → клиент:

```
"table_state"    полный персональный снапшот (после join / реконнекта)
"table_delta"    инкрементальное событие (ставка, новая улица, вскрытие)
"your_cards"     приватно, только владельцу
"action_prompt"  %{deadline_ms: ..., legal_actions: [...]}
"error"          %{code: "...", message: "..."}
```

**Правила протокола**

* Все суммы — целые числа в минимальных единицах (центы/фишки). Никаких float.
* `action_seq` — монотонный счётчик стола. Клиент присылает тот, который видел;
  сервер отвергает действие с устаревшим seq (защита от даблкликов и лагов).
* Идемпотентность: повтор того же `action_seq` — no-op, а не второй рейз.
* Все коды ошибок — из единого списка (`BlockPoker.ErrorCode`), не свободный текст.
* Версия протокола передаётся при `connect` (`vsn`); несовместимая → отказ
  с понятным кодом, чтобы Electron предложил обновление.

### Реконнект

Соединение может рваться. Место за столом при разрыве **не освобождается сразу**:
`TableServer` держит grace-период; вернувшийся внутри окна игрок получает
`table_state` и продолжает играть. По истечении — авто-fold / sit-out.
`Presence` используется для отображения онлайна, но **не** как источник истины
о занятости места.

## 6. Модель данных (MySQL)

Хранит то, что должно пережить рестарт. Схема — в миграциях, здесь только карта.

* `users` — учётка, `email`, `password_hash` (Argon2), статус.
* `refresh_tokens` — хэши refresh-токенов, отзыв.
* `wallets` — денормализованный текущий баланс (кэш поверх ledger).
* `wallet_entries` — **append-only ledger**: `user_id`, `amount` (signed),
  `type` (`deposit` / `buy_in` / `cash_out` / `rake` / `adjustment`), `ref_id`,
  `idempotency_key` (unique). Баланс — сумма записей; `wallets` пересчитываем и сверяем.
* `table_configs` — конфигурация столов (блайнды, макс. игроков, лимиты бай-ина,
  рейк). Из этих строк лобби поднимает `TableServer`.
* `hands` — сыгранная раздача: id, стол, время, борд, победители, пот, рейк.
* `hand_actions` — упорядоченные действия раздачи (реплей, разбор жалоб).
* `hand_players` — участники: стартовый стек, карманные карты (после шоудауна), результат.

**Правила БД**

* Все денежные операции — только через `Ecto.Multi` в транзакции, с
  `idempotency_key`. Ни одна ручка не меняет баланс вне ledger.
* Раздача пишется **одним batch-инсертом по завершении**, а не по ходу улиц.
  Запись — асинхронная задача, не блокирующая следующую раздачу.
* Никаких бизнес-правил в триггерах и хранимках. Правила — в Elixir.
* Все таймстемпы — `utc_datetime_usec`.

## 7. Поток данных (одно действие игрока)

```
Electron ──"action"──▶ TableChannel
                        │  проверка: сокет аутентифицирован, seq актуален
                        ▼
                     Tables.act(table_id, user_id, action)
                        │  :via Registry
                        ▼
                     TableServer.handle_call
                        │  чистый вызов
                        ▼
                     Engine.Rules.apply_action(state, action)
                        │  {:ok, new_state, events} | {:error, reason}
                        ▼
                     TableServer: сохранил state, взвёл таймер
                        │
        ┌───────────────┼────────────────────────┐
        ▼               ▼                        ▼
   PubSub broadcast   адресно игроку       (по завершении раздачи)
   "table_delta"      "your_cards"          History.persist_async
        │
        ▼
   TableChannel.handle_info ──▶ TableView.render(state, for: user) ──▶ Electron
```

`TableView` — единственное место, где состояние превращается в то, что видит
конкретный игрок. Приватная информация вырезается **здесь**, и нигде больше.

### Про CQRS и event sourcing

**Полноценный CQRS/ES не используем.** Решение осознанное, не по незнанию.

Почему нет:

* Главная выгода ES — аудит и восстановление истории — у нас **уже закрыта**
  таблицей `hand_actions`: упорядоченный лог всех действий раздачи, достаточный
  для реплея и разбора жалоб. ES дал бы то же самое ценой отдельной инфраструктуры.
* `Commanded` / `EventStore` в экосистеме Elixir практически привязаны к Postgres.
  На MySQL пришлось бы писать event store руками — это отдельный проект.
* Eventual consistency между write- и read-моделью за покерным столом —
  прямой баг: игрок обязан видеть результат своего действия немедленно.
* Проекции и версионирование событий — постоянная налоговая нагрузка на команду,
  которая окупается на масштабе, до которого мы ещё не дошли.

Что при этом **берём** из подхода — форму, а не фреймворк:

* `Engine.Rules.apply_action(state, action) -> {:ok, state, events}` — это
  command handler в чистом виде: команда на входе, новое состояние и список
  фактов на выходе. Тестируется без процессов и БД.
* `events` — единственный источник и для broadcast'а клиентам, и для записи
  в `hand_actions`. Одни и те же факты, два потребителя.
* Разделение команд и запросов де-факто есть: пишет `TableServer`, читают из
  его же памяти через `TableView`. Разделены операции — **не** хранилища.

Явный запрет на будущее: не заводить отдельную read-модель игрового состояния
в БД и не синхронизировать её асинхронно. Источник истины по активному столу
один — процесс `TableServer`.

## 8. Отказоустойчивость

* Падение `TableChannel` — рвётся одно соединение, стол цел.
* Падение `TableServer` — супервизор поднимает стол заново. Незавершённая
  раздача аннулируется: ставки текущей раздачи возвращаются игрокам из снапшота
  стеков, зафиксированного в начале раздачи; стол стартует новую раздачу.
* Деньги защищены тем, что уходят/приходят в ledger только на buy-in и cash-out,
  а не на каждой ставке.
* Рестарт ноды: столы поднимаются из `table_configs` пустыми, игроки
  переподключаются. Фишки, бывшие на столах, возвращаются в кошельки через
  отдельный recovery-шаг по последнему снапшоту.
* Первая версия — **одна нода**. Кластеризация (Horde/libcluster) не закладывается
  в код, но `Tables` API спроектирован так, чтобы адресация стола осталась
  единственным местом, требующим изменений при переходе на кластер.

## 9. Безопасность

* Клиенту не отправляется ничего, что он не должен знать. Проверяется тестом:
  сериализованный `table_view` для игрока не содержит чужих `hole_cards`.
* Тасовка — Fisher–Yates на `:crypto.strong_rand_bytes/1`. `:rand` для карт **запрещён**.
  В тестах RNG подменяется через параметр, а не через глобальный seed.
* Все действия валидируются на сервере: очередь хода, легальность действия,
  границы суммы. Клиентский `legal_actions` — подсказка UI, не разрешение.
* Rate limiting на канал (действия, чат) и на REST (логин).
* Пароли — Argon2. Токены хранятся хэшами.
* Логи не содержат карт, токенов и паролей (фильтры Logger metadata).
* Античит-хуки (коллюзия, мультиаккаунт) в первой версии не реализуются, но
  `hand_actions` пишется в объёме, достаточном для последующего анализа.

## 10. Конвенции кода

* `mix format` обязателен; CI падает на `mix format --check-formatted`.
* Публичные функции контекстов возвращают `{:ok, _}` / `{:error, reason}`.
  `!`-варианты — только там, где падение действительно уместно.
* `@spec` на всех публичных функциях контекстов и `engine`.
* Структуры — с `@enforce_keys` для обязательных полей.
* Имена: контекст — во мн. числе (`Accounts`, `Tables`), схема — в ед. числе
  (`User`, `HandRecord`).
* Никаких вызовов `Repo` из `socket` и `api` — только через контексты.
* Функция канала или контроллера, длиннее ~15 строк, — почти всегда признак
  утёкшей туда бизнес-логики. Проверить по критериям §3.
* Никаких `Process.sleep` в тестах; таймеры стола прогоняются вручную через
  инжектируемый источник времени.
* Тесты `engine` — без БД и без процессов, должны быть мгновенными.
* Каждый баг в правилах покера сначала воспроизводится тестом в `test/block_poker/engine`.

## 11. Тестирование

### Общее правило

**Базу данных не мокаем.** Мок БД в Elixir — антипаттерн: значительная часть
гарантий по деньгам обеспечивается самой MySQL (`unique` на `idempotency_key`,
откат транзакции, внешние ключи). Мок этих правил проверяет мок, а не продакшен.
Изоляция достигается `Ecto.Adapters.SQL.Sandbox` поверх **настоящей тестовой
MySQL**: каждый тест выполняется в транзакции, которая откатывается после.
Требование — движок InnoDB.

`Mox` применяем только к тому, что действительно недетерминированно или внешне:
**RNG** и **источник времени**. Оба — через behaviour, реализация выбирается
конфигом. Ничего другого мокать не нужно; необходимость мока обычно означает,
что зависимость надо инжектировать явным аргументом.

### Уровни

| Уровень | Что покрывает | БД | Скорость |
|---|---|---|---|
| 1. Unit + property | `block_poker/engine/*` — правила покера | нет | мгновенно, `async: true` |
| 2. Процессы | `block_poker/tables/*` — TableServer, таймеры, реконнект | нет | быстро |
| 3. Контексты | `accounts`, `wallet`, `history` — интеграция с БД | Sandbox | средне |
| 4. Функциональные | каналы и HTTP насквозь: сообщение → ядро → ответ | Sandbox (`:shared`) | медленно |

**1. Ядро правил.** Основная масса тестов. Без БД, без процессов, без Phoenix.
Обязательно property-тесты (`StreamData`) для инвариантов, которые легко нарушить
частными случаями: сумма всех потов равна сумме вложенных фишек; фишки не
возникают и не исчезают; сравнение комбинаций тотально и транзитивно; сайд-поты
при нескольких all-in. Колода тасуется инжектируемым RNG — раздача воспроизводима
по seed.

**2. Процессы столов.** `start_supervised!` на изолированном столе. Таймеры хода
**не отсчитываются реальным временем**: часы инжектируются, срабатывание таймаута
прогоняется вручную. `Process.sleep` в тестах запрещён — он делает тесты
медленными и флаки. Отдельно проверяется восстановление после падения
`TableServer` и поведение при реконнекте в grace-периоде.

**3. Контексты.** Реальная MySQL под Sandbox. Ключевое, что здесь обязано
проверяться на настоящей базе:

* повторный вызов с тем же `idempotency_key` не создаёт вторую запись ledger
  (проверяется, что срабатывает именно constraint БД);
* баланс, посчитанный как сумма `wallet_entries`, сходится с `wallets`;
* откат транзакции при неудачном шаге `Ecto.Multi` не оставляет частичных записей;
* конкурентные buy-in одного пользователя не уводят баланс в минус.

**4. Функциональные.** `Phoenix.ChannelTest` — путь целиком: клиент шлёт
сообщение, ядро отрабатывает, клиент получает push. Сюда же — сценарии
двух и более игроков за одним столом (несколько подключённых сокетов).
Sandbox в режиме `:shared`, потому что работают несколько процессов;
такие тесты — `async: false`.

### Обязательные тесты-инварианты

Эти проверки существуют независимо от фич и не удаляются:

* **Приватность.** Сериализованный `TableView` для игрока не содержит чужих
  `hole_cards`, остатка колоды и seed RNG. Проверяется на сыром payload, а не
  на структуре — тест ищет отсутствие данных в том, что реально уйдёт в сокет.
* **Границы слоёв.** Автотест на архитектуру: в `lib/socket/**` и `lib/api/**`
  нет упоминаний `Repo`, `Ecto.Query` и доменных состояний раздачи (§3).
* **Сохранение фишек.** Ни один сценарий не меняет суммарное количество фишек
  в системе, кроме явных `deposit` / `cash_out` / `rake`.

### Дисциплина

* Каждый баг в правилах покера **сначала** воспроизводится тестом в
  `test/block_poker/engine`, потом чинится.
* Тесты уровня 1 должны оставаться мгновенными: `mix test test/block_poker/engine`
  — это команда, которую гоняют постоянно, она не имеет права ходить в БД.
* `async: true` по умолчанию везде, где нет `:shared` sandbox.
* Фикстуры — через фабрики контекстов, не через прямые `Repo.insert`.
* Покрытие не является целью; целью является отсутствие непроверенных
  денежных и карточных путей.

## 13. Локальное окружение (Windows)

Инструменты ставятся вне проекта, версии — фактические на момент разворачивания:

| Компонент | Версия | Путь |
|---|---|---|
| Erlang/OTP | 27.3.4.13 | `C:\Program Files\Erlang OTP` |
| Elixir | 1.20.3 (OTP 27) | `C:\Elixir` |
| MySQL | 8.4.4 (модуль OSPanel) | `E:\OSPanel\modules\MySQL-8.4\bin` |

### MySQL

OSPanel биндит MySQL не на `127.0.0.1`, а на собственный loopback-алиас
**`127.127.126.32:3306`** — именно этот хост прописан в `config/dev.exs` и
`config/test.exs`. Пользователь `root` с пустым паролем (дефолт OSPanel).

Базы: **`block-poker`** (dev) и **`block-poker_test`** (test). Имя с дефисом,
поэтому в сыром SQL — только в бэктиках.

Если лаунчер OSPanel не запускается, сервер поднимается напрямую тем же конфигом:

```
E:\OSPanel\modules\MySQL-8.4\bin\mysqld.exe --defaults-file=E:\OSPanel\modules\MySQL-8.4\my.ini
```

Проверка: `mysql -u root --host=127.127.126.32 -e "SELECT VERSION();"`

### Сборка NIF (argon2_elixir)

`argon2_elixir` — NIF на C. На Windows `elixir_make` требует именно `nmake`
из Visual C++ Build Tools; MinGW не подходит, `Makefile.win` написан под nmake.
Установлены **VS 2022 Build Tools 17.14** (workload VCTools) в
`C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools`.

`nmake` не лежит в PATH постоянно, поэтому **пересборка NIF** делается из
окружения vcvars, отдельно для каждого `MIX_ENV`. Из `cmd`:

```
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvarsall.bat" x64
mix deps.compile argon2_elixir --force
set MIX_ENV=test
mix deps.compile argon2_elixir --force
```

Собранный NIF лежит в `_build/<env>/lib/argon2_elixir/priv/argon2_nif.dll`.
Пока он на месте, обычные `mix test`, `mix compile` и `mix phx.server`
работают из любой оболочки — MSVC им не нужен. Окружение vcvars требуется
только после `mix deps.clean`, `deps.update` или смены версии Elixir/OTP.
